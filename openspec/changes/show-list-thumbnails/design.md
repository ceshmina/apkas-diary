## Context

動機は proposal.md - Why を参照。要求は specs/diary-site-pages/spec.md を参照。

いまの姿を5つ書き出す。この change の判断はこの5つから出ている。

**1. 一覧は1つの部品を4つのページが共有している。** トップ・年別・月別・月日ページは、いずれも `src/components/EntryList.astro` に `Entry[]` を渡すだけである。行は `<a>` の中に日付の部品（`DateBlock`）と題を置いた grid で、**題の有無を `.date-block:only-child` で見分けている**（題がなければ日付の部品が唯一の子になる）。行に縮小画像を足すと、題のない行でも日付の部品が唯一の子ではなくなり、この見分け方は成り立たない。

**2. 一覧に渡るエントリは、既に本文を持っている。** 一覧はすべて `publishedEntries()`（GSI1 の Query 1本）の結果を切り分けたもので、`Entry.body` を含む。**写真を拾うために取得を増やす必要はない。**

**3. 本文の写真は、すべて `medium` の配信 URL で書かれている。** production の本文に現れる日記の写真の URL は 2,416 箇所あり、すべて `https://photos.apkas.net/medium/<配信パス>` の形である。派生画像は4つのサイズが常に揃っており（`photo-ingest`）、サイズ名を差し替えれば同じ写真の `thumbnail` が得られる（`photo-delivery`）。`thumbnail` は長辺 240px に収めたもの（横位置の 3:2 なら 240×160）で、平均 7.5KB。旧サイトから移した写真も含め、年をまたいで抜き取って確かめたものはすべて `thumbnail` を返した。

**4. 本文の文字列に現れる写真の URL が、すべて画面に出ているわけではない。** production に1件、`[](https://photos.apkas.net/medium/2026/01/25/….webp)` と `!` の抜けた記法で書かれた本文がある（2026-01-25）。これは画像ではなく空のリンクとして整形され、日別ページには写真が出ていない。撮影機材の引き当て（`photoEquipment()`）は本文の文字列から URL を拾っているが、あちらは「どの日の目録を引くか」を決めるためのもので、余分に拾っても害がない。**一覧に並べる写真を同じ拾い方で決めると、日別ページに出ていない写真が一覧にだけ現れる。**

**5. 写真の枚数は日によって大きく違う。** 公開済み 1,139 件のうち、写真0枚が 399 件、1枚が 300 件、2枚が 170 件、3〜9枚が 225 件、10枚以上が 45 件（最大 36 枚、旅行の日に集中する）。題のない行が 695 件あり、トップページの最近の 20 件は写真のある日が 6 件で、どれも題を持たない。**一覧の姿は、写真のない行が続く場合と、1日に数十枚の行が続く場合の両方で破綻してはならない。**

## Goals / Non-Goals

**Goals:**

- ビルドの問い合わせと権限を増やさない。
- **日別ページで読み手が出会う写真と、一覧に並ぶ写真を一致させる。** 拾う規則を、日別ページの整形と同じ出どころに置く。
- 写真のない行に、写真のための空白や枠を持ち込まない。写真のある行とない行で、日付と題の位置を揃える。
- 一覧の行の既存の体裁（日付の部品、題の書体、罫線、手応え）を崩さずに足す。変えるのは PC 幅の列の幅と間隔だけとする（決定7）。

**Non-Goals:**

- **代表写真の指定。** どの写真を一覧に出すかを書き手が選ぶ仕組みは持たない。本文に現れる順で決まる。選びたくなったら、本文の並びを変えるのが唯一の手段になる。
- **新しい派生サイズ。** 既存の `thumbnail` / `small` で賄う（proposal.md - スコープ外）。
- **編集アプリケーションのプレビューへの反映。** プレビューは本文の整形を確かめる場で、一覧を持たない。

## Decisions

### 決定1: 写真は、整形した本文の `img` から拾う

一覧に並べる写真は、**日別ページと同じ整形（`renderMarkdown()`）を通した HTML に現れる `img` の `src`** から拾う。そのうち配信の基点で始まり、配信パスを取り出せるもの（`photoPathFromUrl()` が `undefined` を返さないもの）だけを残し、配信パスで重複を除く。順序は HTML に現れる順、すなわち本文に現れる順である。

本文の Markdown の文字列から URL を拾う形（`photoEquipment()` と同じ `PHOTO_URL_PATTERN`）は採らない。Context 4 のとおり、画面に出ていない写真まで拾ってしまう。Markdown の画像記法（`![…](…)`）と生の `<img>` だけを拾う正規表現を別に書く形も採らない。**日別ページに何が画像として出るかを決めているのは整形であり、その判定を正規表現でもう1つ持つと、2つがずれた日に一覧と日別ページが食い違う。**

整形した HTML から `img` を読むには、`src/lib/markdown.ts` が既に持っている `RAW_IMG` / `RAW_SRC`（生の HTML の `<img>` を、引用符の有無によらず読む正規表現）を使う。整形の出力は Markdown 由来の `img` と、素通りした生の `<img>` が混ざったものなので、両方を読めるこの2つがそのまま当てはまる。`markdown.ts` に「整形した HTML から `img` の `src` を順に返す」関数を1つ足して外に出す。

整形は重くないが、1,139 件の本文を一覧のためにもう1度整形することになる。`src/lib/site-data.ts` に、**エントリの日付ごとに結果を1度だけ作る memo** を置く（`publishedEntries()` と同じ流儀）。トップ・年別・月別・月日ページは同じエントリを繰り返し載せるが、整形は1件につき1度で済む。整形には機材の引き当てを渡さない（`renderMarkdown(body)`）。一覧が要るのは `src` だけである。

### 決定2: 縮小画像の URL は、配信パスとサイズ名から組み立てる

`src/lib/photo.ts` に、**配信パスとサイズ名から配信 URL を組み立てる関数**を足す。既存の `photoUrlOf(base, size, sourceKey)` は、この関数に `photoPathOf(sourceKey)` を渡す形に書き直す。作る文字列は変わらない。規約（サイズ名を先頭に置き、段ごとに符号化する）が1箇所に保たれる。

```
本文の img:  https://photos.apkas.net/medium/2024/03/04/20240304-151441.webp
photoPathFromUrl  ->  2024/03/04/20240304-151441.webp        （配信パス）
新しい関数('thumbnail', 配信パス)
             ->  https://photos.apkas.net/thumbnail/2024/03/04/20240304-151441.webp
```

URL の文字列の `/medium/` を `/thumbnail/` に置き換える形は採らない。本文が `medium` 以外のサイズで書かれた日に黙って壊れるうえ、`photo.ts` が「規約はこのファイル1つが持つ」と宣言しているところに、規約の写しをもう1つ作ることになる。

目録は引かない。URL を組み立てるのに要るものは、本文の URL だけで揃っている。

### 決定3: 縮小画像は行のリンクの中に置き、支援技術からは外す

縮小画像は行の `<a>` の中に置く。押すと行と同じ日別ページへ移る。縮小画像ごとのリンクも `tabindex` も持たせないので、キーボードで辿る位置は行ごとに1つのままである。

縮小画像の並びは `aria-hidden="true"` の要素で包み、`img` の `alt` は空にする。行の名前は、これまでどおり日付（読み上げ用の和文）と題で決まる。本文に書かれた写真の説明（`alt`）を一覧で読ませることはしない。説明は日別ページで写真とともに読むもので、一覧の行の名前に連ねると、1行が数十の説明の読み上げになる日がある（Context 5）。

### 決定4: 題の有無と写真の有無は、行の印で見分ける

Context 1 の `.date-block:only-child` をやめ、行の `<a>` に印の class を持たせる。**題のない行**と**写真のある行**の2つで、grid の組み方はこの2つの組み合わせで決まる。

印は描画の側（`EntryList.astro`）がエントリから決める。CSS が子の数や並びから推し量る形は、この change のように子が1つ増えるたびに崩れる。

### 決定5: 縮小画像は遅延読み込みにし、占める大きさを先に決める

- `loading="lazy"` と `decoding="async"` を付ける。年別ページは写真のある行が数百並ぶ（Context 5）。
- **縮小画像の枠の大きさは CSS だけで決める。** 正方形に切り抜き、大きさは列の幅から決まる（決定6）。枠が画像より先に決まるので、画像の寸法を知らなくてよく、目録を引かずに済む。`width` / `height` 属性には正方形の値を与え、読み込み前後で行の高さが変わらないようにする。
- 読み込みを待つあいだの枠には、罫線の色（`--border`）の面を置く。画像を読めなかったときも、その面が残るだけで行は崩れない。
- 角は `--radius` で立てる。tokens.css は既に「写真の縮小画像」を角を立てるものに数えている。
- 縮小画像そのものにホバーの手応えは付けない。行に触れたときの手応え（日の数字が朱になる、題に朱の下線）が、縮小画像に触れたときにも出る。

### 決定6: 題の下に正方形で並べ、入りきらない日は白に溶かす（見本の案 A′）

本番のエントリと写真で組んだ見本（https://claude.ai/artifact/84EXkG9ECFwMhiSHTRJ878）で比べて選んだ。

**位置。** スマートフォン幅では、題のある行は題の下に3段目として、題のない行は題の位置に並べる。PC 幅（`min-width: 42.5rem`）では、題のある行は題の列の下に、題のない行は題の列に並べる。どちらの幅でも、縮小画像は日付の数字の下には入らず、題と同じ列に収まる。**題のない行では行が2段のまま中身を持つ**ので、題のない行の多い最近の一覧（Context 5）でも間延びしない。

**大きさ。** 縮小画像は正方形で、大きさは**列の幅にちょうど「N 枚と半分」が入る値**にする。N は画面の幅で段を変える。

```
grid-auto-flow: column;
grid-auto-columns: calc((100% - N * <間隔>) / (N + 0.5));
overflow: hidden;
```

| 画面の幅 | 組み | 1行に見える枚数 | 大きさ |
|---|---|---|---|
| 〜432px（27rem） | スマートフォン | 5.5 枚 | 約 36〜56px（375px で約 46px） |
| 432〜552px（34.5rem） | スマートフォン | 7.5 枚 | 約 40〜56px |
| 552〜680px（42.5rem） | スマートフォン | 9.5 枚 | 約 44〜58px |
| 680px〜 | PC | 8.5 枚 | 約 57px（本文の列が 40rem で止まるので一定） |

**段を変えるのは、大きさを 36〜58px ほどに保つためである。** N を 5 に固定すると、大きさは列の幅に比例して伸び続ける。スマートフォンの横向きや狭いウィンドウ（430〜680px）では最大で約 100px になり、680px を境に PC の組みの約 57px へ急に縮む。PC 幅を 8.5 枚にしているのは、決定7で題の列が 416px から 506px に広がり、7.5 枚では約 65px になるためである。100px は `thumbnail`（短辺 160px）では2倍密度の画面で粗い。段の境目は、1つ下の段の大きさが約 56px に達する幅に置いた。

**入りきらない日。** N+1 枚目のある行だけ、半分見えている最後の1枚が右端で地の白に溶けていくよう、並びに `mask-image` の gradient を当てる。見分けは段ごとに `:has(> img:nth-child(6))`・`nth-child(8)`・`nth-child(10)`、PC 幅では `nth-child(9)` で行う。段が上がるたびに、下の段での当て方を打ち消す。スクリプトは使わない。

半端な「N 枚と半分」にしているのは、**入りきるかどうかを、段の中では画面の幅によらず枚数だけで決めるため**である。大きさを固定の値（44px など）にすると、1行に入る枚数が画面の幅で1枚ずつ変わり、「この行は入りきらない」を CSS だけでは見分けられない。見分けずに常に溶かすと、入りきる日にも右端が溶けて、続きがあるように見える（spec「行に入りきる枚数の写真」に反する）。枚数で幅を割れば、N+1 枚目の有無がそのまま「入りきらない」になり、半分の1枚が「先へ続いている」ことを形で示す。

`:has()` を解さないブラウザでは溶かしが当たらず、半分の1枚がそのまま切れて見える。並びは崩れず、続きがあることも読み取れる。

**HTML に載せるのは1行10枚まで**（いちばん多く見える段の 9.5 枚ぶん）。それより後ろの写真はどの幅でも見えないので、載せない。「+N」のような数の表示は置かない。

**採らなかった案。** 見本では次の4案を並べた。

| | A 題の下に並べる | B 右端に1枚 | C 原寸比の帯 | D 大きなタイル |
|---|---|---|---|---|
| 1行の上限 | 5枚＋「+N」 | 1枚 | 8枚（右端を白に溶かす） | 4枚（4枚目に「+N」を重ねる） |
| 切り抜き | 正方形 | 正方形 | しない | 正方形 |
| 2024年の年別ページ | 最大 806 枚・約 6MB | 最大 300 枚・約 2.2MB | 最大 975 枚・約 7MB | 最大 729 枚・約 5〜50MB |

- **A** は位置と大きさの考え方をそのまま引き継いだ。枚数で切って「+N」と数を書くのをやめ、C の「白に溶かす」切り方に替えたのが A′ である。数の表示は、欠けたものを文字で数えさせる。溶かせば、先があることだけが静かに伝わる。
- **B** は最も軽く静かだが、1枚だけでは旅行の日と1枚の日が同じ姿になり、1枚目が代表として適切とも限らない（Non-Goals の代表写真の指定）。
- **C** は縦横比を保つので、枠の幅を先に決めるには写真の寸法が要り、一覧の生成が目録を読むようになる（Goals の「問い合わせを増やさない」に触れる）。
- **D** は PC でタイルが約 160px になり、`thumbnail`（短辺 160px）では粗い。`small` を使うと年別ページが最大約 50MB になる。写真のない行との高さの差も最も大きい。

### 決定7: PC 幅の列の幅と間隔を、字面に合わせて詰める

いまの PC 幅の行は、数字・添え書き（月と曜日）・題の3列を `3.6rem 8rem 残り`、間隔 `1.2rem` で組んでいる。添え書きの字面は「May 2026」でも 62px ほどしかなく、8rem（128px）の列の半分以上が空いている。数字の列も、いちばん広い「20」（37px ほど）より 20px 以上広い。縮小画像を題の列に並べると、これらの空きが題と縮小画像をまとめて右へ押しやり、行の中ほどに穴が開いて見える。

PC 幅の列を次のように改める。スマートフォン幅は変えない。

| | いま | 改めたあと |
|---|---|---|
| 数字の列 | 3.6rem・左寄せ | 2.35rem・左寄せ |
| 添え書きの列 | 8rem | 4rem |
| 列の間隔 | 1.2rem | 1rem |
| 題の列の幅 | 416px | 506px |

- **列の幅は書体の字幅から決めた。** ビルドが配る Instrument Serif・Instrument Sans のファイルから、字間を含めた幅を計算した。数字（2.8rem）はいちばん広い「20」が 36.9px、添え書き（0.7rem）は「May 2026」が 61.8px。それぞれを少し上回る rem に丸めている。添え書きはどの一覧も年を含むので（決定8）、列の幅は1つで足りる。
- **数字は左に寄せ、一覧の左端（上の罫線の始まり）に揃える。** 右に寄せる形も見本で試したが、数字の列を2桁の幅で取る以上、2桁の日でも左に余りが出て、一覧の左端から数字が離れて見えた。左に寄せると、1桁の日（1〜9日）は数字と添え書きの間が 20px ほど広くなるが、添え書きの列が縦に揃っているほうを取る。
- 添え書きの字面は、月の略記（3字）・年（4桁）・曜日の略記（3字）に限られるので、固定の幅で足りる。**列の幅を `auto` にする形は採らない。** 行はそれぞれ別の grid なので、`auto` は行ごとに違う幅になり、題の位置がずれる。一覧全体を1つの grid にして行を `subgrid` にすれば揃うが、スマートフォン幅の組み（2列・2段）まで作り直すことになり、この change の範囲を超える。
- 添え書きには `white-space: nowrap` を当てる。書体の読み込みを待つあいだの代わりの書体が少し広くても、列の中で折り返して行の高さが変わることはない。
- **写真のない行にも同じ詰め方を当てる。** 写真のある行だけを詰めると、行ごとに題の位置がずれる（spec「写真のない日の行には写真に関わる表示を出さない」）。

### 決定8: 一覧の日付は、どの一覧でも年を含めて示す

いまの一覧の部品は `showYear` を受け取り、年別・月別のページだけ年を省いている（`Sep`）。これをやめ、4つの一覧のどれでも `Sep 2026` と示す。

- 一覧の見え方をこの change でそろえ直すのに合わせて、書き手が統一を選んだ。
- **添え書きの列が1つの幅で済む**（決定7）。年を省く一覧だけ列を細くすると、一覧によって題と縮小画像の始まる位置が変わり、縮小画像の大きさも変わる（PC で約 57px と約 61px）。1つにすれば、4つの一覧が同じ寸法で並ぶ。
- 年別・月別のページでは、見出し（`2026`・`Sep`）にも年や月が出ているので、行の年は重なる。一覧の行は日別ページへの入口であり、どの一覧から見ても同じ形であるほうを取る。

一覧の部品の `showYear` を外し、年別・月別のページが `showYear={false}` を渡すのをやめる。日付の部品（`DateBlock`）の `showYear` も、使っていたのは一覧だけなので外す。日別ページは既定（年つき）で呼んでいるので変わらない。`datePartsEn` の `{ year: false }` は前後の導線の日付（`formatDateEn`）が使っているので残し、説明から「年の中の一覧では年を省く」だけを消す。

スマートフォン幅では、年別・月別の一覧の添え書きが `Sep · Tue` から `Sep 2026 · Tue` に伸びる。1行で約 100px で、列（375px の画面で約 270px）に収まる。

### 決定9: ページの見出しを本文と同じ字面にする

ページの見出しの部品（`PageHead`）は、飾りの大きな語（`Recent`・`2026`・`Mar`）に和文の見出し（`h1`、「2024年3月の日記」など）を添えている。和文の見出しは、いま小さなラベルの字面（0.78rem・太さ 500・字間 0.24em）で組んでいる。これを本文の字面にそろえる。

| | いま | 改めたあと |
|---|---|---|
| 大きさ | 0.78rem | `--text-prose`（本文と同じ。15px、PC 幅で 15.5px） |
| 太さ | 500 | 400 |
| 字間 | 0.24em | 0.04em |
| 色 | 淡い文字（`--fg-muted`） | 変えない |
| 書体・約物の詰め | ゴシック・詰めない | 変えない（本文も詰めない） |

- 書き手の判断による。字間を広げたラベルの字面は、和文の見出しを飾りの英字に添える小さな印として組んだものだが、見出しとして読む文には本文の字面のほうが素直である。
- 大きさは tokens.css の `--text-prose` をそのまま使い、新しい値を足さない（`visual-identity`「体裁の基準は1つの出どころを持つ」）。
- 色を淡いまま残すので、飾りの大きな語（黒）と見出し（淡い）の強弱は変わらない。要素は `h1` のままで、読み上げと見出しの辿り方も変わらない。
- **トップの「年別」の見出し（`.section-title`）は変えない。** あちらは編集アプリケーションの節の題と共有している字面で（base.css）、変えると編集アプリケーションの画面まで変わる。

## Risks / Trade-offs

- **[年別ページの読み込み量]** 写真の多い年は、1ページに千前後の縮小画像が載る（2024 年で最大 1,056 枚・約 8MB）。→ 遅延読み込みで、実際に読まれるのは画面に近づいた行の分だけにする。枚数の少ない段では、行の中ではみ出して見えない分（5.5 枚の段なら7〜10枚目）も HTML にあり、ブラウザによってはそれも読む。1行10枚を上限にしてあるので、増えるのは1行あたり4枚までである。HTML に増える `img` は1枚あたり 200 バイト前後で、2024年の年別ページでも HTML の増分は 200KB に収まる。
- **[高密度の画面での精細さ]** `thumbnail` の短辺は 160px（横位置 3:2）。大きさはどの幅でも約 58px 以下なので、2倍密度では 116px 分で足りる。3倍密度のスマートフォン（375px で約 46px）では 138px 分で足りる。幅 430px 前後の3倍密度の端末では最大約 56px で 168px 分が要り、5% ほど引き伸ばすが、見て分かる差ではない。
- **[狭い画面での大きさ]** 大きさを列の幅から決めるので、320px の画面では約 36px まで小さくなる。→ 一覧の縮小画像は「その日を思い出す手がかり」で、写真を見せる場所ではない。手がかりとしては足りる。広いほうは段を変えて約 58px で止める（決定6）。
- **[段の境目での大きさの変化]** 段が変わる幅（432px・552px）の前後で、大きさが約 56px から約 40〜44px に変わる。680px では PC の組みに替わり、約 57px になる。→ 画面の幅を変えながら見比べないかぎり気づかない差で、1つの画面の中では大きさは揃っている。
- **[写真のない行の見た目も変わる]** 決定7は PC 幅のすべての行に当たるので、写真のない行も、添え書きと題の位置が左へ寄る。→ 行どうしの揃いを保つためで、変わるのは列の幅と間隔だけである。スマートフォン幅の行は変わらない。
- **[年別・月別で年が重なる]** 見出しと行の両方に年が出る（決定8）。→ どの一覧でも行が同じ形であることを取った。行の添え書きは淡い小さな字で、見出しと競わない。
- **[書体を読み込む前の添え書き]** 列の幅は Instrument Sans の字幅に合わせてあり、余りは 2px ほどしかない。読み込みを待つあいだの代わりの書体では、添え書きが列からはみ出しうる。→ `white-space: nowrap` で折り返しを止め、行の高さは変えない。はみ出しは列の間隔（1rem）の中に収まり、読み込みが済めば元に戻る。
- **[縦位置の写真の切り抜き]** 正方形に切り抜くと、縦位置の写真は上下が、横位置の写真は左右が落ちる。→ 写真を見る場所は日別ページの拡大表示である。切り抜きを避ける案（C）は、目録の寸法を要するので採らなかった（決定6）。
- **[ビルド時間]** 一覧のために本文をもう1度整形する（決定1）。→ エントリごとに1度だけ作る memo を置く。1,139 件の整形が増えるだけで、ページの数には比例しない。staging のビルドで増分を測る（tasks.md）。
- **[`!` の抜けた画像記法]** Context 4 の本文は、一覧でも写真が出ない。→ 日別ページと一致しているので、これは正しい振る舞いである。本文を直せば、日別ページと一覧の両方に写真が出る。
- **[代表写真を選べない]** 一覧の先頭に来る写真は本文の順で決まり、書き手は選べない。→ Non-Goals。複数枚を並べるので、1枚目が最適でなくても日の手がかりは残る。

## Migration Plan

1. 通常の公開手続きで staging に出し、4つの一覧とスマートフォン幅・スクリプトなしの表示を確かめる。
2. production に出す。データの移行はない。
3. 戻すときは、この change のコミットを戻して公開し直す。データにも基盤にも手を入れていないので、戻した時点で元の姿に戻る。
