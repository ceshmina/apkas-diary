## Context

動機は [proposal.md](proposal.md) の Why にある。ここでは移す先の値と、移したときに日記の側で何が起きるかを決める。

出どころは `../apkas/src/assets/style.css` の `:root` と、同リポジトリの `カラーパレット.png`。パレットは8色ある。

| 役割 | 名前 | 値 |
| --- | --- | --- |
| PRIMARY | Sirka Blue | `#2F5FA7` |
| DEEP | Midnight Sirka | `#172D4F` |
| DARK | Blue Shadow | `#243B5A` |
| LIGHT | Mist Blue | `#A9BDD9` |
| PALE | Blue Haze | `#DCE6F2` |
| NEUTRAL | Cloud White | `#F5F6F4` |
| NEUTRAL DARK | Ink | `#181A1D` |
| ACCENT | Dusk Mauve | `#9A7894` |

ポートフォリオは8色をそのまま変数に置いてはいない。小さい文字でコントラストが 4.5:1 に届かない箇所（淡い文字、暗い設定のアクセント）は、色みを保ったまま明度だけを寄せた値を使っている。日記は同じ役割の変数を同じ名前で持つので、パレットの原色ではなく**ポートフォリオが調整した後の値**を写す。ここを取り違えると、コントラストの検討をもう一度やり直すことになる。

制約は前回から変わらない。別リポジトリ・別配信なので CSS は共有できず、日記は写しを持つ。基準値の出どころは日記の中では `src/styles/tokens.css` の1つで、公開サイトと編集アプリケーションはこれを共に読む。

## Goals / Non-Goals

**Goals:**

- 日記の14個の色（明暗7つずつ）が、ポートフォリオの対応する値と1文字も違わないこと。
- 色を入れ替えた後も、日記に固有の組み合わせ（ピル、囲み、フォーカス環、入力欄）が読めること。ポートフォリオはこれらを持たないので、あちらの検討はここまで及んでいない。
- 写しが2つある箇所（`theme-color`）を取り残さないこと。

**Non-Goals:**

- 色以外の基準値に触れること。
- 日記の側で色を作ること。ポートフォリオにない値が必要になったら、それは基準の不足であって日記の裁量ではない。

## Decisions

### 決定1：変数の対応は前回のまま、値だけを差し替える

対応表は align-with-portfolio で決めたものを使う。`--fg` = `--ink`、`--fg-muted` = `--muted`、`--border` = `--line`、`--bg` / `--surface` / `--accent` / `--accent-soft` は同名。

写す値は次のとおり。「由来」は、その値がパレットの原色そのものか、ポートフォリオが調整したものかを示す。

**明るい設定**

| 日記 | 旧 | 新 | 由来 |
| --- | --- | --- | --- |
| `--fg` | `#1c1a18` | `#181a1d` | Ink |
| `--fg-muted` | `#6d655d` | `#566a85` | Blue Shadow を明るく寄せたもの |
| `--bg` | `#faf8f5` | `#f5f6f4` | Cloud White |
| `--surface` | `#fff` | `#fff` | 変わらない |
| `--accent` | `#b0512a` | `#2f5fa7` | Sirka Blue |
| `--accent-soft` | `#f3e6dd` | `#cfdef2` | Sirka Blue の淡い地。パレットの原色ではない |
| `--border` | `#e5ded4` | `#dce6f2` | Blue Haze |

**暗い設定**

| 日記 | 旧 | 新 | 由来 |
| --- | --- | --- | --- |
| `--fg` | `#ece6de` | `#f5f6f4` | Cloud White |
| `--fg-muted` | `#a2988c` | `#a9bdd9` | Mist Blue |
| `--bg` | `#15120f` | `#172d4f` | Midnight Sirka |
| `--surface` | `#1d1916` | `#243b5a` | Blue Shadow |
| `--accent` | `#e39264` | `#8fb4e2` | Sirka Blue を明るく寄せたもの |
| `--accent-soft` | `#2a1f18` | `#22406b` | 暗い設定のピルの地。パレットの原色ではない |
| `--border` | `#2e2822` | `#355073` | 罫線。パレットの原色ではない |

`--surface` だけは明るい設定で `#fff` のまま変わらない。ポートフォリオも同じで、Cloud White の地の上に置く囲みは純白になる。

**代替案：パレットの原色だけを使い、調整値は日記でも作り直す。** 採らない。同じ役割に別の値が入り、「同じ基準に従う」が値の一致で確かめられなくなる。

### 決定2：`--accent-alt` と `--shadow` は持ち込まない

ポートフォリオはこの2つを持つが、当たっている先は経歴の期間（`.timeline__period`）と円形アイコンの影（`.avatar`）で、日記にはどちらの要素もない。

使い道のない基準値を先に置くと、次に「ここだけ色を変えたい」と思ったときに、根拠のないまま手が伸びる先になる。必要になった時点で、ポートフォリオの同じ変数から写せばよい。

**代替案：将来のために先に置く。** 採らない。上のとおり。

### 決定3：`theme-color` は `--bg` と同時に動かす

`theme-color` の meta は CSS 変数を読めないため、`--bg` の値を手で書き写している。公開サイトと編集アプリケーションの2箇所にあり、それぞれ明暗2つで計4つ。

これは日記の中に写しが2つある唯一の箇所で、片方だけ動かすと、ブラウザの枠だけが古い色のまま残る。既にコメントで「値は tokens.css の `--bg` と同じ」と断ってあるので、この文言は残したまま値だけ差し替える。

**代替案：`theme-color` をやめる。** 採らない。枠の色が地と揃うことは `visual-identity` の要件（「ブラウザの枠との連続」）である。

### 決定4：日記に固有の組み合わせは、写す前にコントラストを測る

ポートフォリオは囲み（`--surface`）の上に淡い文字を置かず、ピルの地の上のアクセント色も日記ほど多く使わない。入力欄・ボタン・`is-quiet` のピルに至っては要素そのものがない。したがって、あちらで 4.5:1 が確かめられていても、日記の組み合わせは別に測る必要がある。

実測した結果、日記に実在する11通りの組み合わせは明暗とも基準を満たす。最も低いのは明るい設定のピル（`#2f5fa7` on `#cfdef2`）で 4.64、暗い設定のピル（`#8fb4e2` on `#22406b`）で 4.86。いずれも 4.5 を上回る。淡い文字は囲みの上で 5.53（明）/ 5.93（暗）。

地から浮くことが要る組み合わせ（囲み対地、ピルの地対地）は、いずれも旧の値より差が開いた。囲みは 1.060 → 1.084（明）、1.069 → 1.212（暗）。ピルの地は 1.154 → 1.259（明）、1.162 → 1.321（暗）。

**測った値をコメントや spec に書き残すことはしない。** 出どころがポートフォリオである以上、日記に数値の根拠を持たせると出どころが2つになる。記録はこの design と tasks に置く。

### 決定5：罫線が明るい設定でわずかに淡くなることは受け入れる

`--border` 対 `--bg` は明るい設定で 1.259 → 1.164 と、旧の値よりわずかに差が縮む。暗い設定では逆に 1.282 → 1.670 と開く。

Blue Haze はパレットの PALE にあたる色で、「空気のように軽い青の霞」として定義されている。淡いことはこの色の性質であって、逸脱ではない。ここで日記だけ濃い罫線を作れば、`visual-identity` の「日記の側で基準を新しく作ってはならない」に反する。ポートフォリオの同じ罫線が同じ淡さで出ている以上、日記だけ違う理由がない。

**代替案：日記だけ罫線を一段濃くする。** 採らない。上のとおり。淡すぎると分かった場合に直すべき場所はポートフォリオの側である。

## Risks / Trade-offs

- **写し直しを忘れる形が、この変更では消えない** → 仕組みで防ぐことはスコープ外とした（proposal）。代わりに、確認の段で「配信物に旧い値が1件も残っていないこと」を色の文字列で検査する。前回も同じ方法で青（`#375e8a`）の残りを確かめている。今回の検査対象はテラコッタ（`#b0512a`）と旧い地（`#faf8f5` / `#15120f`）。
- **各ページの `<style>` に色が残っていた場合、そこだけ旧い配色のまま残る** → 前回 5.8 で「色と角丸の宣言は各ページから消えた」ことを確認しているが、その後に3つの変更（split preview、photo catalog、legacy photos）が入っている。実装の前に、`src/` と `editor/src/` を横断して色の直書きを検査する。
- **`PhotoZoom.astro` の `#000` と `rgb(255 255 255 / 0.72)` が検査に引っかかる** → これはトンマナの対象外と決めたもの（proposal のスコープ外、前回も同じ）。検査で見つかっても直さない。
- **公開ボタンとの競合** → 前回と同じ形の危険がある。編集アプリケーションの「公開」は GitHub の `main` を作り直して配るため、このブランチが `main` に入る前に手元から production へ配ると、ボタンが押された時点で公開サイトだけが旧い配色に戻る。下の Migration Plan で扱う。

## Migration Plan

前回（align-with-portfolio）は、ブランチのまま手元から production へ配り、マージまでのあいだ「公開」ボタンを押さないという運用で凌いだ。同じ綱渡りを繰り返さない。

1. staging へ配って確認する。ここは `main` と結び付いていないので、いつ配ってもよい。
2. **`main` にマージする。**
3. その後に production へ配る。マージ済みなので、「公開」ボタンが押されても配られるのは新しい配色である。

この順にすれば、公開サイトだけが旧い配色に戻る窓が開かない。

**切り戻し**：色以外に触れないため、`src/styles/tokens.css` と2つの `Base.astro` を戻して配り直せば元に戻る。データにも URL にも影響がなく、生成されるページの集合も変わらない。
