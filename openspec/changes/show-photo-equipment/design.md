## Context

動機は proposal.md - Why を参照。要求は specs/diary-site-pages/spec.md を参照。

いまの姿を4つだけ書き出す。この change の判断はすべてこの4つから出ている。

**1. 目録は既に機材を持っているが、サイトの生成はそれを読む経路を持たない。** 公開サイトのビルドの入力は `src/lib/site-data.ts` の1枚に閉じており、そこが読むのは `listAllPublished()`（GSI1 の Query）だけである。写真は GSI キー属性を書かないので索引に載らない（sparse index）。**同じテーブルに居ながら、いまのビルドからは見えていない。**

**2. 本文が写真について知っているのは配信 URL だけである。** 本文は Markdown（と旧サイトから引き継いだ HTML）で、写真は `https://<配信の基点>/medium/2026/08/13/DSCF1234.webp` の形で書かれている。目録の識別子も元写真のキーも本文には無い。しかも配信 URL の拡張子は常に `.webp` で、**元写真の拡張子（`.JPG` / `.HEIC` など）は URL からは復元できない**。目録の `sk` はファイル名（拡張子を含む）なので、URL から `sk` を組み立てることはできない。

**3. 公開手続きの role はベーステーブルへの Query を持たない。** `terraform/modules/publish` に「サイトの生成が読むのは GSI1 だけなので、Query は索引の ARN に限る。ベーステーブルへの Query は与えない」と書いてある。写真の目録（`pk = PHOTO#<日付>`）はベーステーブルにあるので、**権限を足さないかぎり、手元では動いて公開手続きだけが失敗する**。

**4. 拡大表示のセルは既に「写真＋説明」の2段でできている。** `PhotoZoom.astro` の `figure` が `img` と `figcaption` を縦に積み、`photo-zoom.ts` が移動のたびに中身を入れ替えている。説明の不在は `:empty { display: none }` で消している。

## Goals / Non-Goals

**Goals:**

- 記録されているものを、**日記に手を入れずに**読めるようにする。
- 機種の一覧・対応表をコードに持たない。知らない機材が来ても表示が崩れない。
- ビルドの入力が1つ増えても、下書きが流れ込む経路は増えないこと。
- 公開手続きの role が、いまと同じく**エントリのベーステーブルを引けない**ままであること。

**Non-Goals:**

- 露出・撮影日時の表示（proposal.md - スコープ外）。**ただし、それらを出すと決めたときに経路をもう1本引くことにはならない形にしておく。**
- 編集アプリケーションのプレビューへの反映。プレビューは本文の整形を確かめる場で、拡大の仕掛けを持たない。
- 目録の書き込み・スキーマの変更。この change は読むだけである。

## Decisions

### 決定1: URL から目録を引くのではなく、目録から URL を組み立てて突き合わせる

本文の `img` の `src` と、目録の記録を**配信パス**で突き合わせる。配信パスとは、配信キー（`photoKeyOf`）からサイズ名を除いた部分である。

```
本文:  https://photos.apkas.net/medium/2026/08/13/DSCF1234.webp
                                ~~~~~~ サイズ名（捨てる）
                                       2026/08/13/DSCF1234.webp  ← 配信パス
目録:  sourceKey = 2026/08/13/DSCF1234.JPG
       photoKeyOf('medium', sourceKey) = medium/2026/08/13/DSCF1234.webp
                                                2026/08/13/DSCF1234.webp  ← 一致
```

URL から `sourceKey` を逆に導く道は採らない。**導けないからである**（Context 2）。配信キーは元写真の拡張子を `webp` に替えたもので、`.jpg` で入れても `.JPG` で入れても `.HEIC` で入れても同じ URL になる。逆向きは一意でない。

一意でないものを推測で埋める形——「`.jpg` だろう」と当てて目録を引く——は採らない。当たっているうちは動き、外れたときに**その写真だけ静かに機材が出ない**。出ないことが正常な状態（記録のない写真）と見分けがつかないので、壊れていることに気づけない。前向きに組み立てて突き合わせるなら、規約（`photoKeyOf`）が両側で同じ1つであり、ずれる余地がない。

`src/lib/photo.ts` に2つ足す。

- `photoPathOf(sourceKey)`: 元写真のキーから配信パスを作る。`photoKeyOf` は `${size}/${photoPathOf(sourceKey)}` になる（既存の関数はこれを使って書き直す。規約が2箇所に分かれない）。
- `photoPathFromUrl(base, url)`: 配信 URL から配信パスを取り出す。基点が一致しないもの・段数が足りないものは `undefined`。各段は `decodeURIComponent` で戻す（`photoUrlOf` が段ごとに符号化しているため）。

置き場所を `src/lib/photo.ts` にするのは、あのファイルが「投入から配信まで、規約はこの1つが持つ」と宣言しているためである。**逆向きの規約だけ別の場所に置くと、片方を変えたときにもう片方が残る。**

### 決定2: 目録は「本文に写真が現れた日」だけを、ビルド中に1度だけ引く

`src/lib/site-data.ts` に、配信パス → 機材の字面の Map を1つ作る。手順は3段。

1. 公開済みエントリの本文から、配信の基点で始まる URL をすべて拾う（`publishedEntries()` の結果を使い回す。取得は増えない）。
2. 配信パスから日付を取り出し、**重複を畳む**。
3. その日付だけを `listPhotosByDate()` で引き、機材を持つ記録を Map に入れる。

Promise を1つ memo 化して、1,164 ページの生成すべてが同じ Map を見る（`publishedEntries()` と同じ流儀）。

**全件の Scan は採らない。** `src/lib/store/queries.ts` が「走査は公開サイトの生成の経路には現れない」「写真が増えるほどサイトの生成が重くなる、という結び付きは生じない」と明記している。日付ごとの Query なら、増えるのは**写真のある日の数**であって写真の枚数ではない。1日に何枚貼っても往復は1回で、写真を増やすことがビルドを重くしない。この性質は、いまの書きぶり（1日に数枚〜数十枚）とそのまま噛み合う。

日付を**エントリの日付ではなく URL から**取るのは、本文が別の日の写真を指せるためである。いまは投入も移行も「日記の日付に置く」規約で動いているので実際には一致するが、一致を前提にすると、**一致しなくなった日に機材が静かに出なくなる**。URL から取れば前提が要らない。

往復の本数は写真のある日の数（数百）になるため、同時に走らせる本数に上限を置く。`mapWithConcurrency`（`src/migrate/parallel.ts`）がちょうどそれだが、**`src/migrate/` は移行が済めば消える前提のディレクトリである**（`legacy-photo.ts` の冒頭にそう書いてある）。公開サイトの生成が消える前提のものに依存してはいけないので、`src/lib/parallel.ts` へ移し、移行の側はそこを読むようにする。関数の中身は変えない。

### 決定3: ビルドの入力は2つになるが、下書きの通り道は増えない

`site-data.ts` の冒頭は「このモジュールが、公開サイトのビルドにおける唯一のデータ入力である」と宣言している。入力が2つになるので、この宣言を書き換える。**書き換えるのは宣言であって、保証ではない。**

保証は次の形で保たれる。

- **エントリの取得は今までどおり `listAllPublished()` の1本だけ**。下書きはそこに最初から流れてこない（sparse index）。これは1文字も変えない。
- **写真の目録に公開・下書きの区別は無い**。写真は日記に属するのであって、公開状態を持たない。
- **引く日付は、公開済みエントリの本文に現れた日付だけ**。下書きの本文はこの経路に入らないので、下書きにしか貼られていない写真の日付が引かれることもない。仮に引いたとしても、Map は本文の URL で引くものなので、公開ページに現れない写真の記録は出力のどこにも現れない。

つまり**下書きが漏れうる経路は1本のままである**。増えたのは「公開済みの本文に既に書かれている写真について、その写真の機材を読む」という経路で、公開されていないものへは届かない。

### 決定4: 権限は目録のパーティションに限って足す

公開手続きの role に、ベーステーブルへの `dynamodb:Query` を足す。ただし `dynamodb:LeadingKeys` の条件を付け、**パーティションキーが `PHOTO#` で始まるものに限る**。

```hcl
statement {
  sid     = "QueryPhotoCatalog"
  effect  = "Allow"
  actions = ["dynamodb:Query"]

  resources = [var.table_arn]

  condition {
    test     = "ForAllValues:StringLike"
    variable = "dynamodb:LeadingKeys"
    values   = ["PHOTO#*"]
  }
}
```

条件なしでベーステーブルへの Query を与える形は採らない。いまそこに書いてあるのは「サイトの生成が読むのは GSI1 だけなので、Query は索引の ARN に限る。ベーステーブルへの Query は与えない」であり、**読む必要のできたものだけを足して、読む必要のないものは足さない**のがこの一文の意図である。条件を付ければ、`ENTRY#<年>` のパーティションは権限の側で引けないままになる——下書きを含むエントリの取得経路は、コードだけでなく IAM でも閉じている。

この条件は DynamoDB の fine-grained access control そのもので、Query は `pk` を必ず指定するため素直に効く。

**この変更は terraform apply を伴い、コードより先に当てる必要がある。** 順番を逆にすると、手元では動くのに公開手続きのボタンだけが失敗する（Context 3）。Migration Plan に順番として書く。

### 決定5: 機材の字面を決める規則は1つの関数に閉じ、ビルド時に1度だけ適用する

`src/lib/equipment.ts` を作り、目録の `PhotoExif` から出す1行を組み立てる関数を1つ置く。

| 記録 | 出るもの |
| --- | --- |
| `model` のみ | `X-T5` |
| `model` + `lensModel`（レンズが機種名を含まない） | `X-T5, XF33mmF1.4 R LM WR` |
| `model` + `lensModel`（レンズが機種名を含む） | `iPhone 15 Pro` |
| `lensModel` のみ | `XF33mmF1.4 R LM WR` |
| どちらも無い | なし（`undefined`） |

`make` は使わない。`Model` は機種を一意に指しており、書き手にとって `X-T5` と `ILCE-7M4` はどちらも自分の機材の名前である。`make` を前に付ける形（`FUJIFILM X-T5` / `SONY ILCE-7M4`）も考えたが、**EXIF の `Make` はメーカーの書いた字面がそのまま入っており、大文字の揺れを画面に持ち込むことになる**。`Canon EOS R6` のように `Model` が既にメーカー名を含むものもあり、重複を避ける判定をもう1つ増やすことになる。出さなければ、どちらも起きない。

レンズを出すかどうかは、**`lensModel` が `model` を含むかどうか**だけで決める（大文字小文字は無視し、前後の空白は落として比べる）。スマートフォンの `LensModel` は `iPhone 15 Pro back triple camera 6.86mm f/1.78` のように機種名で始まるので、この1つの判定で落ちる。メーカーの一覧（`Apple` / `Google` / …）を持つ形は採らない。**一覧に載っていない端末が来た日に、レンズ名として長い文字列がそのまま出る**——しかも気づくのは、その写真を拡大して見たときである。値どうしの関係で決めるなら、知らない機材でも同じ規則が働く。

判定はビルド時に1度だけ行い、**出来上がった1行を配る**。ブラウザ側に規則を持たせない。拡大表示は説明（`caption`）も文字列として受け取っているので、扱いが揃う。

### 決定6: 機材は本文の `img` に `data-` 属性として載せる

整形（`renderMarkdown`）に配信パス → 機材の Map を渡し、hast の `img` に `data-equipment` を付ける。既存の `imageFigurePlugin` と同じ場所・同じやり方である。**本文（DynamoDB の値）は書き換えない。** 見せ方は表示側で解く、という `markdown.ts` の既定の流儀に従う。

別案として、ページに対応表（`<script type="application/json">`）を1つ置き、ブラウザ側で URL から引く形も考えた。採らない。拡大は**本文の `img` から始まり、前後の写真も本文の `img` として並んでいる**（`photo-zoom.ts` の `wrap()`）。写真のところに書いてあれば、対応づけの表も、引き当てに失敗したときの分岐も要らない。`photo-zoom.ts` は `caption` を `figure` から読んでいるのと同じ手つきで、`img.dataset` から読める。

引数は任意にする。編集アプリケーションのプレビュー（`renderMarkdown` の呼び出し元のうち2つ）は渡さず、いまと同じ出力になる。

記録のない写真には属性を付けない。空の属性を付けると、拡大表示の側で「空文字か未設定か」を見分ける必要が生まれる。**不在は不在として表す**（`location` を持たないエントリに `location` 属性を書かないのと同じ）。

### 決定7: 拡大表示のセルに3段目を足し、色と書体で説明と分ける

`PhotoZoom.astro` の `figure` に、`figcaption` の下へ1行足す。`photo-zoom.ts` の `Cell` に持ち手を1つ増やし、`fill()` が説明と同じように入れ替える。閉じるときに説明を消している（`caption.style.opacity = '0'`）のと同じ扱いをここにも与える——写真が本文へ帰るとき、機材の行だけが残ってはいけない。

体裁は `visual-identity` に従い、**新しい色も新しい大きさも増やさない**。

- **書体**: `--font-ui`（欧文のラベル）。機材名は `X-T5` や `XF33mmF1.4 R LM WR` のような欧文であり、月・曜日の略記や前後の導線の日付と同じ役目の字である。説明は著者の文なので本文系の字のままにする。**書体の違いが、著者の言葉と機械の記録の違いに重なる。**
- **色**: 白の不透明度を説明より下げる（説明 0.72 に対して 0.48）。暗幕の上での contrast は 4.89 で、文字に求められる 4.5 を上回る。
- **大きさ**: 前後の導線の日付と同じ 0.74rem・letter-spacing 0.08em。拡大表示の中に新しい寸法を作らない。

`:empty { display: none }` は説明と同じ。記録のない写真では要素が消え、写真と説明の間隔も変わらない。

`aria-label` には入れない。いま `dialog` の `aria-label` は説明（無ければ「写真」）で、**それが何の写真かを言う言葉**である。機材はそこに足す種類の情報ではない。行そのものは読み上げの対象として残るので、読み上げで辿れなくなるわけではない。

## Risks / Trade-offs

- **レンズ名に機種名が含まれる一眼カメラがあれば、レンズが出ない** → 実害はレンズが出ないことだけで、誤った機材名が出ることはない。固定レンズの機種（`X100V` など）では、そもそもレンズ名が機種の言い直しなので**省くのが正しい**。交換レンズの名称に機種名が入る例は確認できていない。出なかったら、そのとき目録の値を見て考える。
- **往復が数百本に増える** → 同時に走らせる本数に上限を置く（決定2）。増えるのは写真のある日の数で、枚数では増えない。実測して、ビルド時間への影響をタスクの中で記録する。
- **terraform を先に当てないと公開手続きだけが失敗する** → Migration Plan の順番として明示する。手元のビルドは admin の profile で動くため、**この失敗は手元では再現しない**。staging のボタンを押すところまでを確認の手順に入れる。
- **配信物に機材名が現れる** → spec に「配信物に現れるのは機材の名称に限る」を置いた。位置情報は目録が最初から持っておらず（`photo-catalog`「位置情報は記録されない」）、露出と撮影日時は Map に入れない。**出さないものは、ブラウザに届く形にもしない。**
- **`photoKeyOf` を `photoPathOf` を使う形に書き直す** → 出力は変わらない（同じ文字列を作る）。`lambda/photo-resize` 側の同名の規約（`deliveryKeyOf`）には手を入れない。あちらは書く側で、パッケージが独立している。**片方だけ関数の形が変わるが、作る文字列は変わらない。**
- **ビルドが `PHOTO_URL` を要求するようになる** → 手元の `config/<環境>.env` にも CodeBuild のプロジェクト定義にも既にある（`terraform/modules/publish` が渡している）。欠けたときに何を直せばよいかが分かるよう、`scripts/build.sh` の `require_env_vars` に足す。

## Migration Plan

1. **terraform を staging に当てる**（決定4）。コードより先。この時点では誰も使わない権限が1つ増えるだけで、既存の公開手続きは何も変わらない。
2. コードを反映し、手元で staging のデータからビルドして、生成物の `data-equipment` の数と中身を確かめる。
3. staging の公開手続きを**ボタンから**起動する。権限が足りていることは、ここでしか確かめられない（手元は admin の profile で動く）。
4. staging のサイトで、機材のある写真・ない写真・スマートフォンの写真・説明と併せて出る写真を目視する。
5. production に terraform → コード → 公開手続きの順で同じことを行う。

**ロールバック**: コードを戻せば表示は消える。目録も日記も書き換えていないので、戻すものは他に無い。IAM の statement は残しても害が無いが、コードを戻したまま置くなら外す（使わない権限を「念のため」で置かない、という `terraform/modules/publish` の書きぶりに従う）。

## Open Questions

- 移行した写真のうち、実際に機材が記録されているものの割合。`migrate-legacy-photos` の report.md は「撮影情報が失われた写真は1枚も無い」と書いているが、**元写真そのものが EXIF を持っていたか**は別の話である（旧サイトに上げる前に落とされていた古いものがありうる）。ビルドして数えれば分かるので、タスクの中で数える。表示の可否には影響しない——持たない写真には出さないだけである。
- 機材の行を、いつか本文の写真の下（拡大しない状態）にも出すかどうか。今回は出さないと決めたが、`data-` 属性が本文の `img` に載るので、出すと決めたときに新しい経路は要らない。
