## Context

動機は proposal.md の Why を、満たすべき振る舞いは specs/diary-site-pages/spec.md を参照。ここでは実装の形を決めるうえで効いた、現状の作りと写真の実態を述べる。

**このサイトには閲覧のための JavaScript が1行もない。** すべてのページが静的な HTML と CSS だけで出来ており、`<script>` を持つコンポーネントもページも存在しない。今回がその最初の1つになる。したがって「JS を足すかどうか」ではなく「JS が動かないときに何が残るか」が設計の中心にある。

本文中の写真は2つの形で現れる。

- `![説明](URL)` から作られる `figure > img (+ figcaption)`。`figcaption` は `src/lib/markdown.ts` の hast plugin が `alt` から作っている。
- 旧サイトから引き継いだ `table > tr > td > img`。横並びの配置のために本文に直接書かれた HTML で、表ではない。並びの下に `td[colspan]` が置かれ、並び全体に対する説明になっている（実データには「4枚目は帰り道」のような、明らかに1枚には帰属しない文がある）。production の1092件のうち86件がこの `table` を含む。

写真の枚数は日記によってまちまちで、1枚のものから20枚近いものまである。1日の写真はおおむね時刻の順に本文へ並ぶ。

写真は外部ホストにある。本文に出ているのは `https://photos.old.apkas.net/medium/…`（1920×1280、約140KB）で、同じ相対パスの `/large/` に 3840×2560（約500KB）がある。`/original/` は 403 を返す。本文の幅は 42rem（672px）なので、本文に出ている時点で medium は既に表示幅の約3倍を持っている。

## Goals / Non-Goals

**Goals:**

- 拡大の見た目と操作が、本文の DOM 構造（`table` のセルの中か `figure` の中か）に左右されないこと。
- 拡大したまま、その日の写真をひととおり見て回れること。指の動きに表示が追従し、操作の途中で引き返せること。
- 本文の HTML と、生成される1000ページ超の配信物を膨らませないこと。
- JS が動かない環境で、ページが現在とまったく同じ姿になること。「壊れた見た目で残る」ではなく「仕掛けが無かったことになる」。
- 開く動作が、追加の通信を待たずに始まること。写真を移る動作も同じであること。

**Non-Goals:**

- 本文の Markdown や生成される HTML を、拡大のために書き換えること。
- 写真ホストの URL 規約を確かめにいくこと（生成時に `/large/` の存在を問い合わせるなど）。
- 日記をまたいで写真を辿ること。

## Decisions

### 1. 拡大表示は `<dialog>` の top layer に置く

`dialog.showModal()` で開く。z-index を積み上げる自前の overlay は使わない。

本文の写真は `td` や `figure` の中にある。その場で拡大しようとすると、祖先の `overflow`・stacking context・`table-layout: fixed` の列幅が、拡大の見た目に影響しうる。top layer はページの stacking から完全に外れた層なので、本文の構造が何であっても拡大表示は同じになる。

あわせて、Esc による閉鎖・背後のページの inert 化・フォーカスの閉じ込め・暗幕（`::backdrop`）がブラウザ側の担保になる。自前の overlay ではこれらを全部自分で書くことになり、間違えられる箇所がその数だけ増える。

**却下した案**: `position: fixed` の div を最前面に置く。同じ絵は作れるが、上に挙げたものを1つずつ実装することになる。

### 2. dialog の中は、写真1枚ではなく3枚（前・現在・次）を横に並べたトラックにする

`dialog` はページに1つだけ、空の状態であらかじめ置く。中には画面幅ぶんのセルを3つ横に並べ、それぞれに `img` を持たせる。中央のセルが今見ている写真で、両隣に並びの前後の写真が入る。写真を移ると、トラックを1セルぶん動かしてから、3つのセルの中身を詰め直す。

隣の写真を実体として持つのは、横のドラッグに追従して**隣が実際に見えている**必要があるためである。離した瞬間に切り替えるだけなら1枚で済むが、それでは指の動きに対して何が起きるのかが操作中に分からない。

隣の写真の medium は、同じページの本文に既に出ているので読み込みもデコードも済んでいる。3枚に増やしても通信は増えない。端では隣のセルを空にする（決定9）。

本文の `img` そのものに `transform` をかけて拡大する案は取らない。要素が `td` の中にいるまま画面全体へ広がることになり、決定1で外したはずの本文の構造に、拡大の見た目が再び縛られる。写真を移る動きも作れない。

開いているあいだ、**今見ている写真**に対応する本文側の `img` を `visibility: hidden` にして二重に見えないようにする。移ったら、前の写真の `visibility` を戻し、新しい写真のほうを隠す。

### 3. 開閉のアニメーションは FLIP

押された `img` の `getBoundingClientRect()` を測り、中央のセルの `img` をその矩形と同じ位置・大きさに置いてから、目標の矩形へ `transform` で遷移させる。閉じるときは逆向きに同じことをする。

`width` / `height` / `top` / `left` を直接遷移させると毎フレーム、レイアウトが計算し直される。`transform` と `opacity` だけならレイアウトは起こらない。

目標の矩形は「viewport から余白を引いた領域に、画像の縦横比のまま収まる最大」とする。**画像の実寸を上限にはしない。** 写真を大きく見るための機能で、余白を残して小さく出すのは目的に反する。medium しか読めない写真を高解像度ディスプレイで開くと等倍を超えて引き伸ばされることがあるが、多くの場合は決定5の差し替えで解消する。

閉じるときの矩形は、閉じる時点で測り直す。上下の動きで閉じたときも、他の写真へ移ったあとも、開いたときの矩形はもう正しくない。

`prefers-reduced-motion` のときは CSS 側で `transition` を無効にする。JS の手順は変えない。始点と終点の指定は同じまま、そのあいだが無くなるだけになる。写真を移るときのトラックの移動も同様に、途中が無くなって切り替わりだけが残る。

### 4. 仕掛けはクライアント側で組み立て、生成 HTML には出さない

スクリプトが動いたときに初めて、本文の各 `img` を `<button type="button">` で包み、`cursor: zoom-in` などの手がかりを付ける。生成された HTML には `button` も、拡大用の class も出ない。

`src/lib/markdown.ts` の hast plugin で生成時に `button` を巻く案もあった。取らない理由は2つ。

- JS が動かない環境に、押しても何も起きない `button` が残る。仕掛けが無かったことにならない。
- 押せる手がかりを見せるかどうかの判断が、スクリプトが動いたかどうかと切り離せない。同じ判断が2箇所に散る。

`button` で包むのは、フォーカス・Enter/Space・フォーカスリングをブラウザから受け取るため。`tabindex` と `role="button"` を `img` に振る案は、キー操作を自分で書くことになる。

対象は日別ページ本文（`.body`）の `img` のうち、`a` の中にないものすべて。リンクの中の画像は、拡大よりリンク先へ移る意図が先にある（現状の実データには存在しないが、規則として決めておく）。

`showModal` を持たないブラウザでは、この組み立て自体を行わない。何も包まれず、ページは今のままになる。

### 5. large への差し替えは、開き切ったあとに、今見ている1枚だけ

`src` の `/medium/` を `/large/` に置き換えた URL を `new Image()` で読み、成功したら中央のセルの `img` の `src` を差し替える。写真を移ったら、移った先で改めて同じことをする。**隣のセルは medium のまま**にしておく。まだ見られていない写真に 500KB を先に払う理由がない。

差し替えを**開くアニメーションの完了後**に始めるのは、遷移の最中に大きな画像のデコードが挟まるとコマが落ちるため。矩形は既に確定しているので、差し替えても位置も大きさも動かない。見えるのは、同じ場所の絵が静かに精細になることだけになる。

失敗（`onerror`、`/medium/` を含まない `src`、読み終わる前に閉じられた場合、読み終わる前に別の写真へ移った場合）は、いずれも「何もしない」で済ませる。medium の拡大表示がそのまま残る。読み込み中であることを示す表示も出さない。仮に出すと、待つ必要のないものを待たされているように見える。

**却下した案**: 生成時に `/large/` の存在を確かめて `srcset` を持たせる。1092件・2365枚の写真ぶんの HEAD 要求がビルドに乗り、外部ホストの応答がビルドの成否を左右するようになる。得られるのは「無い写真では差し替えを試みない」ことだけで、試みて失敗しても表示は変わらない。

### 6. ジェスチャは Pointer Events で受け、最初の動きで軸を決める

`pointerdown` / `pointermove` / `pointerup` で扱う。タッチもマウスのドラッグも同じ経路で受けられる。

動き始めの十数 px で、縦のジェスチャか横のジェスチャかを決める（軸ロック）。決まったあとは、もう一方の向きの成分を無視する。斜めの動きに対して閉じるのと移るのが同時に起きたり、途中で入れ替わったりしないようにするためである。指の動きは完全にはまっすぐにならないので、これを決めずに両方へ追従させると、どちらの操作をしているのかが表示から読めなくなる。

確定の閾値は距離と速度の両方で見る。ゆっくり大きく動かしたときと、素早く弾いたときのどちらでも確定する。

- 縦（閉じる）: 画面の高さに対する割合で見る。誤って閉じないことを優先し、横より深めに取る。
- 横（移る）: 画面の幅に対する割合で見る。写真を次々に見ていく操作なので、縦より浅くてよい。

閾値に届かないまま指を離したら、動かした量を戻して元の状態に帰る。追従している最中に何が起きるかが見えているので、途中で引き返せる。

マウスのホイールは追従させず、累積した量が閾値を超えたところで閉じる。ホイールは1操作あたりの量が端末で大きく違い、指の動きのように連続した量として扱えないためである。向きは上下どちらでもよい。

`touch-action: none` を拡大表示に当てて、ブラウザ側のスクロール・pull-to-refresh・横スワイプによる履歴移動に操作を取られないようにする。

### 7. 閉じる操作はクリック・Esc・上下の動きの3つ

- クリック（タップ）: 拡大された写真の上でも、その外側でも閉じる。開くのがクリックなら閉じるのもクリックであってほしい。写真の上だけを除外すると、大きく写った写真の上を押した人が閉じられなくなる。ドラッグと区別するため、軸ロックが起きなかった（ほとんど動かなかった）ときだけクリックとして扱う。
- Esc: `dialog` が持っている挙動をそのまま使う（`cancel` イベントを捉えて、閉じるアニメーションを挟む）。
- 上下の動き: 上向きも下向きも閉じる。閾値は決定6のとおり深めに取る。

上下のどちらでも閉じるのは、拡大中にページを読み進めようとする動きが上下どちらにも起こりうるためである。片側だけを閉じる操作にすると、もう一方は「何も起きない向き」になり、それを覚えている必要が出る。誤爆は向きを絞ることではなく閾値で防ぐ。

### 8. 写真の並びは本文の出現順。左向きが並びの手前、右向きが先

スクリプトが `button` を巻くときに作った配列が、そのまま並びになる。`figure` の中の1枚も `table` の中の1枚も区別しない。読み手にとっては同じ「その日の写真」であり、本文でどう配置されているかは書き手の都合である。

向きは、既にサイトが持っている規約の別の適用として置く。日付の導線では「`←` が新しい日付」だが、これは一覧が新しい順に並んでいることの裏返しで、元をたどれば **`←` は並びの手前、`→` は並びの先**という1つの規則になっている。写真の並びは本文の上から下なので、`←` が上にある写真、`→` が下にある写真になる。

指の向きは、内容が指についてくる向きにする。左へ動かせば右から次の写真が入ってくる。これは `→` キーと同じ移動になる。

キーボードの左右キーにも同じ移動を割り当てる。ドラッグでしか移れないと、キーボードで開いた読み手には並びが存在しないのと同じになる。

### 9. 並びの端では折り返さない

最初の写真で手前へ、最後の写真で先へ動かそうとしたときは、移動量に抵抗をかけて（動かした量の一部だけ動かす）指を離したら元に戻す。隣のセルは空のままなので、暗幕がそのまま見える。

日付の導線で「隣が無い側には導線を置かず、無いことを示す文言も出さない」としているのと同じ扱いである。端であることは、動かしたときの手応えの違いとして分かる。何枚目を見ているかを数字で出すことも、今回はしない。

**却下した案**: 最後から最初へ循環させる。何周でも見られるが、並びの先頭と末尾が消えるため、ひととおり見終わったことが分からなくなる。

### 10. 移動したあとに閉じるときは、その写真を画面に入れてから戻す

閉じるとき、今見ている写真に対応する本文の `img` が画面の外にあれば、先にその位置までページを送り（`scrollIntoView`）、そのうえで矩形を測り直して FLIP を始める。

拡大したまま10枚先の写真へ移ることがあり、そのときの本文の位置は開いた場所のままである。測り直しをしないと、写真は画面外へ飛んでいくように見える。読み手にとっては最後に見ていた写真が今いる場所なので、そこへ本文の側を合わせる。

写真を移らずに閉じたときは元の位置が画面内にあるため、ページは動かない（spec の「閉じたあとの読む位置」）。

### 11. 拡大表示に添えるのは `figcaption` だけ

`figure` から開いた写真は、その `figcaption` の文を拡大表示にも出す。`table` の並びから開いた写真には、`td[colspan]` の文を出さない。

並びの説明は並び全体に対する文であって、その1枚の説明ではない。「4枚目は帰り道」のような文が実際にあり、2枚目を拡大した画面にこれを添えると、その写真の説明として読まれてしまう。書かれた文を失わないことは大事だが、書かれていない意味を足すのはそれ以上に避けたい。並びの説明は背後の本文に残っており、閉じれば元の位置で読める。

写真を移ると説明も一緒に入れ替わる。説明を持たない写真では、その場所ごと消える。

## Risks / Trade-offs

- **`dialog` の top layer に依存する** → `showModal` の有無で分岐し、無い環境では仕掛けを組み立てない。ページは今と同じになる。この分岐は決定4の組み立てと同じ場所にあり、判断は1箇所で済む。
- **画面端からの横スワイプがブラウザの「戻る」に取られる**（iOS Safari など） → `touch-action: none` で拡大表示の内側の操作は自前で持つが、画面端から始まるジェスチャは OS 側が先に取ることがある。端から始まった横の動きで前の写真に移れないことは起こりうる。キーボードと、端以外からのドラッグでは移れる。
- **上下どちらでも閉じるため、意図しない閉鎖が起こりうる** → 閾値を深めに取り（決定6）、追従の途中で引き返せるようにする。閉じても失われるものは無く、元の写真の位置に戻るだけである。
- **large の追加通信（1枚あたり約500KB）** → 見た写真の分だけ発生する。隣の写真を先読みしないので、移らなければ払わない。同じ写真を2度開いてもブラウザのキャッシュに載る。
- **large が無い写真では等倍を超えて引き伸ばされる** → 高解像度ディスプレイでやや甘く見える。表示自体は保たれる（spec の「高精細な画像が読めない場合」）。medium は 1920px あり、本文で見えていたものより常に大きい。
- **本文の `img` を `button` で包むことでレイアウトが動きうる** → `table-layout: fixed` の列幅と `figure` の間隔は、包んだあとに実際の生成物で確かめる。`display: block` / `padding: 0` / `border: 0` を当てて既定の `button` の体裁を消す。
- **写真の多い日記では並びが20枚近くになる** → トラックが持つのは常に3枚で、枚数に比例して増えるものはない。本文側の `img` は元から全部読み込まれている。
- **全ページに同じスクリプトが載る** → Astro が1つのファイルに bundle し、各ページはそれを参照する。実体は1つで、CloudFront にも1つとして載る。

## Migration Plan

表示のみの変更で、DynamoDB のデータにも書き込み経路にも触れない。ビルドし直せば新しい配信物になる。staging に出して、PC と実機のスマートフォンの両方で確かめてから production に進む。

戻すときは、日別ページからコンポーネントの読み込みを外して再ビルドすれば、スクリプトを含まない今の配信物に戻る。
