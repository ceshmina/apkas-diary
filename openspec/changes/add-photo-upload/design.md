## Context

動機は proposal.md の Why を参照。ここでは方式の選定に効く現状だけを挙げる。

- 写真の投入は `npm run photo -- <環境> --file ... (--date ... | --key ...)` の1本だけで、`src/cli/put-photo.ts` がアップロード用バケットへ `PutObject` する。派生画像を作るのは S3 の `ObjectCreated:*` で起動する Lambda であり、**投入と生成は同期しない**。
- 派生画像のキーと URL の規約は `src/lib/photo.ts`（`photoKeyOf` / `photoUrlOf`）が持っており、編集アプリケーションは同じリポジトリの `src/lib` を相対 import で共有している。
- CLI は生成の完了を、**配信先バケットへの `HeadObject`** で見ている。`src/lib/env.ts` にその理由が書かれている——配信 URL を叩いて調べると、まだ無いあいだの 403 が CDN に載り、**自分の問い合わせが原因でしばらく読めなくなる**。
- 編集アプリケーションは Lambda + API Gateway HTTP API。**応答は 30 秒が上限**で、統合タイムアウトとして基盤側が担保している。
- 編集アプリケーションの画面は**すべてサーバ描画のフォーム**である。client script は1つも無い。進行中の状態を追う手段としては `/publish` が `<meta http-equiv="refresh">` を使っている（`Base.astro` の `refreshSeconds`）。
- 編集アプリケーションの実行ロールには **S3 と CloudFront の権限がいっさい無い**。「画面に置かない」ではなく「権限を与えない」で担保する形が、削除操作の不在（`entry-editing`）と配信物への非到達（`editor-hosting`）の芯になっている。
- アップロード用バケットは versioning が有効で、パブリックアクセスは全面禁止、CORS の設定は無い。
- セッションは `__Host-diary-session`、`SameSite=Lax` の署名付き Cookie ひとつ。
- 変換 Lambda は MemorySize 2048 / Timeout 60。

## Goals / Non-Goals

**Goals:**

- 投入の入口が2つになっても、**写真の置き場所と URL を決める規約は1つに保つ**。CLI とブラウザで別々の規則が生まれない。
- 編集アプリケーションの権限の増分を、**置くこと**と**出来たかを見ること**だけに閉じる。配信されるものを直接書き換えられる主体を増やさない。
- 部品を増やさない。写真の側に足すのは、ブラウザから送るための CORS 設定だけとする。バケットも CloudFront も変換 Lambda も、作りは変えない。
- 書きかけの本文が、写真を入れる操作で失われない。

**Non-Goals:**

- 1枚の送信の進み具合（何 % 送ったか）を見せること。**何枚のうち何枚が済んだかは出す**が、1枚の中の進捗は追わない。
- 元写真の一覧・削除・読み出しを編集アプリケーションから行えるようにすること。
- 変換の設定（サイズ・形式・品質）を投入のたびに選べるようにすること。既存の4つの規約を動かさない。

## Decisions

### 決定1: 元写真はブラウザからアップロード先へ直接送る

検討した案:

| 案 | 内容 | 判断 |
| --- | --- | --- |
| **A. presigned な資格でブラウザ → S3 直接** | 編集アプリケーションは資格を発行するだけ | **採用** |
| B. 編集アプリケーション経由 | ブラウザ → Lambda → S3 | 却下 |
| C. B に multipart upload を足す | 分割して送り、Lambda が結合する | 却下 |

B を却下する決め手は**大きさの上限**である。API Gateway の HTTP API はペイロードを 10MB までしか通さず、Lambda 側の同期呼び出しの上限は 6MB で、そこへ届く時点で base64 になるため実質の上限は 4〜5MB になる。スマートフォンの写真ですらここに触れることがあり、カメラの JPEG は確実に超える。**「文章を書くための入口が受け取れる大きさ」に写真を縛る**ことになり、`photo-ingest` に足す要件と正面から衝突する。

加えて B は、写真の内容をまるごと Lambda のメモリに載せる。編集アプリケーションは 1024MB で動いており、数十 MB の受け渡しのために割り当てを上げるのは、使っていない時間の費用を持たない構成に対して割に合わない。

C は上限を回避できるが、分割・結合・中断時の後始末を自分で持つことになる。**S3 が既に持っている機能を、Lambda を挟んだぶんだけ作り直す**形であり、部品を増やさないという方針に反する。

### 決定2: presigned POST を画面上のスクリプトから1枚ずつ送る

ブラウザから S3 へ直接送る方法は2つある。

| 案 | 内容 | 判断 |
| --- | --- | --- |
| **A. presigned POST** | 署名済みのフィールドと1枚のファイルを `multipart/form-data` で POST する | **採用** |
| B. presigned URL（`PUT`） | 署名した URL に本文をそのまま `PUT` する | 却下 |

A を採るのは、**POST policy が条件を持てる**ためである。`content-length-range` で大きさの上限を、`starts-with $key` で置ける場所を、**署名の中に**閉じ込められる。`PUT` の署名にはオブジェクトの大きさを縛る手段がない（対応する IAM の条件キーが存在しない）。決定3 と決定6 はこの性質に依っている。

**送るのは画面上のスクリプトである。** 素の HTML フォームから S3 へ POST する形（`success_action_redirect` で戻す）も成立し、当初はそちらを採っていたが、**複数枚をまとめて投入するなら成立しない**。S3 の POST Object は1回の要求につき1枚しか受け取らないため、N 枚は N 回の要求になる。フォームの送信は1回でページを離れてしまうので、2枚目以降を送る機会がない。

したがって:

- **1枚ぶんの署名を N 回使い回す。** policy の条件は日付の接頭辞と大きさだけで、ファイル名を含まない（決定3）。同じ資格で N 枚を送れるので、署名は1回でよい。
- 各要求には `success_action_status: 201` を付ける。S3 は 201 と、`Key` を含む XML を返す。**結果のキーは S3 が返したものを使う**ので、置換の規則がスクリプト側に写らない。
- すべて送り終えたら、キーを並べた結果の画面へ遷移する。

**代償として CORS の設定が要る。** スクリプトからの要求なので、応答を読むにはアップロード用バケットが編集アプリケーションのオリジンを許す必要がある。当初これを避けたのは「公開されない元写真の置き場所に穴を開けない」ためだったが、**CORS は権限ではない**——ブラウザに応答を読ませてよいかを宣言するだけで、署名のない要求は CORS があってもなくても拒否される。許すオリジンを環境ごとの編集アプリケーションに限れば、実際に増える面はない。

**スクリプトが要ることは、この画面については受け入れる。** 編集アプリケーションの他のページはすべてサーバ描画のフォームのままである。ここだけが動くのは、(1) 複数枚を送るには N 回の要求が要る、(2) 送っている最中の進み具合を見せたい、(3) 生成された写真を確かめるために表示したい（決定10）、の3つが揃っているためで、いずれもフォームの往復では満たせない。スクリプトが動かない環境では投入できないので、その旨を画面に出す。

`success_action_redirect` を使わなくなったため、**S3 からトップレベルのナビゲーションで戻ってくる経路は無くなった**。セッション Cookie の `SameSite=Lax` に依存するのは Google の認証からの戻り（`/auth/callback`）だけである。

### 決定3: キーは `YYYY/MM/DD/${filename}`。日付は署名が決め、ファイル名はブラウザが埋める

署名を作る時点では、利用者がどのファイルを選ぶかまだ分からない。フォームを描いてから選ぶからである。そこで S3 の POST が持つ `${filename}` 変数を使う。

- `key` フィールドを `2026/08/11/${filename}` として置く。S3 が受け取ったファイル名で置き換える。
- policy には `["starts-with", "$key", "2026/08/11/"]` を入れる。**置ける場所は署名された日付の下に閉じ込められる。**

これで、CLI の `--date` が作るキー（`yearOf/monthOf/dayOf` + `basename`）と同じものになる。`--key` に相当する「キーを直接指定する」経路は**作らない**。日付という軸をこのシステム全体が共有しており、そこから外れた場所に置ける入口を、いちばん手軽な入口の側に持たせない。

却下した案: **ファイルを選ばせたあと、スクリプトが1枚ごとにキーを確定して署名を取りに行く。** `${filename}` に頼らずに済むが、N 枚に N 回の署名が要り、キーを組み立てる規則がスクリプト側にも写る。`${filename}` なら**署名は1回で N 枚に使え**、キーを決めるのは最後まで S3 と `src/lib/photo.ts` だけになる。

### 決定4: 生成の完了は配信先バケットの `HeadObject` で見る。CDN は叩かない

CLI が既に同じことをしており（`put-photo.ts` の `probeUpdatedAt`）、理由も `src/lib/env.ts` に書かれている。**配信 URL を叩いて調べると、まだ無いあいだの 403 が CDN に載り、自分の問い合わせが原因でしばらく読めないままになる。** 待つための操作が、待っている当のものを遅らせる。

判定は「存在するか」ではなく「**署名した時刻より後に書かれたか**」で行う。

- 差し替えのとき、前回の派生画像が残っているので、存在だけを見ると投入した直後に「できました」と言ってしまう。
- CLI は投入の**前**に控えた `LastModified` と比べているが、ブラウザからの投入では、控えるべき時点＝署名の時点である。**署名は元写真が置かれるより必ず前**なので、「署名時刻より新しい派生画像がある」なら、それはこの投入から作られたものである。
- 署名時刻は `success_action_redirect` の URL に載せて往復させる。改竄されても、狂うのは自分の写真の完了表示だけで、他に影響しない。

副産物として、**署名時刻より古い派生画像が存在していた場合、そのキーは以前にも使われていた**と分かる。同じ日に同じファイル名の写真を入れてしまったとき、画面で「差し替えた」と言える。

待ちはサーバ側で行わない（応答は 30 秒が上限）。`/publish` と同じく `<meta http-equiv="refresh">` で数秒おきに読み直し、完了したら更新をやめる。

**待ちには上限を置く（90 秒）。** 読めない形式を投入すると派生画像は永遠に現れず、待つ画面がそのまま止まる。このリポジトリでいちばん起きやすいのは **HEIC** で、変換に使う sharp が HEVC をデコードできないため、**投入は成功するのに生成だけが起きない**（README「HEIC は投入できない」）。上限に達したら更新をやめ、「遅れているのか読めなかったのかはここからは分からない」と、HEIC の可能性とログの在り処を添えて示す。失敗としては扱わない——待ちきれなかったことをエラーと呼ぶ理由がないのは CLI と同じである。

上限を CLI の 30 秒より長くしてあるのは、こちらが**投入の前**（署名の時点）から数え始めるためで、大きな写真を送っているあいだもこの時間が進む。

同じ理由から、投入の画面にも HEIC が変換できないことを先に書いておく。**待つ画面で気づくより、選ぶ前に言うほうが手数が少ない。**

権限は配信先バケットへの `s3:GetObject` と `s3:ListBucket` の2つ。**`ListBucket` が要るのは、それを持たない主体には「無い」が 404 ではなく 403 で返るためである。** 変換 Lambda が同じ理由で同じ2つを持っている（`terraform/modules/photos/main.tf` の `ProbeDerivatives`）。無いと「まだ無い」と「読めない」を区別できず、初回の投入が権限の失敗として現れる。**書き込みは与えない。**

### 決定5: 投入の画面は編集画面から独立させ、往復で本文を失わない形にする

投入は複数枚を順に送り、終わったら結果の画面へ遷移する。**そのページに書きかけの本文があると、遷移と同時に失われる。** したがって投入の口を編集画面の中に置くことはできない。

- `/photos/new?date=<日付>&return=<戻り先>`: 日付とファイルを選ぶ画面。ここが署名を発行する。
- `/photos/uploaded?...`: S3 からの戻り先。URL・貼れる記述・生成の完了を出す。

編集画面には**「保存して写真を追加」**を置く。押すと通常の保存（既存の `putEntry`）を行ってから `/photos/new` へ送る。保存を伴うことは**ボタンの文言そのもの**で分かる（`entry-editing` に足した要件）。一覧からも日付を選んで単独で使える。

却下した案:

- **編集画面に投入の口を埋める。** 上のとおり本文が消える。投入を非同期にして同じページに留まる形も採れるが、そうすると編集画面が投入の進み・生成の待ち・確認の表示まで抱えることになる。**書く画面と入れる画面を分けたほうが、どちらも小さく保てる。**
- **別タブで開く（`target="_blank"`）。** 保存を伴わない利点があるが、戻ってきたことを編集画面が知らないので、貼る作業は結局手作業になる。加えて端末によってタブの扱いが変わる。**保存してから移る**ほうが、この道具の性質（下書きを寝かせながら書く）に合っている。

`return` は画面に出す「戻る」リンクにのみ使い、**自動では飛ばさない**。値は `/entries/` で始まることを確かめてから使う（外部への誘導に使われる経路を作らない）。

### 決定6: 資格は 15 分・50MB・書き込みのみ

- **有効期間 15 分。** フォームを開いてからファイルを選び、送り終えるまでを収める。policy の期限は S3 が要求を受け取った時点で見るため、細い回線で大きな写真を送っている最中に切れうる。5 分では足りない場面がありうるので 15 分にする。切れたらやり直せばよい（元写真は置かれていない）。
- **`content-length-range` は 1 〜 50MB。** 空のファイルを弾き、上を切る。50MB は、スマートフォンと一般的なカメラの JPEG / HEIC が確実に収まり、かつ変換 Lambda（2048MB / 60 秒）が現実に扱える範囲として置く。**これは変換側の限界そのものではなく、いちばん手軽な入口に置く歯止めである。** 超えるものは手元の CLI から入れる。
- **署名は `PutObject` の1つだけ。** 発行された資格で読み出しも一覧も削除もできない。これは資格の作り方ではなく、実行ロールが `PutObject` しか持たないことによる（決定7）。**署名は実行ロールの権限を超えられない。**
- **1枚ぶんの署名を、その画面で選んだ N 枚すべてに使う。** policy はファイル名を含まないため、同じ資格が日付の下のどのファイル名にも使える。枚数ぶん署名を作る意味がない。

### 決定7: 実行ロールに足すのは3つのアクションだけ

| 対象 | アクション | 理由 |
| --- | --- | --- |
| アップロード用バケット `/*` | `s3:PutObject` | 元写真を置く |
| 配信用バケット `/*` | `s3:GetObject` | `HeadObject` の認可（決定4） |
| 配信用バケット | `s3:ListBucket` | 「まだ無い」を 404 として受け取るため（決定4） |

**アップロード用バケットへの `s3:GetObject` は与えない。** 元写真は付随情報を除去する前のものであり、撮影場所を含みうる。置ける入口であることが、過去に置いたものを持ち出せる経路になってはならない（`editor-hosting` に足した要件）。

代償として、**投入の前に「同じキーが既にある」ことを確かめられない。** これは決定4 の副産物（投入後に「差し替えた」と分かる）で受け止め、失われないことは versioning が担保する。

**配信用バケットへの書き込みと、写真配信の CloudFront への権限は与えない。** 配信されるものを書けるのは変換 Lambda だけ、という現状を動かさない。invalidation も変換 Lambda が既に行っている。

### 決定8: 設定は既存の出どころから引く。転記を増やさない

- `editor/function.jsonnet` に `PHOTO_UPLOAD_BUCKET` / `PHOTO_BUCKET` / `PHOTO_URL` を足し、いずれも tfstate から読む。`src/lib/env.ts` の既存の関数がそのまま使える（`required()` は呼ばれたときにだけ落ちる遅延評価なので、写真に触らない経路は影響を受けない）。
- 手元での実行（`scripts/dev-editor.sh`）は、`load_env` が `config/<環境>.env` を `set -a` で読み込むため**すでにこの3つを持っている**。足すのは `require_env_vars` の確認だけで、欠けていれば起動の時点で分かる。
- Terraform は、root module が `module.photos` の出力を `module.editor` へ渡す形にする。**写真の module には手を入れない。** `config/<環境>.env` への転記も増えない。

### 決定9: 元写真に Content-Type を付けない

POST のフォームに `Content-Type` フィールドを置かないと、オブジェクトは `binary/octet-stream` になる。ブラウザは multipart の各パートに種別を書くが、S3 が見るのはフォームのフィールドのほうである。

置かない理由は2つ。**元写真は配信されない**ので表示に影響しない（変換は中身を見て行う）。そして**編集アプリケーションには元写真を読み出す権限がない**（決定7）ので、CLI が Content-Type を付けている理由——手元に落として開いたときのため——がこの経路には存在しない。

投入がスクリプトから行われる以上、`file.type` を読んで埋めることはできる。それでも置かないのは、**値を使う相手がいない**ためである。policy の条件が1つ増え、CLI と揃っていない状態が「揃った」ように見えるだけで、読む者が現れない。必要になったときに足せばよい。

### 決定10: 生成された写真は `thumbnail` を画面に出して確かめる

投入が終わったあと、**生成された写真そのものを画面に出す**。URL の一覧だけでは、意図した写真が入ったかを確かめるのに1つずつ開くことになる。日付を間違えた・向きが倒れている・別の写真を選んでいた、はいずれも本文に貼る前に気づきたい。

出すのは `thumbnail`（長辺 240px）である。4つのうちいちばん小さく、確認に足りる。複数枚を並べるので、`medium` を並べると画面が重くなる。

**生成が終わったものだけを出す。** まだ無いうちに `<img>` を置くと、ブラウザが配信 URL を取りにいき、**まだ無いあいだの 403 が CDN に載る**（決定4 で避けたことを、確認の表示のほうから起こしてしまう）。したがって表示は `HeadObject` が「出来た」と答えたあとに限る。順序が逆になってはならない。

### 決定11: 画面には運用の手順を書かない

投入の画面に置く説明は、**その画面で操作する人に必要なものだけ**にする。上限の大きさ、変換できない形式、生成に少し時間がかかること——このあたりまでである。

手元の CLI の呼び出し方、バケットの名前、ログの在り処といった運用の知識は書かない。同じことが README にあり、そこが本来の置き場所である。画面に書くと、**その画面を使うたびに読み飛ばす行が増える**。

## Risks / Trade-offs

- **同じ日に同じファイル名の写真を入れると上書きになる** → CLI と同じ性質で、`photo-ingest` が定める挙動（再投入は作り直し）そのものでもある。versioning があるので元写真は取り戻せる。加えて決定4 の副産物で、画面が「差し替えた」と言える。
- **スクリプトが動かないと投入できなくなった** → 素の HTML フォームで送る形は複数枚と両立しない（決定2）。動かない環境ではその旨を画面に出す。**編集アプリケーションの他のページは従来どおりフォームだけで動く**ので、影響はこの画面に閉じている。
- **アップロード用バケットに CORS が付く** → 許すオリジンは環境ごとの編集アプリケーション（と、手元での開発に使う `localhost`）に限る。CORS は権限ではなく、署名のない要求は変わらず拒否される。
- **一時的な資格が HTML に載る** → 返るのは認証を通った利用者にだけである。対象は1つの日付、期間は 15 分、できるのは書き込みだけ。それでもブラウザの履歴やキャッシュに残りうるので、投入の画面には `Cache-Control: no-store` を付ける。
- **転送の途中で資格の期限が切れる** → 失敗し、元写真は置かれない。やり直せる。15 分はそれが起きにくい長さとして選んでいるが、極端に細い回線では起こりうる。
- **ブラウザからの投入が編集アプリケーションの記録に残らない** → 内容が編集アプリケーションを通らない以上、通った記録も残らない。何がいつ置かれたかはアップロード用バケットの versioning が持ち、変換の成否は変換 Lambda の記録が持つ。**新しく記録の仕組みを作らない。**
- **`SameSite` を `Strict` に変えると戻りが未認証になる** → 決定2 のとおり。`session.ts` にその依存を書き残す。Google の認証からの戻りも同じ性質なので、変えるときは両方が壊れる。
- **1枚だけ失敗する状態がありうる** → N 回の要求は独立しているので、3枚目だけ失敗して残りは入る、が起こる。取り消さず、どれが失敗したかを出して残りはそのまま使えるようにする（`photo-ingest` の「一部が失敗する」）。**途中まで入ったものを巻き戻すほうが害が大きい**——巻き戻すには削除の権限が要り、それは与えていない。
- **確認の表示が配信を汚しうる** → 生成が終わる前に `<img>` を置くと、決定4 で避けた「403 が CDN に載る」を確認の側から起こす。表示は `HeadObject` が答えたあとに限る（決定10）。
- **投入の経路が2つになった** → 規約（キー・URL・サイズ・形式）はすべて既存の1箇所に残るが、**投入する側のコードは2つになる**。`src/lib/photo.ts` の注記（変換 Lambda と規約を共有していない）と同じ性質の注意が1つ増える。

## Migration Plan

1. staging に `terraform apply`。増えるのは編集アプリケーションの IAM ポリシーの3つのステートメントと、アップロード用バケットの CORS 設定である。**バケットそのものも CloudFront も変換 Lambda も作りは変わらない。**
2. `npm run deploy:editor -- staging`。
3. staging で写真を投入し、CLI から同じ日付・同じファイル名で投入した場合と**同じキー・同じ URL**になることを確認する。生成の完了表示が、実際に画像が返るようになる時点と一致することも見る。
4. `terraform plan` が差分を出さないことを確認する（既存の運用と同じ）。
5. production に同じ順で適用する。

**ロールバック**: `lambroll rollback` で投入の画面が消える。Terraform は module 呼び出しの変数・IAM・CORS を戻せばよい。**手元の CLI からの投入は最初から最後まで変わらない**ので、この change のどの段階で止めても写真は入れられる。
