## Context

動機は proposal.md の Why を参照。ここでは approach を決めるうえで効いた、旧サイトの記事の実態だけを述べる。

`apkas/eskarun` の `_articles/` に 1090 件の Markdown がある。うち `20210101.md` は旧サイトのテスト用の下書きで、移行対象は 2023-01-01 から 2026-06-07 までの **1089件**。ファイルの置き場は `<年>/<年月>/<YYYYMMDD>.md` だが、`20251130.md` だけがルート直下にある（旧サイトは再帰的に読むので、この1件も記事として扱われている）。日付を持っているのはファイル名だけで、本文にも frontmatter にも日付は書かれていない。

frontmatter は `title`（426件）、`location`（107件）、`status`（上記テスト記事の1件のみ）。加えて `tilte` と綴りを誤った記事が2件ある。旧サイトはこれをタイトルなしとして扱っていた。

本文の内訳を数えた結果が次の通り。**663件はタイトルを持たない**。

| 要素 | 件数 | 備考 |
| --- | --- | --- |
| `![](…)` 説明なしの画像 | 637件 | |
| `---`（hr） | 449件 | 一日の中の話題の区切り |
| `![説明](…)` 説明つきの画像 | 97件 | 旧サイトは画像下にキャプションとして表示 |
| `<table>` の画像グリッド | 86件 / 188箇所 | 2列99・3列34・1列6など |
| `<td colspan>` の説明行 | 20件 | グリッド全体に対する説明 |
| `##` 見出し | 33件 | |
| リンク | 50件 | |
| リスト / 打ち消し / インラインコード / 引用 / 数式 | 5 / 5 / 6 / 2 / 1件 | |

**本文に現れる HTML タグは `table` / `tr` / `td` / `img` の4種しかない**。`img` には `src` と `class`（`top` / `middle` / `bottom` / `caption` / `bottom-caption` / `nopb`）、`td` には `colspan` だけが付く。旧サイトは `rehype-raw` で HTML を通し、Tailwind のクラスと React コンポーネントで見せていた。`class` の正体は画像の上下 padding の指定で、連続するグリッドを一塊に見せるためのものだった（`nopb` はどの分岐にも一致せず、旧サイトでも効いていない）。

画像は 2369 参照すべてが `photos.old.apkas.net` にあり、生存を確認済み。実寸は 2048px 幅程度。

## Goals / Non-Goals

**Goals:**

- 旧サイトの記事を、書かれた内容を落とさずに DynamoDB へ移せるようにする。
- 移行したエントリが、旧サイトと同等に読める状態で表示される。特に、書いた文が画面から消えないこと。
- 移行の実行前に、何が入り何が置き換わるのかを確かめられること。

**Non-Goals:**

- 1089件を実際に投入すること。この change では代表16件までとし、投入先と時期は表示が仕上がってから決める（決定7）。
- 旧サイトの見た目の再現。読めることを満たせば、余白や体裁は現在のサイトの流儀でよい。
- 移行を繰り返し行えるようにすること。一度きりの操作として作る。
- 旧サイトそのものの処遇。停止するかどうかはこの change の外。

## Decisions

### 1. 本文は書き換えず、表示側で解く

取り込みでは本文に手を入れない。HTML を Markdown に直すことも、`class` を外すことも、キャプションを別の書き方に置き換えることもしない。整えるのは frontmatter 直後の空行と末尾の改行だけとする。

理由は、**書き換えは失うだけで取り戻せない**ため。1089件の本文を機械的に変換すれば、変換器の取りこぼしがそのまま日記の欠落になる。元ファイルは旧リポジトリに残るとはいえ、それは「間違えても元があるから戻せる」という話で、間違いに気づける保証はどこにもない。本文を素通しすれば、DynamoDB の内容と旧ファイルの内容が一致し、突き合わせで検証できる。実際、代表16件で `export/` への書き出しが旧ファイルとバイト単位で一致することを確認した。

代償として、本文の中に表示のための HTML が残り続ける。これは `diary-entry-store` の「本文は Markdown として保持する。整形済みの HTML を保持してはならない」に触れそうに見えるが、触れない。この要件が禁じているのは**本文全体を HTML に変換して保持すること**、つまり表示側の実装に本文の形式を握らせることであって、著者が Markdown の中に書いた HTML はもとの記述そのものである。Markdown は HTML の混在を仕様として許している。

**却下した案**: グリッドを独自記法（`::: grid` のようなコンテナ）に変換して保持する。本文が読みやすくなり将来の表示側の自由度も上がるが、変換の正しさをこちらが保証しなければならず、1089件ぶんの検証コストが「読めるようにする」という目的に見合わない。旧サイトの HTML は用途が1つでタグも4種しかないため、そのまま解釈するほうが確実である。

### 2. タイトルのないエントリは日付を見出しにし、日付行を出さない

663件が該当する。`(無題)` は「本来あるべきものが無い」と読ませてしまうが、日記に名前を付けない日が多いのは欠落ではない。

日付の書式は**日付行と同じ曜日つきで統一する**（`2026年1月1日（木）`）。同じものが2つの書式で現れるほうが、見出しが少し長いことより読み手を混乱させる。`src/lib/date.ts` の `formatDateJa` をそのまま使い、書式を増やさない。

```
【タイトルあり】                    【タイトルなし】
2026年8月1日（土）   ← 日付行        2026年1月1日（木）  ← 見出し
日記を再開した       ← 見出し        元日、みんな休みなので…
本文…
```

書式を揃えられるのは、**日付を出す場所が排他になる**ため。タイトルがあれば日付行に、なければ見出しに出し、両方に出すことはない。同じ日付が1ページに2度現れないので、書式を変えて見分けさせる必要がそもそもない。

日付を持たないページは存在しないので、日付は常にどちらか一方に現れる。

### 3. 画像の説明は `figure` / `figcaption` に組み替える

`![説明](…)` の説明は、いまの整形では `img` の `alt` になるだけで画面に出ない。`alt` は画像が表示できないときの代替であって、添えられた文ではない。書いた文が読めない状態を解消する。

組み替えは **Markdown の整形処理の中**で行う。`@astrojs/markdown-satteri` の `createSatteriMarkdownProcessor` は `hastPlugins` を受け取るので、hast を歩いて `img` を見つけ、条件を満たすものだけを差し替える。

```
条件: alt が空でない、かつ段落の中で画像が単独で置かれている
      <p><img src alt="会場"></p>
   -> <figure><img src alt="会場"><figcaption>会場</figcaption></figure>
```

段落の中で単独であることを条件にするのは、**文章の途中に置かれた画像を巻き込まないため**。`文章の途中に ![説明](…) がある場合` を `figure` にすると段落が壊れる。`alt` は残す。画像が表示できないときの代替としての役目は変わらない。

実装可能性は確認済みで、上の3つの形（説明つき・説明なし・文中）が意図どおりに分かれることを検証した。

**却下した案**: 整形後の HTML 文字列を置換する。`renderMarkdown` の戻り値は文字列なので手軽だが、HTML を正規表現で扱うことになり、本文中に直接書かれた `<img>`（グリッドの中）まで巻き込む危険がある。hast の段階なら、木の形で条件を書ける。

**却下した案**: CSS だけで解く（`img[alt]::after { content: attr(alt) }`）。`img` は置換要素なので疑似要素を持てず、そもそも実現しない。

### 4. グリッドは `table` のまま CSS で整える

本文の `table` を DOM の構造としてはそのまま使い、日別ページのスタイルで見せ方を与える。

| 対象 | 与えるもの | 理由 |
| --- | --- | --- |
| `table` | `table-layout: fixed` / `width: 100%` | 列幅を等分する。既定の自動レイアウトでは画像の実寸比で列幅が決まり、揃わない |
| `td` の間 | 間隔 | 画像同士が接して1枚に見えるのを避ける |
| `td[colspan]` | 中央寄せ・小さめ・淡い色 | 並び全体に対する説明として読ませる |
| `figcaption` | 同上 | 画像1枚の説明と、並びの説明の体裁を揃える |

`td[colspan]` で説明行を選べるのは、画像の入るセルに `colspan` が付いた例が1つもないため（`colspan` は説明行の `2` が30箇所、`3` が7箇所のみ）。

`img` の `class` は使わない。旧サイトでは連続するグリッドを一塊に見せる余白指定だったが、**表示が本文中の class 名に依存する状態を続けたくない**。本文は著者の書いたものであって、表示側の設定を置く場所ではない。グリッド間の余白は一律にする。連続するグリッドは、一塊ではなく別々の並びとして見える。

### 5. `createdAt` は取り込み時刻とし、書き込み経路は変えない

移行したエントリの `createdAt` は `putEntry` が付ける取り込み時刻になる。旧リポジトリの git 履歴から初出コミットの日時を引けば実際に書かれた時期に近い値を入れられるが、そのためには `putEntry` に `createdAt` を外から渡す口を開ける必要がある。

開けない。`createdAt` / `updatedAt` の管理を1箇所に閉じてあるのは、書き込み経路が増えたときに時刻の扱いが割れないようにするためで、その口は移行が終わっても残る。日記の所属日は `date` が持っており、`createdAt` は画面のどこにも出ない。一度きりの移行のために、恒久的に効く保証を緩める取引が見合わない。

### 6. 取り込みは一時的な CLI として作り、実行前に下見できるようにする

`npm run import-legacy -- <環境> --source <旧記事のディレクトリ>` を追加する。既存の `entry` と同じく、環境名を第1引数に取って対象環境を明示させる。

日付は**ファイル名からのみ**決める。本文や frontmatter に日付はなく、推定の余地を残す理由がない。ファイル名が日付の形でないファイルは取り込まず、警告として報告する。

取り込みは `putEntry` を通す。日付が一意キーなので、同じ日付への取り込みは2件目を作らず更新になる。この性質は移行では**危険な側**に働く（既存のエントリを黙って置き換えうる）ため、`--dry-run` で「新規か更新か」を日付ごとに示す。実行前に何が置き換わるかを見られない移行は行わない。

絞り込みは `--only <日付,…>`（代表的な記事だけを入れる）と `--from` / `--to`（範囲を区切る）を用意する。段階的に入れて確認するために要る。`--only` に指定した日付の記事が見つからないときは0件で正常終了させずエラーにする。指定の打ち間違いと、元の記事の不在を取り違えないため。

`status` の既定は `published` とする。旧サイトで公開されていたものを移すのだから、公開状態が既定である。frontmatter に `status` があればそちらを優先する。

`tilte` の綴り誤り2件は `title` として取り込み、警告に出す。旧サイトではタイトルなしとして表示されていたが、書き手の意図は明らかであり、移行はそれを直せる機会である。黙って直さないのは、こちらの解釈が入った箇所を移行後に確かめられるようにするため。

同じ日付のファイルが複数見つかった場合は、**どちらも取り込まず**警告する。日付が一意キーである以上、片方を黙って採用するとどちらが残ったのか後から分からない。

移行が終わったら、この CLI と `src/legacy/` は削除する。残しておくと、旧サイトのファイル構成に依存したコードを保守し続けることになる。

### 7. staging に入れるのは代表16件までとする

全件を staging に入れない。表示の確認に必要なのは**パターンの網羅**であって件数ではなく、16件で32パターンすべてを踏める。

件数を増やすと失うものがある。staging のテスト用エントリ6件のうち5件は旧サイトに同じ日付の記事があり、全件を入れると置き換わる。その中には下書きの動作確認に使っている 2025-12-24 が含まれ、旧記事は公開状態で入るため **staging から下書きがいなくなる**。下書きが公開サイトに出ないことは確認し続けたい性質なので、確認手段のほうを潰す取引になる。代表16件はどのテスト用エントリとも日付が重ならず、この問題が起きない。

1089件の実際の投入先は、表示が仕上がってから決める。旧サイトのファイルは消えないので、決定を遅らせても失うものがない。

## Risks / Trade-offs

- **表示の確認が代表16件に依存する**。パターンの洗い出しが漏れていれば、その形は誰にも見られないまま本番に入る。洗い出しは本文の機械的な走査（HTML タグ・Markdown 記法・frontmatter キーの全数え上げ）で行っており、目視で選んでいない。
- **全件の書き込みは途中で失敗しうる**。`putEntry` は1件ずつの PutItem なので、途中で止まっても入ったぶんは残る。再実行すれば同じ結果になる（同じ日付は更新になる）ため、リトライで回復できる。`--from` / `--to` で範囲を絞って再開することもできる。
- **`class` を使わない判断により、連続するグリッドの見え方が旧サイトと変わる**（14件が該当）。一塊だった並びが別々の並びとして見える。読めなくなるわけではないため許容する。
- **数式1件は文字のまま出る**。`($2^A$)` のように括弧つきで書かれており、文としては読める。

## Migration Plan

1. staging に代表16件を入れて表示を確認する（済）。
2. 表示側の変更を入れ、同じ16件で確認する。
3. staging にデプロイし、稼働中のサイトで確認する。
4. 1089件の投入先と時期は、ここまでが済んでから決める。
