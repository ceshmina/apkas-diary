## Context

動機は proposal.md の Why を参照。ここでは実装の形を決めるうえで効いた、現状の作りと日記データの実態を述べる。

サイト生成の入力は `src/lib/site-data.ts` の `publishedEntries()` ただ1つで、GSI1 から取った公開済みエントリの全件を日付の昇順で返す。年別・月別・月日別といった切り口はすべて、この配列をメモリ上でまとめ直して作っている。隣接するエントリも、この配列の添字の隣として取れる。新しい問い合わせは要らない。

日記は毎日書かれてはいない。移行済みの1089件は2023-01-01から2026-06-07までに散っており、書かれていない日のほうが多い。したがって「前後」を暦上の前日・翌日として解決すると、その多くはエントリの存在しない日付を指す。

一覧の並びは現在ばらばらである。トップページ（`recentEntries`）と月日ページは降順、年別ページと月別ページは `byDateAsc` で昇順。年への導線は降順、月への導線は昇順。

## Goals / Non-Goals

**Goals:**

- 日記を続けて読むときに、一覧を経由せずに隣の日へ移れること。
- 左右の向きが何を意味するかがサイト全体で一定であること。ページによって `←` の指す方向が変わらない。
- 隣接の解決が、下書きを一切参照せずに済むこと。
- 端（最新・最古）でも導線の位置が動かず、向きの手がかりが崩れないこと。

**Non-Goals:**

- 一覧ページどうしの移動を足すこと。
- 隣接を暦の連続として扱うこと。エントリのない日をページとして持つ考えは取らない。
- 訪問者が並び順を切り替えられるようにすること。

## Decisions

### 1. 「隣接」は暦の隣ではなく、公開エントリの並びの隣とする

`2026-06-07` の次に古いエントリが `2026-06-03` なら、`→` は `2026-06-03` を指す。あいだの4日を飛ばす。

暦上の前日・翌日を指す作りにすると、エントリのない日を指したときに 404 へ送るか、リンクを消すかのどちらかになる。前者は導線として壊れており、後者は「書かれていない日が続くとその先へ進めない」という行き止まりを作る。日記の大半の日は書かれていないので、行き止まりのほうが常態になってしまう。

書かれた日記だけを繋げば、導線は必ず存在するページを指し、日記を書いた順に読み進められる。これは読み手が求めている「次の日記」と一致する。

### 2. コード上は `prev` / `next` ではなく `newer` / `older` と呼ぶ

矢印の規約が「`←` が新しい、`→` が古い」であるため、`prev` / `next` はどちらの意味にも読める。時間の前後として読めば `prev` は古い側、画面の左右として読めば `prev` は新しい側になる。この2つは今回互いに逆を向いており、名前を見た人ごとに解釈が割れる。

`newer` / `older` は日付との対応が一意に決まる。画面上の配置は「`newer` が左」という1文で決まり、その1文だけが規約になる。

同じ理由で `rel="prev"` / `rel="next"` は付けない。この属性は文書の順序を表すものだが、時系列の記事に対する慣例が定まっておらず、付けたところで正しさを主張できない。付けないことによって失われる機能もない。

### 3. 隣接エントリは日付とタイトルだけを渡す

`getStaticPaths` の props に隣のエントリを丸ごと入れず、`{ date, title }` だけの型を渡す。

日別ページは1000件を超え、その1件ずつに前後2件ぶんの本文を持たせることになるが、表示に使うのは日付とタイトルだけである。運ばない理由は無駄の削減が半分、もう半分は取り違えの余地を消すためで、隣のエントリの本文がそもそも props に入っていなければ、それを誤って描画することもない。

```ts
/** 隣接するエントリへの導線に出す最小限。本文は運ばない。 */
export interface EntryLink {
  date: string
  title: string
}
```

### 4. 隣接の解決は `site-data.ts` に置く

`site-data.ts` が公開サイトのビルドにおける唯一のデータ入力である、という既存の原則に従う。ページ側で `publishedEntries()` を引いて添字を操作すると、データの加工がこのモジュールの外に漏れ、原則が「だいたい守られている」状態に薄まる。

昇順の配列に対して、添字 `i` のエントリの `newer` は `i + 1`、`older` は `i - 1` になる。昇順であることは `publishedEntries()` の約束なので、この対応は関数の中で1度だけ書けばよい。

### 5. 導線は本文の直後、既存のリンク群の上に置く

日別ページの末尾には既に「N月の一覧」「N年の一覧」「過去の同じ日」が並んでいる。前後の導線はこれらより先に、独立した `nav` として置く。

読み終えたあと最も起こりやすい行動は「次を読む」であり、一覧へ戻るのはその次に来る。既存のリンク群に4つ目、5つ目として混ぜると、左右の配置が取れなくなるうえ、使う頻度の違いが見た目に出ない。

### 6. 端では片方だけを出し、位置は動かさない

最新のエントリには `newer` が、最古のエントリには `older` が存在しない。その側には何も置かない。「これ以上ありません」のような文言は出さない。タイトルのないエントリに `(無題)` と書かないのと同じ理由で、そこに何かが欠けているわけではないためである。

ただし、残ったほうが中央や逆側に寄ってはならない。`older` だけのときにそれが左端に来ると、`→` の矢印が画面の左にあることになり、向きの手がかりが壊れる。

そこで、2つの導線に等しい基準幅（`flex: 1 1 14rem`）を与え、`older` の中身を `justify-content: flex-end` で右に寄せる。片方しかないときは残ったほうが幅いっぱいに広がるが、`newer` は左、`older` は右に中身が置かれたままになる。狭い画面では基準幅を保てなくなって上下に折り返り、そのときも各行の中で同じ左右が保たれる。

**却下した案**: `justify-content: space-between` で両端に寄せる。要素が1つのときに左寄せになるため、最古のエントリで `→` が左に来てしまう。`older` に `margin-left: auto` を与える案も、位置は正しくなるが幅の取り合いが `flex: 0 1 auto` のままになり、狭い画面で上下に折り返らずに横で潰れ合う。

### 7. 一覧の向きは新しい順に統一する

`byDateAsc` を使っていた年別ページ・月別ページを `byDateDesc` に変える。年別ページの月への導線も降順にする。

一覧が新しい順であることと、`←` が新しい側であることは、同じ1つの規約の両面である。一覧を上から下に読むことと、日別ページで `→` を辿ることが、どちらも過去へ遡る動きになる。年への導線（既に降順）とトップページ（既に降順）に合わせる形でもある。

## Risks / Trade-offs

- **`←` が「戻る」と一致しない**。ブラウザの戻る操作や、多くのサイトのページ送りでは `←` が「前のページ／古い方」を指す。今回はこれと逆になる。受け入れる理由は、逆にすると一覧の並び（上が新しい）と食い違い、同じサイトの中で2つの向きが同居してしまうため。サイト内で1つに揃っていれば、数ページ辿るうちに掴める。
- **矢印だけでは向きの意味が伝わらない**読み手がいる。導線に日付を出すため、`2026年8月2日` と `2026年7月31日` のどちらが新しいかは読めば分かる。矢印は視覚的な手がかりであって、唯一の手がかりではない。
- **年別・月別ページの見え方が変わる**。同じ URL の中身の並びが逆になるが、URL の集合は変わらず、リンクもブックマークも壊れない。

## Migration Plan

なし。表示のみの変更で、DynamoDB のデータにも書き込み経路にも触れない。ビルドし直せば新しい配信物になる。
