## Context

動機は proposal.md の Why を、満たすべき振る舞いは `specs/photo-ingest/spec.md` と `specs/photo-delivery/spec.md` を参照。ここでは実装の形を決めるうえで効いた、現状の作りを述べる。

**S3 + CloudFront + OAC + ACM + Route53 の組み合わせは、`terraform/modules/delivery` に既にある。** 独自ドメイン、us-east-1 の証明書、DNS 検証、A/AAAA の alias、OAC 限定のバケットポリシーまで一式が揃っている。写真の配信はこの形をもう一度なぞることになる。違うのは、配信元に置かれるものが「ローカルで生成して sync したもの」ではなく「クラウド側で自動生成されたもの」であることだけである。

**サイトのデプロイは `aws s3 sync dist/ --delete` である。** 配信元にあって `dist/` に無いものは消える。写真を同じバケットに置いたら、次のデプロイで全部消える。バケットを分ける理由はここに尽きる。

**このリポジトリに Lambda はまだ1つもない。** ビルド成果物を伴うデプロイの型が存在しない。Terraform が扱ってきたのは、中身を持たない箱（S3、DynamoDB、CloudFront）と、ファイル1つで済むもの（CloudFront Function）だけである。

**インフラの形と、関数のコードは、変わる頻度が違う。** バケットや CloudFront はいちど決まればほとんど動かないのに対し、変換の中身は動かしながら直すことになる。Terraform に両方を持たせると、コードを1行直すたびに state を触る操作を通すことになり、変更の大きさに対して手続きが重くなる。

**画像処理は native binary への依存を持つ。** サイト生成の依存関係（`astro`、`@aws-sdk/*`）は純粋な JavaScript で、`npm ci` がプラットフォームを問わず通る。ここに Linux 用のバイナリを持つパッケージを混ぜたくない。

**日別ページの拡大表示は、URL 規約に依存するコードを既に持っている。** `src/components/photo-zoom.ts` は表示中の `src` の `/medium/` を `/large/` に置き換えて高解像度版を読む。新しい配信の URL 規約は、この置換が成り立つ形でなければならない。

## Goals / Non-Goals

**Goals:**

- 公開物に写真の付随情報が残らないことを、実装者の注意ではなく**経路の形**で担保すること。人が配信用バケットに書く手順を作らなければ、EXIF 付きの写真が公開される経路そのものが存在しない。
- 4つのサイズが常に揃っていること。参照する側が「このサイズはあるか」を確かめずに URL を組み立てられること。
- 生成を人が呼ばないこと。「投入したがリサイズを忘れた写真」という状態が作れないこと。
- 写真の配信と日記サイトの配信が、互いを壊せないこと。
- Lambda が native binary を抱えても、サイト生成の依存関係が増えないこと。
- インフラの変更と、関数のコードの変更を、互いを待たずに出せること。コードを直す操作が Terraform の state に触らないこと。

**Non-Goals:**

- 生成の即時性。投入から配信可能になるまでに数秒かかってよい。
- 派生画像の履歴管理。派生は元写真から何度でも作り直せる。
- 旧ホストからの移行と、本文の書き換え（proposal のスコープ外）。

## Decisions

### 1. バケットを2つに分け、配信用には Lambda しか書かない

アップロード用と配信用の2つを作る。人が置けるのはアップロード用だけ、配信用に置けるのは Lambda だけ、という役割にする。

分ける理由は2つある。1つは Context に書いたとおり、サイトの `sync --delete` と同居させられないこと。もう1つが本質で、**「公開されるものは、元写真から機械的に作られたものに限る」を構造で言えるようになる**ことである。配信用バケットに人が写真を置く手順があると、EXIF 付きの原本をうっかり置ける経路が残る。仕様の「付随情報が残らない」を、毎回の注意ではなく経路の不在で守る。

**却下した案**: 1つのバケットを `upload/` と `public/` のプレフィックスで分ける。プレフィックス単位の権限は書けるが、CloudFront のオリジンパスと IAM の条件の2箇所に同じ前提が散る。片方だけ直したときに穴が開く。バケットが2つなら、境界は名前そのものになる。

### 2. バージョニングは元写真のバケットにだけ有効にする

- **アップロード用: 有効**。元写真は作り直せない。同じキーへの投入は上書きになるので（spec の「同じキーへの再投入」）、取り違えたときに戻せる必要がある。spec の「元写真の取り違えからの復旧」はこれで満たす。
- **配信用: 無効**。派生画像は元写真からいつでも作り直せる。履歴に価値がなく、写真1枚につき4つの古い版が貯まるだけになる。

既存のサイト配信バケットはバージョニングが有効だが、あれは `--delete` を伴う sync の受け皿という別の事情による。同じ形を惰性でなぞらない。

### 3. 生成は S3 イベントから Lambda を直接呼ぶ。読めない入力では例外を投げない

`ObjectCreated:*` の通知で Lambda を非同期に呼ぶ。キューも EventBridge も挟まない。1日に数十枚という規模で、順序も集約も要らない。

非同期呼び出しでは、関数が投げた例外に対して Lambda が2回まで再試行する。この性質に合わせて失敗を2種類に分ける。

- **画像として読めなかった**: 記録だけ残して**正常終了する**。何度やり直しても結果は変わらない。3回失敗させる意味がなく、spec の「読めなかったことで以後の投入の処理が止まってはならない」もここで満たす。
- **書き込みに失敗した／読み出しに失敗した**: 例外を投げ、再試行に委ねる。一時的な失敗であれば次で通る。

**却下した案**: SQS を挟む。失敗の可視化と再処理には向くが、この規模で実際に起きる失敗は「画像でないファイルを置いた」がほとんどで、それは再処理しても通らない。リソースを1つ増やす見返りがない。

### 4. 1回の呼び出しで4サイズを作り、元写真のデコードは1度だけにする

サイズごとに関数を呼び分けると、同じ元写真を4回デコードする。デコードは処理時間の大半を占める。1度読んだものから4つを作る。

**各サイズは常に元写真から縮小する**。`large` から `medium` を、`medium` から `small` を作ると、縮小のたびの誤差が積み重なる。

拡大しないという要件（spec）は、「長辺を N に収める。ただし元より大きくはしない」という1つの指定で書ける。元が小さければ何もせずに素通りし、結果として元と同じ大きさの派生画像ができる。サイズごとの分岐は要らない。

### 5. 付随情報は「消す」のではなく「引き継がない」。ただし向きと色は画素に焼き込む

sharp は、明示的に指定しない限り入力の metadata を出力へ引き継がない。したがって**何も書かなければ** spec の「付随情報がすべて除去される」が満たされる。消す処理を足すのではなく、引き継ぐ指定を書かないことで満たす。書き忘れが安全な側に倒れる向きになる。

ただしそのままでは、一緒に落ちた2つの情報のせいで見え方が変わる（spec の「除去によって見え方が変わらない」）。

- **向き**。多くのカメラは横向きに撮ったまま記録し、EXIF の Orientation で「表示するときは90度回せ」と伝える。これを単に落とすと、縦位置の写真が横倒しで配信される。リサイズの**前に**回転を画素へ適用する。前でなければならないのは、長辺の判定が回転後の縦横で行われる必要があるためである。回転後に縦長になる写真の長辺は、回転前の幅ではなく高さにある。
- **色**。広い色空間で記録された写真から ICC プロファイルだけを落とすと、閲覧側はその画素を sRGB として解釈する。同じ数値が別の色として表示され、写真全体がくすむ、あるいは不自然に濃くなる。画素を sRGB に変換したうえで出力する。sRGB は Web の既定なので、プロファイルを埋めなくても同じ色で表示される。

**「EXIF が消えている」ことと「見え方が変わっていない」ことは別々の検査になる**。前者は生成物の metadata を読めば分かるが、後者は元写真と並べて見なければ分からない。tasks で分けて確かめる。

### 6. URL 規約はサイズ名を先頭に置き、拡張子は `.webp` にする

```
/<size>/<元キーの拡張子を webp に替えたもの>
```

サイズを先頭に置くのは旧ホストの形である。これを引き継ぐことで、既存の `photo-zoom.ts` が持つ `/medium/` → `/large/` の置換がそのまま成り立つ。この change では本文を書き換えないため実際に効くのは移行のときだが、**規約を今ここで決めてしまう**ので、後から気づいて直すことになる場所を作らない。

拡張子を `.webp` にするのは、名前と中身を食い違わせないためである。`.jpg` のまま WebP を返すと、ブラウザは Content-Type を見るので表示はできるが、保存して手元で開いたときに扱いに迷う。

**却下した案**: 拡張子を持たせない（`/medium/2026/08/08/IMG_1234`）。将来 AVIF へ移るときに URL を変えずに済むが、その利点は `Accept` ヘッダによる出し分けと組にして初めて出る。出し分けはキャッシュのキーを増やし、CloudFront の設定を複雑にする。今それを買う理由がない。

### 7. 元写真のキーがそのまま配信のパスになる。接頭辞は付けない

アップロード用バケットは写真専用なので、`original/` のような接頭辞は要らない。キーは `2026/08/08/IMG_1234.jpg` の形をとる。

投入 CLI は `--date` から `YYYY/MM/DD/` を組み立て、ファイル名をそのまま後ろに付ける。`--key` を与えればキー全体を明示できる。日付でディレクトリを切るのは、写真が1日の日記に属するという実態に合うためで、日付は既にこのシステム全体の並べ替えの軸になっている。

### 8. キャッシュはブラウザに1日、CDN に1年。作り直したときだけ invalidate する

派生画像には `Cache-Control: public, max-age=86400, s-maxage=31536000` を付ける。

同じ URL の写真は内容が変わらないのが常態なので、CDN では長く持たせる。差し替えが起きたときは、CDN が invalidation で即座に、ブラウザが最大1日で追いつく。

**invalidation は、配信先に同じキーの派生画像が既にあったときだけ行う**。Lambda は書き込む前にそれを調べ、あったときだけ4つのパスに対する invalidation を発行する。初回の投入では何もしない。キャッシュに載っていないものを消す要求に料金を払う理由がなく、無料枠（月1000パス、写真250枚ぶん）を初回投入で食い潰さずに済む。

**却下した案**: `max-age=31536000` だけにする。CDN は invalidation で更新できるが、一度見たブラウザは1年間古い写真を持ち続ける。差し替えの反映されない期間が長すぎる。

**却下した案**: `max-age=0, s-maxage=31536000`。常に正しいが、写真が20枚並ぶページを開くたびに20本の条件付き要求が出る。差し替えの稀さに対して払う代償が大きい。

### 9. コードは lambroll が持ち、Terraform は関数の存在と配線だけを持つ

`lambroll deploy` はコードと実行時設定だけを差し替え、`terraform apply` はインフラだけを動かす。互いの state に触らない。Context に書いた「頻度が違うものを同じ手続きに載せない」を、ツールの分担として実現する。

ただし **S3 のイベント通知と `aws_lambda_permission` は、関数が実在していないと作れない**。トリガーの配線を Terraform に置く以上、関数の実体が先に要る。そこで境界を**「存在と配線は Terraform、中身は lambroll」**に引く。

- Terraform は `aws_lambda_function` を、**動かない placeholder** を中身にして作る。宣言するのは `function_name` / `role` / `runtime` / `handler` / `architectures` だけで、メモリもタイムアウトも環境変数も書かない。
- placeholder は `data "archive_file"` でインラインの内容から組み立てる。バイナリをリポジトリに置かない。中身は「まだ lambroll でデプロイされていない」と記録して終わるハンドラにする。`terraform apply` から最初の `lambroll deploy` までの窓で写真が投入されたとき、記録を読めば理由がそのまま分かる。
- `lifecycle { ignore_changes }` に、**`function.jsonnet` が設定するものをすべて**並べる（`filename`、`source_code_hash`、`memory_size`、`timeout`、`environment`、`layers`、`ephemeral_storage`）。このリストは `function.jsonnet` の項目と1対1で対応していなければならない。
- `role` / `function_name` / `runtime` / `handler` / `architectures` は **ignore しない**。Terraform 側が唯一の宣言元であり、`function.jsonnet` はこれらを tfstate から読む（決定10）。同じ値が2箇所に書かれる状態を作らない。

**並べ忘れた項目は `terraform apply` が黙って既定値へ戻す。** これがこの形の弱点で、規約でしか守れない。`lambroll deploy` の直後に `terraform plan` が差分を出さないことを確認する手順を tasks に置き、リストの正しさをそこで見張る。

**却下した案**: `ignore_changes = all`。並べ忘れという失敗の形そのものが消えるが、ロールを作り直して ARN が変わったときに関数が古い ARN を持ち続け、呼び出しが実行時に静かに失敗する。設定が戻る事故は `terraform plan` で見えるのに対し、こちらは動かしてみるまで見えない。見える失敗のほうを取る。

**却下した案**: lambroll に関数そのものを所有させ、Terraform 側のトリガー配線を変数で囲って初回だけ2段階に適用する。1つのリソースを1つのツールが持つ形になるが、新しい環境を作るたびに `apply → deploy → apply` の順序が要る。

**却下した案**: Terraform だけで完結させる（`filename` と `source_code_hash`）。ツールは1つで済むが、コードを直す操作とインフラを触る操作が同じ重さになる。Goals に反する。

配布物は、macOS 上で `--os=linux --cpu=arm64` を指定して sharp を入れたディレクトリとして作り、`lambroll deploy --src` に渡す。`lambda/photo-resize/` に独自の `package.json` を置き、ルートの依存には sharp を入れない。サイト生成の `npm ci` に Linux 用の native binary を持ち込まない（Goals）。arm64 を選ぶのは、同じ性能あたりの単価が安く、sharp が prebuilt binary を持つためである。

**却下した案**: コンテナイメージ。ECR のリポジトリと push の手順が増える。zip は Lambda の直接アップロード上限（50MB）に収まる見込みで、その手間を買う理由がない。

**却下した案**: sharp を Lambda Layer に切り出す。関数の zip は小さくなるが、管理するリソースが1つ増え、レイヤーのバージョンと関数の対応を保つ手間が生じる。切り出す利益は複数の関数が同じレイヤーを共有するときに出るもので、関数は1つしかない。

### 10. `function.jsonnet` は tfstate を直接読む。値を転記しない

lambroll は jsonnet の native function として `tfstate` を持つ。ロール ARN、関数名、配信先バケット名、CloudFront のディストリビューション ID を、Terraform の state から直接引く。

このリポジトリは `terraform output` を `config/<環境>.env` へ手で転記する形を既に持っているが、それはサイトのビルドとデプロイがそれらを**環境変数として**要るからである。lambroll は state を読めるので、転記を1段挟む理由がない。転記があれば、転記し忘れという失敗の形が生まれる。

**環境の選択は、どの state を指すかだけで決まる。** `function.jsonnet` は1つで両環境に使える。state の場所は `terraform/envs/<環境>/backend.hcl` にあり（コミット対象外、README に用意する手順が既にある）、デプロイスクリプトはそこから `s3://<バケット>/<キー>` を組み立てて `--tfstate` に渡す。環境名を第1引数に取る既存の形（`load_env`）がそのまま効くので、対象環境を明示しない実行は成立しない。

state を読むのは、決定9で Terraform を唯一の宣言元にした値（ロール ARN、関数名、runtime、handler、architectures）と、Terraform が作った他のリソースの識別子（バケット名、ディストリビューション ID）である。`function.jsonnet` が自分で決めるのはメモリ・タイムアウト・コードだけになる。

**却下した案**: `terraform output` を `config/<環境>.env` に転記し、`must_env` で読む。既存の形には合うが、Lambda のために4つの値を増やすことになる。それらはサイトのビルドが使わない値で、`config/<環境>.env` に置く理由が「他がそうだから」以外にない。

### 11. CloudFront は圧縮を切り、CloudFront Function を持たない

- **`compress = false`**。WebP は既に圧縮されている。その上に gzip や brotli をかけてもほとんど縮まず、CPU と時間だけを使う。既存のサイト側が `compress = true` なのは、HTML と CSS と JS を配るからである。同じ形を惰性でなぞらない。
- **CloudFront Function は置かない**。サイト側の `rewrite-index.js` は、`/2026/08/01` のようなパスに `/index.html` を補うためのものだった。写真の URL は常にオブジェクトを直接指すので、補うものがない。

### 12. 存在しない写真には S3 の 403 をそのまま返す

OAC 経由のバケットポリシーは `s3:GetObject` しか許さないため、存在しないキーに対して S3 は 404 ではなく 403 を返す。サイト側はこれを 404 ページに寄せているが、写真では寄せない。

- CloudFront で応答コードを差し替えるには、**応答として返すページの実体**が要る。それを配信用バケットに置くことになり、決定1の「配信用に置かれるのは元写真から作られた派生画像だけ」が崩れる。境界を1つ緩めて得られるのが応答コードの見栄えだけ、という取引になる。
- 参照する側（`<img>`、`new Image()`）にとって 403 と 404 はどちらも「読めなかった」になる。写真ホストで区別に意味がない。

**却下した案**: バケットポリシーに `s3:ListBucket` を足して S3 に 404 を返させる。応答コードは素直になるが、それを与えると配信ドメインの根への要求がバケットのオブジェクト一覧として返りうる。spec が明示的に禁じているもの（「配信元に置かれたオブジェクトの一覧が返ってはならない」）を、応答コードの見栄えのために開けることになる。

### 13. 投入 CLI は既存の形をなぞり、生成の完了を短く待つ

`scripts/photo.sh` と `src/cli/put-photo.ts` の組にする。環境名を第1引数に取り、`config/<環境>.env` を読み、`npx tsx` で実体を呼ぶ。`npm run entry` とまったく同じ入口の形になる。「対象環境を明示しないと実行できない」（spec）は、既存の `load-env.sh` がそのまま担保する。

アップロードのあと、**配信先に `medium` が現れるまで短く待ってから URL を表示する**（上限は数十秒）。生成は非同期なので、待たずに URL だけ出すと、その URL を本文に書いた直後に開いた人が読めないものを見る。上限に達しても失敗とはせず、「まだ現れていない」と伝えて終わる。生成が遅れているのか失敗したのかは、記録を見れば分かる。

**却下した案**: 待たずに URL だけ表示する。実装は最小になるが、投入が成功したのか静かに失敗したのかを、操作した人がその場で知る手段がなくなる。

**却下した案**: Lambda の完了を厳密に追う（イベントや通知を受ける）。CLI がイベントの完了監視を持つことになる。配信先を数回覗きにいくだけで足りる話に、仕組みを増やしすぎている。

## Risks / Trade-offs

- **sharp の prebuilt binary が HEIC を読めない可能性がある**（ライセンス上の事情で HEVC デコーダを同梱しない） → 実データで確かめるタスクを置く。読めない場合は、手元で JPEG に変換してから投入する運用にする。写真の出所は自分のカメラと端末に限られるので、運用で吸収できる。対応が要るなら別の change で足す。
- **配信用バケットに人が書けないのは運用上の約束であって、権限による禁止ではない** → admin profile は何でもできる。Deny を書いて塞ぐこともできるが、Terraform 自身の操作まで巻き込んで締め出す危険がある。実際に守っているのは「書き込む手段が Lambda ひとつしかない」ことであり、これは経路の不在ではあっても権限の壁ではない。正直な限界として記す。
- **元写真を消しても派生画像が残る**（proposal のスコープ外） → 消す必要が生じたときは両方のバケットから手で消し、invalidate する。README に手順を書く。
- **巨大な画像でメモリまたは時間を使い切りうる** → メモリ 2048MB・タイムアウト 60 秒で始め、実データで確かめる。使い切った場合は記録に残り、派生画像は作られない。配信中のものが壊れることはないので、失敗の影響はその1枚に閉じる。
- **CloudFront ディストリビューションが環境あたり1つ増える** → 固定費は発生しないが、証明書の DNS 検証と配信の展開に数分かかる。既存のサイトを立てたときと同じ待ち時間になる。
- **`ignore_changes` に並べ忘れた項目を `terraform apply` が黙って既定値へ戻す** → 決定9の弱点で、規約でしか守れない。`lambroll deploy` の直後に `terraform plan` が差分を出さないことを確認する手順を置く。並べ忘れが残ったまま apply が走ると、メモリ不足やタイムアウトという形で後から現れる。気づけないわけではないが、気づくのが遅い。
- **`terraform apply` から最初の `lambroll deploy` までの窓では、placeholder が動いている** → その窓で投入された写真は変換されずに終わる。記録に理由が残るので、投入し直せばよい。新しい環境を作るときにしか開かない窓である。
- **`lambroll delete` を実行すると、Terraform が付けた S3 からの呼び出し許可も一緒に消える** → 許可は関数のリソースポリシーに載っており、lambroll はこれを管理しない。関数を消してしまった場合は `terraform apply` で配線を張り直す。`lambroll deploy` では消えない。
- **前提とするツールが1つ増える** → lambroll の導入が必要になる。README の「必要なツール」に足す。導入していない環境では `npm run deploy:lambda` がその場で失敗する（黙って古いコードが動き続けることはない）。

## Migration Plan

日記サイトの生成物にも DynamoDB のデータにも触れない。この change を適用してもサイトの見た目は1ページも変わらない（本文の参照は旧ホストのまま）。

1. staging で `terraform apply`。証明書の DNS 検証が通ることを確かめる。この時点で関数は placeholder のまま動いている。
2. `npm run deploy:lambda -- staging` で実装を載せる。
3. `terraform plan` が差分を出さないことを確かめる。`ignore_changes` の並びが `function.jsonnet` と対応していることの確認であり、以後 `lambroll deploy` のたびに行う。
4. 実際の写真を1枚投入し、4つのサイズが揃うこと、EXIF が残っていないこと、向きと色が変わっていないことを確かめる。
5. 同じキーに別の写真を投入し、配信内容が入れ替わることを確かめる。
6. `config/staging.env` に output を転記する（投入 CLI が使う値。lambroll は tfstate を読むので転記に含めない）。
7. 同じ手順で production に進む。

以後、コードだけを直したときは `npm run deploy:lambda -- <環境>` で完結する。`terraform apply` は要らない。

戻すときは、`envs/*/main.tf` から module の呼び出しを外して apply すれば、写真の配信基盤ごと消える（関数も Terraform が持っているので一緒に消える）。日記サイトには影響しない。元写真を残したい場合は、消える前にバケットの中身を手元へ落とす。コードだけを戻したいときは `lambroll rollback` で1つ前のバージョンに戻せる。

## Open Questions

- **sharp の prebuilt binary で HEIC を読めるか。** 読めなくても JPEG 経由で運用でき、specs も、選んだ approach も、tasks の並びも変わらない。実装のときに確かめて README に書けばよい。
