# 移行の結果

2026-08-14 に実施。

## 数

| | staging | production |
|---|---|---|
| 走査したエントリ | 25 | 1,110 |
| 旧ホストを参照していた日記 | 12 | 720 |
| 移行した写真 | 59 | 2,365 |
| 書き換えた箇所 | 59 | 2,365 |
| 元写真から投入（撮影情報あり） | 59 | 2,365 |
| 配信画像から投入（撮影情報なし） | **0** | **0** |
| 派生画像が揃わなかったもの | 0 | 0 |
| 目録に届かなかったもの | 0 | 0 |
| 目録機能より前の投入を拾い直したもの | 12 | 30 |

元写真の総量は production で 18.12 GB。投入は並列度8で約40分、変換 Lambda の追随はさらに数分。初回の投入なので CDN の無効化は発生していない（拾い直しの 30 枚ぶんのみ発生）。

**撮影情報が失われた写真は1枚も無い。** 旧ホストの `/original/` に元写真が残っており、配信用の WebP から作り直す必要がまったく無かった。この change を今やる理由（proposal.md - Why）がそのまま結果に出ている。

## 保管しているもの

いずれもリポジトリの外、`/migration/` と手元のディレクトリ（`.gitignore` 済み）。

| もの | 場所 | 中身 |
|---|---|---|
| 台帳 | `migration/<環境>/photos.jsonl` | 写真1枚ごとの、旧 URL・新 URL・取得元・投入先・照合の結果 |
| 書き換え前の本文 | `migration/<環境>/snapshots/<日付>.json` | production 720 件 / staging 12 件 |
| 旧バケットの元写真 | `~/apkas-old-originals/` | 2,378 ファイル・19 GB |

**旧バケットの同期は、日記から参照されていない 13 枚も含んでいる**（2,378 対 2,365）。旧ホストを止めたときに、参照の無い写真だけが失われるという状態を作らないためにそのまま残してある。

戻すときは `npm run migrate-photos -- <環境> rollback`。本文だけを控えの内容に戻す。写真は新旧どちらのホストからも配信され続けるため、戻しても表示は壊れない。

## やり残し

- **公開サイトへの反映**。`npm run deploy -- production` は人の意思を要求する（`scripts/deploy.sh`）。反映するまで公開サイトは旧ホストの URL を配信し続けるが、旧ホストが生きているあいだ表示は正常である。
- **旧ホストの廃止**。本文からの参照は無くなったが、DNS と配信の停止はこの change の対象外（proposal.md - スコープ外）。廃止する前に、上の同期を確実に保管すること。

## 途中で直したこと

**投入の側の記録を飛ばしていた**（design.md 決定1）。当初は「PutObject だけを行い目録には触れない」としていたが、配信 URL（`url`）を書くのは投入の側だけで、変換 Lambda は書かない。staging の 59 枚がすべて `url` を持たない記録になり、「記録は配信 URL と元写真のキーを持つ」（`photo-catalog`、MUST）を満たさなかった。移行は新しい経路ではなく投入そのものなので、`putPhoto()` を通すよう直した。照合の条件にも `url` の存在を加えてある。**staging を通していなければ、production の 2,365 枚が同じ形で欠けたまま本文の書き換えまで進んでいた。**

**部分的な棚卸しが台帳を消していた**。`plan --only` が走査した日の行だけを書き戻しており、他の日の行——と、そこに記録された投入済みの印——を落としていた。手元の DynamoDB Local での通しで見つけ、既存の台帳へのマージに直した。
