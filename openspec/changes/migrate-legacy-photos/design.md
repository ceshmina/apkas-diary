## Context

動機は proposal.md - Why を参照。ここでは設計を規定する現状の事実だけを挙げる。

- **新基盤の投入規約**: upload バケットに `YYYY/MM/DD/<ファイル名>.<拡張子>` で置くと、photo-resize Lambda（2048MB / 60s、S3 イベント駆動）が派生4サイズ（thumbnail/small/medium/large、WebP）の生成と目録への記録（EXIF 込み）を自動で行う。この規約に沿わないキーは派生のみ生成され目録に載らない。
- **旧参照の実態**（production 本文、調査済み）: 2,365件・全ユニーク。**各写真はちょうど1つのエントリからのみ参照**されており、同一エントリ内での basename 衝突も無い。パスは2形式ある。
  - フラット形式 `medium/YYYYMM/YYYYMMDD-xxx.webp`: 2,345件。ファイル名は全件 `YYYYMMDD-` 始まり。うち10件はディレクトリ月とファイル名日付が食い違う（深夜撮影）。
  - 階層形式 `medium/YYYY/MM/DD/NAME.webp`: 20件（2025/04/25〜30 のみ）。ファイル名に日付を含まない。
  - 参照はすべて `/medium/`。`/large/` 等の直接参照はゼロ（拡大表示は client script の文字列置換で到達する）。
- **旧基盤の元写真**: `photos.old.apkas.net/original/<dir>/<name>.(jpg|JPG)` が取得可能で EXIF が残る（2023〜2026年の各時期でサンプル確認済み）。`/medium/` `/large/` の WebP は EXIF 除去済み。旧 S3 には AWS SSO の `apkas` プロファイルで直接アクセスできる。
- **エントリの正は DynamoDB**。`export/` はビルド時に再生成されるミラーであり、読み取り元にしてはならない。本文の書き戻しは `putEntry()`（`src/lib/store/put.ts`）が唯一の経路で、`createdAt` の保存と GSI キーの整合を担う。
- staging に旧参照が59件あり、staging は独立した table / バケット / 配信ドメインを持つ。

## Goals / Non-Goals

**Goals:**

- 旧参照 2,365件のすべてを、EXIF 込みの目録記録と新基盤の配信に載せ替える。
- 編集画面の日記詳細で、**その日記が使っている写真が**一覧に出るようにする（日付キーの設計がこれを担保する）。
- 全工程を manifest を介した検証可能・冪等・再実行安全な形にする。

**Non-Goals:**

- 旧ホストの廃止・DNS 変更（別 change）。
- 本文の URL 以外の書き換え（HTML の整形、class の除去などは行わない）。
- photo-resize Lambda や表示側のコード変更。

## Decisions

### 決定1: 目録は直接書かず、既存の投入経路を通す

移行スクリプトは upload バケットへの PutObject までしか行わず、派生生成と目録記録は既存の Lambda に任せる。

- 理由: `photo-catalog` の要求「目録へ書けるのは投入と変換だけ」を守る。記録の形（EXIF 抽出、id 付与、renderedAt）が新規投入と機械的に同一になり、移行分だけ形が違うという状態を作らない。移行コードが持つ権限も S3 への書き込みだけで済む。
- 代替案: DynamoDB へ直接 BatchWrite する案は、記録の形の複製（Lambda 側ロジックの再実装）と書き込み主体の増加を招くため退けた。

### 決定2: 日付キーは「参照元エントリの日付」とする

sourceKey は `<参照元エントリの日付 Y/M/D>/<元ファイル名>.<拡張子>` とする。撮影日（ファイル名由来）ではない。

- 理由: 日記は時差を吸収した暦日で書かれており、編集画面の要求は「その日記が使っている写真が出ること」。目録の日付はエントリとの紐付け（`PHOTO#<date>`）そのものなので、参照元エントリの日付に合わせるのが要求に直結する。
- この規則が決定的であることは検証済み: 全2,365参照はユニークで各写真の参照元エントリは一意に定まり、同一エントリ内の basename 衝突も無い。フラット・階層の2形式も「エントリ日付 + basename」の一様な規則に畳める。
- 帰結: ディレクトリ月とファイル名日付が食い違う10件は、エントリの日付側に寄る。URL のパス日付と目録の日付は sourceKey から連動するため、常に整合する。

### 決定3: 元写真は3段階で探す（同期した旧バケット → 旧ホストの `/original/` → 旧ホストの `/large/`）

`apkas.admin` プロファイルで旧バケットの `original/` プレフィックスを手元に sync し、basename で manifest と突き合わせる。sync に無いものは旧ホストの `/original/` から拡張子を探索して取り、そこにも無いものだけ配信画像へ落とす。

- 理由: 実キーの一覧が手元にあれば拡張子を探索せずに済み、再実行も差分 sync で速い。一方で、**旧バケットへの到達は移行の前提にしない**。旧ホストの `/original/` が使えることは実測で確かめてあり（全期間から等間隔に抜いた60件すべてが取得でき、拡張子は `.jpg` 58 / `.JPG` 2）、認証情報が使えない状態でも移行そのものは進められる。前提を1つ減らせるなら減らす。
- 元写真が見つからない・デコードできない場合のみ、配信用 `/large/` WebP（3840px、EXIF 無し）を元写真として投入する。フォールバックしたことは manifest に記録し、件数を最終レポートに出す。`photo-catalog` は撮影情報の欠落した記録を許容している（MAY）ため、記録自体は成立する。
- 注意: photo-resize Lambda は HEIC をデコードできない。元写真に HEIC が現れた場合はフォールバック側に倒す。

### 決定4: manifest を工程間の唯一の受け渡しにする

棚卸しで `旧URL → エントリ日付 → sourceKey → 新URL → 元写真の取得元 → 状態` を1行とする manifest（JSON Lines）を生成し、取り込み・検証・書き換えはすべて manifest を入力にする。

- 理由: 各工程が冪等・再実行安全になる（取り込み済みはスキップ、検証失敗行だけ再投入、書き換えは検証済み行だけ対象）。何がどこまで進んだかが1ファイルで追える。
- 棚卸しは DynamoDB を読む（export/ ミラーは使わない）。生成時に、パターン逸脱・sourceKey 衝突・参照元エントリの非一意をエラーとして検出し、1件でもあれば先の工程に進めない。

### 決定5: 本文の書き換えは URL 文字列の完全一致置換とする

Markdown のパースはせず、manifest にある旧 URL を新 URL へ完全一致で置換する。

- 理由: 参照は Markdown `![]()` と raw HTML `<img src>` の2形で現れるが、どちらも URL は本文中に生の文字列として一度だけ現れる。URL はユニークかつ十分に長く、誤置換の余地が無い。migrate-legacy-diary の「本文は書かれたまま保持する」方針とも揃う（URL 以外の一字も変えない）。
- 書き換えは取り込みと検証が全件通ったあとにのみ実行する。書き戻しは `putEntry()` 経由。実行前に対象エントリの本文スナップショットを手元に保存し、逆置換スクリプトを用意して即時ロールバック可能にする（DynamoDB の PITR は最終手段）。

### 決定6: 目録未登録の新基盤写真は S3 自己コピーで再処理する

upload バケットの日付規約に合致するキーを列挙し、目録に記録が無いものを CopyObject（自己コピー、MetadataDirective=REPLACE）で再処理させる。

- 理由: 元写真が upload バケットに残っているため、ObjectCreated を再発火させるだけで EXIF 込みの記録が埋まる。既存の派生は同内容で上書きされるだけで表示に影響しない。
- 注意: この経路では medium が既存のため写真ごとに CloudFront invalidation が走る。対象は少数（目録機能導入以前の投入分のみ）なので無料枠に収まる。

### 決定7: 取り込みの並列度はスクリプト側で絞る

アップロードの並列度は4〜8とする。Lambda はイベント駆動で十分に並列に捌けるため、律速は手元の回線とし、2,345件でも1時間以内に収まる見込み。初回投入では medium が未存在のため CloudFront invalidation は発生しない設計になっている（コストゼロ）。

## Risks / Trade-offs

- [Lambda の目録書き込みは失敗しても throw しない設計で、投入成功＝記録成功ではない] → 検証工程で manifest 全行について、delivery バケットへの HeadObject（4サイズ）と目録レコードの存在・`renderedAt`・`exif` の有無を機械照合する。CDN 経由の HEAD は negative cache の影響を受けるため使わない。
- [書き換え後に表示が壊れる形の失敗がいちばん痛い] → 書き換えは全工程の最後に置き、staging（59件）で公開サイトの表示・拡大表示（medium→large 置換）・編集画面の一覧まで目視確認してから production に進む。スナップショット + 逆置換で即時に戻せる。
- [元写真の欠落・デコード不能（HEIC 等）] → フォールバック（/large/ WebP）で記録は成立させ、EXIF 欠落として manifest に残す。件数が多い場合（例: 1割超）は一旦停止して原因を見る。
- [書き換え実行中の同時編集で上書き競合] → 書き手は一人なので、書き換えは編集を止めて一気に実行する。実行直前に棚卸しを再実行し、本文が変わっていないことを確認してから置換する。
- [旧バケットの構成が想定と違う（original の欠け方が偏っている等）] → 最初に sync して突き合わせ結果を見るまで取り込みを始めない。棚卸しレポートで充足率を先に確定させる。

## Migration Plan

1. **staging リハーサル**: 棚卸し → 取り込み → 検証 → 書き換え → 表示確認までを staging で通す。
2. **production 棚卸し**: manifest 生成、旧 S3 sync、充足率レポート。エラーゼロを確認。
3. **production 取り込み + 検証**: この時点では本文は旧 URL のままなので、失敗してもユーザー影響はゼロ。何度でもやり直せる。
4. **production 書き換え**: スナップショット取得 → 置換 → `putEntry()` 書き戻し → サイト再ビルド・デプロイ。
5. **系統2の再処理**: upload バケットと目録の差分を自己コピーで解消。
6. **README 更新・後片付け**: 目録の適用範囲の記述を更新。手元の sync データと manifest は保管する。

ロールバック: 書き換え前スナップショットからの逆置換（書き換え工程のみが不可逆性を持つ。それ以外の工程は追記のみで、旧基盤にも一切書き込まないため、いつでも中断・破棄できる）。

## Open Questions

- 旧 S3 のバケット名と `original/` プレフィックスの正確な構成（`apkas.admin` プロファイルで `aws s3 ls` すれば分かる。旧ホストの `/original/` が使えることを確かめたため、これは速さのための選択肢であって前提ではない）。
- 系統2の正確な件数（upload バケットと目録の差分を取れば確定する。少数であることは分かっている）。
