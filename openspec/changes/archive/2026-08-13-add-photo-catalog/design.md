## Context

動機は proposal.md の Why を参照。ここでは方式の選定に効く現状だけを挙げる。

- 写真の経路は「アップロード用バケットへ置く → S3 の `ObjectCreated:*` で変換 Lambda が起動 → 配信用バケットへ4つの派生画像を書く → CloudFront が配る」の一本道。**投入と生成は同期しない。**
- 元写真のキーと配信 URL の規約は `src/lib/photo.ts` が持つ。キーは `YYYY/MM/DD/<ファイル名>`、URL はサイズ名を先頭に置いて拡張子を `.webp` に替えたもの。**同じ規約を `lambda/photo-resize/src/index.ts` も二重に持っている**（パッケージが分かれているため共有していない）。
- 投入の入口は手元の CLI（`src/cli/put-photo.ts`）とブラウザ（`editor/src/pages/photos/new.astro` → `uploaded.astro`）の2つ。どちらも `photoSourceKeyOf` を通るので置き場所は1つの規則で決まる。CLI にはこれとは別に、キーを直接指定する `--key` がある。
- DynamoDB は単一テーブル。エントリは `pk = ENTRY#<年>` / `sk = <YYYY-MM-DD>`、公開分だけが `gsi1pk = ENTRY` を持つ sparse index に載る。`scanAllIncludingDrafts` は **`type = 'entry'` を条件に走査**しており、**別の種類のアイテムが同居する前提で既に書かれている。**
- 書き込みは `src/lib/store/put.ts` の `putEntry` に集約されている。`PutCommand`（アイテム全体の置換）で、GSI キー属性の付け外しと作成日時の引き継ぎをここだけが知る。
- 変換 Lambda の実行ロールが持つのは S3 と CloudFront と CloudWatch Logs だけで、**DynamoDB の権限はいっさい無い。**
- 変換 Lambda は EXIF を「消して」いない。sharp が明示しない限り入力の付随情報を出力へ運ばないため、**書かないことがそのまま除去になっている。**
- 編集アプリケーションの画面はすべてサーバ描画のフォームで、client script は写真の投入の1箇所だけ。進行中の状態は `<meta http-equiv="refresh">`（`Base.astro` の `refreshSeconds`）で追う。
- `DIARY_TABLE_NAME` は `config/<環境>.env` に既にあり、`load_env` が export する。**CLI から目録を書くために新しい転記は要らない。**

## Goals / Non-Goals

**Goals:**

- 記録の書き手が2つ（投入と変換）になっても、**どちらが先に走っても最終的な記録が同じ**になる。生成が投入と同期しない以上、順序は選べない。
- 目録が配信の正にならない。目録の側の失敗が、写真が見られないという形で現れない。
- **日記の本文に触れられる主体を増やさない。** 変換 Lambda に DynamoDB の権限を渡すが、届く範囲は写真の記録までとする。
- 転記を増やさない。設定は既にある出どころから引く。
- 編集アプリケーションに client script を増やさない。写真の一覧はサーバ描画で足りる。

**Non-Goals:**

- 目録から派生画像を作り直す手順。元写真は保管されているので原理的には可能だが、今回は入口を作らない。
- 目録の全件一覧・検索・機材での絞り込みの画面。今回置くのは日付から引く経路だけとする。
- 記録の削除。写真そのものを消す経路を作らないのと同じ扱いにする。
- 目録の内容を公開サイトの生成の入力にすること。今回は書き込み側だけを作る。

## Decisions

### 決定1: 目録は日記と同じテーブルに置く

検討した案:

| 案 | 内容 | 判断 |
| --- | --- | --- |
| **A. 同じテーブルに別の種類のアイテムとして置く** | `pk = PHOTO#<YYYY-MM-DD>` / `sk = <ファイル名>` | **採用** |
| B. 写真専用のテーブルを新設する | 変換 Lambda にはそちらだけを渡す | 却下 |

B の利点ははっきりしている。変換 Lambda が日記のテーブルに触れないことが、権限の条件ではなく**入れ物の分離**として担保される。写真の記録は元写真から作り直せる（元写真は versioning 付きで保管されている）ので、再取得不可能な日記と同じ保護の下に置く必然性もない。

それでも A を採るのは、`scanAllIncludingDrafts` の `type = 'entry'` という条件が**既にこの同居を前提として書かれている**ためである。テーブルを分けると、この条件は意味を失ったまま残る。加えて、写真とエントリはどちらも日付を軸に並ぶものであり、同じ日を指す2つのアイテムが2つのテーブルに分かれる形は、あとから見て理由が読み取りにくい。復旧（PITR）の設定が1つで済むことも小さくない。

B の利点である「日記に触れられない」は、決定7 の権限の条件で満たす。**入れ物ではなく権限で担保する**のは、配信用バケットへ書けるのが変換 Lambda だけであること（`photo-ingest`）と同じ形である。

キーの設計:

```
pk = "PHOTO#<YYYY-MM-DD>"   日付でパーティションを切る（1日あたり数枚〜数十枚）
sk = "<ファイル名>"          日内でファイル名順に並ぶ
```

`sk` をファイル名にすると、**同じ元写真のキーへの再投入が同じアイテムへの書き込みになる**。これは「同じキーへの再投入は派生画像を作り直す」（`photo-ingest`）とそのまま対応する。並びがファイル名順になるのは、カメラの連番がそのまま撮影順になるためで、`photo-catalog` の「並びの安定」を索引の側が満たす。

`gsi1pk` / `gsi1sk` は書かない。GSI1 は sparse index なので、書かなければ写真は索引に載らず、公開サイトの生成の入力（`listAllPublished`）は何も変わらない。

### 決定2: 識別子は属性として持ち、キーにはしない

`id` は `crypto.randomUUID()` で発行し、アイテムの属性として持つ。プライマリキーには使わない。

キーにしない理由は、**同じ元写真のキーへの再投入で2件目が生まれてしまう**ためである。識別子をキーに据えると、再投入のたびに新しいアイテムができ、どれが今配信されているものかが目録から分からなくなる。アイテムの同一性は「どこに置かれた写真か」で決まるべきで、それは元写真のキーである。

識別子を別に持つ意味は、**置き場所や URL の規約が将来変わっても写真を指し続けられる**ことにある。いまは目録の外から `id` で引く経路が無いため索引も作らない。必要になった時点で GSI を足せる（DynamoDB は既存テーブルへの GSI 追加を許す）。

ULID などの時系列で並ぶ識別子は採らない。並べる軸は既に日付とファイル名で足りており、依存を1つ増やすだけの理由がない。`crypto.randomUUID()` は Node 22 の標準にあり、**投入側と変換側の両方で追加の依存なしに同じものが使える。**

### 決定3: 2つの書き手は、それぞれ自分の持ち分だけを書く

記録の属性は書き手によって分かれる。

| 属性 | 書く側 |
| --- | --- |
| `id` / `date` / `filename` / `sourceKey` / `url` / `createdAt` | 投入（CLI・編集アプリケーション） |
| `exif` / `width` / `height` / `renderedAt` | 変換（Lambda） |
| `type` / `updatedAt` | 双方 |

書き込みは `PutItem` ではなく **`UpdateItem` で自分の持ち分だけを `SET` する**。`putEntry` が `PutItem`（全体置換）なのと逆になるが、エントリの書き手は1つ、写真の書き手は2つという違いによる。全体置換にすると、投入側の書き込みが変換側の書いた `exif` を消す——しかも消えるのは**あとから書き直せない情報**である。元写真が残っているので原理的には作り直せるが、そのための手順は今回作らない（Non-Goals）。

### 決定4: 先に走ったほうが識別子を決める

生成は投入と同期しないため、**変換 Lambda が投入側より先に記録を作ることがありうる**。ブラウザからの投入では、元写真が S3 に置かれてから利用者が結果の画面に到達するまでのあいだに、変換が終わっていることは普通に起きる。

そのため変換側も識別子を発行できるようにし、双方が次の形で書く。

```
SET id = if_not_exists(id, :id), createdAt = if_not_exists(createdAt, :now), ...
```

`if_not_exists` は書き込みの時点でアイテムを見て評価されるので、**2つの主体が別々に発行した識別子のうち、先に書いたほうが残る。** あとから書いたほうは自分の発行したものを捨てる。どちらが先でも最終的な記録は同じになり、識別子は一度決まったら変わらない（`photo-catalog` の「写真は変わらない識別子を持つ」）。

代替として「変換側は既存のアイテムがあるときだけ書く」（`ConditionExpression: attribute_exists(pk)`）も考えたが、これは順序によって `exif` が欠けた記録が残る。**順序が結果を変えない**ほうを採る。

### 決定5: 保持する URL は1つ。4つ持たない

`url` には `medium` の配信 URL を入れる。4つのサイズをすべて持つことはしない。

`photo-delivery` が「サイズ名を差し替えれば同じ写真の別のサイズが得られる」を要件として持っているため、**1つあれば残りは問い合わせなしに導ける。** 4つ持つと、同じ事実が4箇所に書かれ、配信ドメインが変わったときに直す対象が4倍になる。

`medium` を選ぶのは、それが本文に貼る既定のサイズだからである（`entry-editing`）。記録を読んだ側が、いちばんよく使う形をそのまま得られる。

`sourceKey` も持つ。URL からは拡張子が `.webp` に替わったあとの形しか分からず、**投入し直すべき対象を特定できない。**

### 決定6: EXIF は取り出す項目を列挙して選ぶ

sharp の `metadata()` が返す `exif` は生のバッファであり、解釈には `exif-reader` を足す（sharp が想定している組み合わせ）。変換 Lambda の依存に1つ加わる。

**取り出す項目は列挙して選ぶ。** 読み取った全体を保存して、あとから位置情報を除く形にはしない。

```
Make / Model / LensModel / FocalLength / FNumber / ExposureTime / ISO / DateTimeOriginal
```

除外する形にしないのは、`photo-catalog` の「位置情報は記録されない」を、**除外の条件が正しいことに依存させない**ためである。列挙して選べば、書き忘れは「項目が足りない」として現れる。除外する形だと、書き忘れは「位置情報が入っている」として現れる。**失敗が安全な側に倒れるほうを採る**——これは変換 Lambda が付随情報を「消す処理を足す」のではなく「引き継ぐ指定を書かない」ことで除去しているのと同じ判断である。

寸法（`width` / `height`）は `rotate()` を適用したあとの値を取る。付随情報に記録された回転は既に画素へ反映されているため、**目録の寸法と配信される画像の向きが食い違わない。**

読み取りは `try` で囲み、失敗しても記録そのものは作る。`photo-catalog` の「情報が欠けていることを理由に、記録そのものを作らないでいてはならない」に対応する。

### 決定7: 変換 Lambda の権限は `PHOTO#` の下だけに限る

変換 Lambda の実行ロールに与えるのは、対象テーブルへの `dynamodb:UpdateItem` ひとつだけ。さらに条件を付ける。

```hcl
condition {
  test     = "ForAllValues:StringLike"
  variable = "dynamodb:LeadingKeys"
  values   = ["PHOTO#*"]
}
```

`dynamodb:LeadingKeys` はその要求が触れるパーティションキーを見る条件キーで、これにより**エントリ（`ENTRY#<年>`）へは届かない。** `GetItem` も `Query` も `PutItem` も `DeleteItem` も与えないので、読むことも消すこともできない。

日記はこのシステムでいちばん失いたくないものであり、写真の記録を足すという理由でそこへ触れる主体を増やさない。`photo-catalog` の「目録へ書けるのは投入と変換だけ」と「変換はエントリを読み書きできない」は、この1つのポリシーで満たされる。

**条件が実際に効いていることは staging で確かめる**（tasks）。IAM の条件は書けてしまうが効かない形があり、書いたことをもって担保としない。

編集アプリケーション側には2つ足す。既に持っているのは `GetItem` / `PutItem` / `Scan` の3つで、**`Query` も `UpdateItem` も入っていなかった**——一覧が走査で足り、エントリの書き込みが `PutItem` だけだったためである。

- `dynamodb:Query`（条件なし）: 記事の編集画面がその日の写真を `pk = PHOTO#<日付>` で引く。**条件は付けない。** 編集アプリケーションは `Scan` で同じテーブルを丸ごと読める——エントリを読むのが仕事なので当然である——から、読み取りの片方だけを絞っても境界にならない。
- `dynamodb:UpdateItem`（`LeadingKeys` を `PHOTO#*` に限る）: 投入を終えた画面が目録に記録する。**こちらは絞る。** エントリへの書き込みを `putEntry` の `PutItem` 1本のままにしておくためで、アイテム全体を組み立て直す経路しか無ければ、GSI キー属性の付け外し（`toItem` が一手に持っている）を飛ばした半端な更新が生まれない。

同じ `LeadingKeys` でも変換 Lambda とは狙いが違う。あちらは**日記に届かないこと**そのものが要件で、こちらは**日記への書き方を1つに保つ**ためである。

**`DeleteItem` と `BatchWriteItem` を持たないことは変わらない。** 目録から記録を消す経路は編集アプリケーションにも生まれない。

### 決定8: 生成の完了の判定は S3 のまま。`renderedAt` は表示にだけ使う

目録に `renderedAt` を持つが、**投入直後の待ち画面の判定は今までどおり配信用バケットの `HeadObject` で行う。**

判定を目録に移すと、変換 Lambda が DynamoDB に書けなかったときに「派生画像はあるのに、いつまでも準備中と表示される」状態が生まれる。`photo-catalog` の「目録は配信の正ではない」はここに効く。**配信できるかどうかを決めるのは、派生画像が配信先に在ることだけである。**

`renderedAt` を使うのは記事編集画面の一覧（`entry-editing`）で、ここでは「まだ生成されていない写真を、生成済みとして見せない」ために読む。判定の根拠が2つに分かれるが、両者は用途が違う。待ち画面は「**この投入で**作られたか」（署名時刻との比較が要る）、一覧は「**そもそも**作られたか」を見ている。

一覧のほうで `renderedAt` を使うのは、写真1枚ごとに S3 へ問い合わせると、10枚並ぶ日の編集画面が10回の `HeadObject` を待つことになるためである。目録は1回の `Query` で済む。

### 決定9: ブラウザからの登録は結果画面の描画で行う

編集アプリケーションが目録に書くのは `/photos/uploaded` の描画時とする。元写真はブラウザから S3 へ直接送られるため、**編集アプリケーションがキーを知るのはここが最初**である（S3 の応答が返したキーをブラウザが持ってくる）。

この画面は生成を待つあいだ3秒ごとに読み直されるので、書き込みは**何度実行しても同じ結果になる形**でなければならない。決定3・決定4 の `UpdateItem` + `if_not_exists` がそのまま満たす。

登録のためだけの API を別に置くことはしない。画面が既に受け取っているものを、もう一度別の経路で送り直す形になる。

### 決定10: 記事編集画面の写真一覧はサーバ描画

`editor/src/pages/entries/[date].astro` の描画時に、その日の写真を1回の `Query` で引いて並べる。一覧そのものに client script は要らない（記述を写す操作だけは後から足した——決定13）。

並べるのは投入直後の結果画面（`uploaded.astro`）と**同じ形の要素**——サムネイル・貼れる記述・各サイズの URL——にする。`entry-editing` の「投入直後との一致」は、見せ方を揃えることで満たす。

写真の一覧はフォームの外に置く。一覧はどれも読み取り専用の要素であり、**編集中のタイトルと本文に触れない。** 保存を伴う操作にもならないので、`entry-editing` の「写真の提示は編集中の内容を失わせない」は構造として満たされる。

生成がまだの写真は、投入直後の画面と同じく**画像を出さない**。まだ無いあいだの要求が CDN に 403 として載り、自分の確認が原因でしばらく読めなくなることを避ける。

### 決定11: 目録の型と読み書きは `src/lib/store/photo.ts` に置く。Lambda は二重に持つ

CLI と編集アプリケーションは `src/lib/store/photo.ts` を共有する。`putEntry` が書き込みの経路を1つに集約しているのと同じ形にする。

変換 Lambda はこれを共有できない。パッケージが独立しており（sharp の native binary をサイト生成の依存に混ぜないため）、`src/lib` を跨いで import しない構成になっている。**キーと URL の規約が既に二重になっているのと同じ扱いとし、どちらかを変えるときは両方を直す。** 二重に持つ範囲は、アイテムのキーの組み立てと属性の名前に限る。

### 決定13: 貼れる記述の複製のために client script を1つ増やす

**決定10 で「client script は増やさない」と書いたが、これは増やす。** 一覧そのものはサーバ描画のままで、足すのは記述を写す操作だけである。

クリップボードへの複製はブラウザでしか行えず、サーバ描画では代われない。1枚貼るたびに記述を選択し直す手数は、写真が数枚ある日には毎回かかる。

置き場所は `editor/src/components/CopyField.astro` の1つにする。投入を終えた画面と記事の編集画面の双方が使うので、**部品を1つにすることで「双方が同じものを示す」（`entry-editing`）を写しではなく構造で満たす。** Astro は同じ部品を何度使ってもスクリプトを1度しか読み込まないため、写真が並んでも増えるのは要素だけである。

**入力欄は残す。** `navigator.clipboard` は安全な文脈でしか存在せず、スクリプトが読み込まれていないこともある。そのとき記述が画面から消えていると、**手数を減らすための追加が、貼れる記述を得る手段そのものを壊す**ことになる。複製が働かないときは選択だけ行い、何も起きないまま終わらせない。

### 決定12: 設定は既にある出どころから引く

- CLI: `DIARY_TABLE_NAME` は `config/<環境>.env` に既にある。`scripts/photo.sh` の `require_env_vars` に足すだけで、**転記は増えない。**
- 編集アプリケーション: 既に `DIARY_TABLE_NAME` を読んでいる。何も足さない。
- 変換 Lambda: `lambda/photo-resize/function.jsonnet` に `DIARY_TABLE_NAME` を足し、値は tfstate（`module.storage.aws_dynamodb_table.diary.name`）から引く。写真の module がテーブルを知る必要が出るため、root module から `table_name` / `table_arn` を渡す。

## Risks / Trade-offs

- **変換 Lambda の DynamoDB 書き込みが失敗する** → 生成そのものは止めない（`photo-ingest` の要件）。失敗はログに残り、同じ元写真を投入し直せば記録は揃う。写真が見られなくなることはない。
- **`dynamodb:LeadingKeys` の条件が期待どおり効かない** → 書けたことをもって担保としない。staging で、変換 Lambda の資格でエントリの読み書きが実際に拒否されることを確かめてから production へ進む。
- **`scanAllIncludingDrafts` の読み取り量が写真のぶんだけ増える** → 走査は写真のアイテムも辿ったうえで種類で落とすため、消費する容量は増える。この経路を使うのは編集アプリケーションの一覧と書き出しの2つで、**公開サイトの生成には現れない**（`diary-entry-store` の「索引を用いるエントリの取得は他の種類のものに影響されない」）。写真1枚あたりのアイテムは小さく、支払い方式は要求ごとの従量である。増分を受け入れる。
- **同じ日に同じファイル名の別の写真を入れると上書きになる** → S3 の側で既にそうなっており（同じキーへの投入は差し替え）、目録がそれを写しているだけである。元写真は versioning で戻せる。
- **`exif-reader` の解釈が写真によって揺れる** → 項目が欠けるだけで、記録は作られる。表示する側が欠落を前提に書く必要があるが、公開サイトへの表示は今回のスコープに含めない。
- **記録と配信が食い違う** → 目録は写しであり、正は S3 にある（決定8）。食い違ったときに信じるのは配信のほう、という順序を決めてある。
- **過去に投入した写真が目録に無い** → 意図した状態（proposal の非目標）。既存の記事は本文の URL で表示されており、目録の有無は表示に影響しない。編集画面の一覧には過去の写真が並ばないが、それらは既に本文に貼られている。

## Migration Plan

過去の写真を遡って登録することはしない。テーブルの定義（キースキーマ・GSI1）は変えないため、既存のアイテムへの移行操作も無い。

適用の順序:

1. `terraform apply`（staging）— 変換 Lambda の IAM ポリシーに DynamoDB を足し、root module からテーブルを渡す。
2. `npm run deploy:lambda -- staging` — 変換 Lambda を差し替える。`function.jsonnet` に環境変数が増える。
3. `npm run deploy:editor -- staging` — 編集アプリケーションを差し替える。
4. staging で確認（tasks の検証）ののち、同じ順で production。

**順序がずれても壊れない。** 1 と 2 のあいだに写真を投入すると、変換 Lambda は権限が無くて記録を書けないが、派生画像の生成は成功する（`photo-ingest` の要件）。2 と 3 のあいだに投入すると、記録は `exif` の側だけが埋まる。いずれも、あとから同じ元写真を投入し直せば揃う。

戻すとき: 編集アプリケーションと変換 Lambda を前の版に戻せば、書き込みは止まる。**既に書かれた写真のアイテムを消す必要はない。** エントリの読み取りは `type = 'entry'` で絞られており、写真のアイテムがテーブルに残っていても公開サイトの生成にも書き出しにも現れない。
