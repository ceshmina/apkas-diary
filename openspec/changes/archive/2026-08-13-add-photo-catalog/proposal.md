## Why

写真はこれまで**置いた場所しか知られていない**。S3 のキーと、そこから機械的に決まる4つの URL がすべてで、「その写真がいつ・何で撮られたか」も「どの日記に使ったか」も、システムのどこにも残っていない。投入した直後の画面を閉じると、貼れる記述を得る手段は URL を組み立て直すことだけになる。

そのため、投入から少しでも時間が空いた写真は扱えない。**書きかけの記事に、昨日入れた写真をもう1枚足す**ができない。撮影機材を日記に添えることもできない。EXIF は配信物から除去されるが（`photo-ingest`）、それは公開してよい形に整えるためであって、情報そのものを捨てたいわけではない。除去の前に読み取っておけば、公開物を汚さないまま日記の側で使える。

投入の入口はブラウザにも広がり、写真は文章と同じ場所から入れられるようになった。**足りていないのは、入れたあとの写真をシステムが覚えていることである。**

## What Changes

- 写真1枚ごとの記録を保持する**目録**を設ける。投入された写真には識別子（ID）が発行され、配信 URL・投入日・元写真のキーとともに、日記と同じデータストアに登録される。
- 目録への登録は**投入の経路によらない**。手元の CLI からでもブラウザからでも、投入すれば記録される。人が登録する操作は持たない。
- 変換 Lambda が、派生画像を作る過程で**元写真の EXIF から撮影に関する情報を読み取り、目録に書き足す**。機材・レンズ・撮影条件・撮影日時が対象。**位置情報は読み取らない**（非目標を参照）。あわせて元写真の寸法と、派生画像が出来たことも記録する。
- 写真は**日付によって日記のエントリに紐づく**。写真のキーが既に日付から決まっており、エントリも日付で一意であるため、紐付けのための新しい入力は要らない。
- 記事の編集画面に、**その日に投入した写真の一覧**を置く。サムネイル・本文に貼れる記述・4つのサイズの URL が、投入した直後の画面と同じ形で、いつでも得られる。
- 目録に書けるのは**投入の経路と変換の処理だけ**にする。日記のエントリを書き換える権限と、写真の記録を書き換える権限を、同じ経路の上で混ぜない。

明示的に含めないもの（非目標）:

- **過去に投入した写真の遡っての目録化**。既存の記事は本文に書かれた URL で写真を表示しており、目録が無くても表示は変わらない。再配置も行わない。
- **公開サイトへのカメラ名などの表示**。今回は目録に貯めるところまでとする。表示は、データが溜まってから別の変更で決める。
- **位置情報（GPS）の保存**。日記に使う用途がなく、**保存しなければ公開側へ漏れる経路が最初から存在しない**。除去の担保を、保存したうえでの取り扱いの正しさに置き換えない。
- **写真の削除・非表示、および紐付けの付け外し**。エントリに削除の操作を持たないのと同じ理由による。写真をどの記事で使うかは本文が決める。
- **本文への自動挿入**。画面が示すのは貼れる形までとする（`entry-editing` の既存の判断を引き継ぐ）。
- **元写真のキーの規約の変更**。ID は目録の中の識別子であり、配信 URL の組み立て（`photo-delivery`）には影響しない。

## Capabilities

### New Capabilities

- `photo-catalog`: 投入された写真1枚ごとの記録を保持する。識別子の発行、配信 URL と元写真のキーの保持、撮影に関する情報の保持、日記のエントリとの紐付け、そして日付からの引き当て。**目録は配信の正ではなく、配信されているものの写しである**という位置づけを含む。

### Modified Capabilities

- `photo-ingest`: 投入が目録への登録を伴うこと、変換が撮影に関する情報の読み取りを伴うこと、位置情報を読み取らないこと、および目録への記録の失敗が派生画像の生成を妨げないことを足す。派生画像の生成・サイズ・形式・付随情報の除去は変えない。
- `entry-editing`: 編集中のエントリについて、その日に投入した写真を投入の直後でなくても得られること、そこから本文に貼れる記述と各サイズの URL が得られることを足す。
- `diary-entry-store`: エントリ以外の種類のアイテムが同じデータストアに存在しても、エントリの読み取り結果に現れないことを足す。写真の記録を同じストアに置く以上、公開サイトの生成と書き出しがそれを拾わないことを要件として言い切っておく。

## Impact

- **データストア**: 既存のテーブルに写真の記録を追加する。テーブルそのものと GSI1（公開エントリの索引）の定義は変えない。写真の記録は GSI1 のキー属性を持たないため索引に載らず、公開サイトの生成の入力は変わらない。
- **変換 Lambda**: EXIF の読み取りと目録への書き込みを足す。EXIF の解釈に依存を1つ加える。自環境のテーブルの**写真の記録だけ**を書ける権限を与える（エントリは書けない）。
- **編集アプリケーション**: 投入の完了時に目録へ登録する経路と、記事の編集画面に写真の一覧を足す。既存の投入・完了確認の画面の作りは変えない。
- **CLI**: `npm run photo` に目録への登録を足す。実行にテーブル名の設定が必要になる。
- **Terraform**: 写真の module がテーブルを知る必要があるため、root module からの受け渡しを増やす。編集アプリケーションの権限には `dynamodb:Query`（その日の写真を引く）と、`PHOTO#` の下に限った `dynamodb:UpdateItem`（目録に記録する）が増える。既に持っているのは `GetItem` / `PutItem` / `Scan` の3つだけだった。削除にあたる権限は引き続き与えない。
- **共有コード**: 写真の記録の型と読み書きを `src/lib/` に置き、CLI・編集アプリケーション・Lambda が同じ規約を通るようにする。ただし Lambda はパッケージが分かれているため、キーの規約と同じく**二重に持ち、変えるときは両方を直す**扱いになる。
- **README**: 写真の目録と、記事編集画面からの写真の扱いを追記する。
