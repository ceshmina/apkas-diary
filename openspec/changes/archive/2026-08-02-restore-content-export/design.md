## Context

`astro.config.ts` は `exportEntries()` を `astro:build:done` フックから呼び、`{ dir, written, removed }` を受け取ってログに出す。この呼び出し側は残っているため、復元するのは呼ばれる側の1モジュールだけでよい。取得経路も既にある（`scanAllIncludingDrafts()`。下書きを含む全件を日付の昇順で返す）。

制約は `content-export`（`openspec/specs/content-export/spec.md`）の5つの要件に尽きる。とくに効いてくるのは「書き出しは冪等である」で、同じデータからは常に同じファイル群が出なければならず、1件だけ更新したときに他のファイルが変化してはならない。

失われた実装がどの形式だったかは復元できない。git の履歴・stash・書き出し先のいずれにも残っていないため、形式は改めて決める。

動機は proposal.md - Why を参照。

## Goals / Non-Goals

**Goals:**

- clone した状態で `astro` を呼ぶコマンドが通ること。
- `content-export` の5要件を実装が満たすこと。
- 10年後にこのアプリケーションを失っていても、書き出したファイルだけで日記が読めること。
- 書き出したファイルから DynamoDB のアイテムを機械的に組み立て直せること。復元の手順そのものは実装しないが、形式がそれを妨げないこと。

**Non-Goals:**

- 新しい依存を足さないこと。YAML ライブラリを入れない（決定3）。
- 書き出しの高速化。1日1件なら10年で3600ファイルであり、全件書き直しても問題にならない規模である。

## Decisions

### 1. YAML frontmatter に属性を置き、その下に本文をそのまま置く

```
---
date: 2026-08-02
status: published
title: "hr の確認"
createdAt: 2026-08-02T01:00:00.000Z
updatedAt: 2026-08-02T01:30:00.000Z
---

一段落目のテキスト。

---

二段落目のテキスト。
```

「エディタで開くだけで日付・タイトル・公開状態・本文が読める」という要件と、「復元時に機械的にパースできる」という目標を同時に満たす形はこれしかない。frontmatter は Markdown を扱う道具のあいだで事実上の標準であり、10年後に読み手が現れたときに説明を要さない。

本文中の `---`（`hr`）とは衝突しない。frontmatter は先頭の `---` から次の `---` までを見る規則であり、本文がどこで `---` を使っても解釈は変わらない。本文が `---` で始まる場合も、frontmatter の終端の次の行以降は本文として扱われるため問題にならない。

| 選択肢 | 評価 |
| --- | --- |
| **YAML frontmatter + 本文** | **採用**。人にも機械にも読める |
| 見出しとして書く（`# タイトル` + 本文） | 人には自然だが、`status` の置き場所が本文と区別できず、復元時のパースがヒューリスティックになる |
| JSON | 本文が1行のエスケープされた文字列になり、「エディタで開くだけで本文が読める」を満たさない |

`createdAt` / `updatedAt` も含める。これらはエントリに属する値であってビルド時刻ではないため、冪等性を損なわない。落とすと、復元したときに作成・更新時刻が失われる。

属性の並びは上記の順に固定する。並びが実行ごとに変われば、内容が同じでも差分が出る。

### 2. `<書き出し先>/<年>/<YYYY-MM-DD>.md`

日付から一意に定まり、1エントリ1ファイルという要件をそのまま満たす。年でディレクトリを切ると1ディレクトリは最大366ファイルに収まり、サイトの URL 構造とも階層の切り方が揃う。

フラットに並べる案は、10年で1ディレクトリ3600ファイルになる。年月まで切る案は1ディレクトリ最大31ファイルになるが、手で辿るときの階層が深く、得るものが少ない。

ファイル名に年を含める冗長さは残すが、ファイルを1つだけ取り出して別の場所に置いたときに日付が分かる利点を取る。

### 3. YAML ライブラリを使わず、書く側だけを自前で持つ

書き出す属性は5つで、うち4つ（`date` / `status` / `createdAt` / `updatedAt`）は形式が決まっており、素のスカラーとして安全に書ける。

`title` だけが任意の文字列であり、`: ` を含む、`#` で始まる、引用符で始まる、改行を含む、といった場合に素で書くと壊れる。これは **常に JSON の文字列リテラルとして書く** ことで解決する。YAML 1.2 は JSON のスーパーセットであり、`JSON.stringify()` の出力はそのまま妥当な YAML の二重引用符スカラーになる。エスケープの規則を自分で考える必要がない。

読む側は標準的な YAML パーサで読める。つまり依存を足さずに書けて、読むときには既存の道具が使える。

### 4. 内容が同じでも毎回書く

冪等性の要件は「ファイル群として同一であること」であり、mtime には及ばない。既存ファイルを読んで比較してから書くかどうかを決める最適化は、この規模では複雑さに見合わない。

ただし内容の生成は完全に決定的にする。ビルド時刻・実行順・ロケール・タイムゾーンに依存する値を一切含めない。`date` は文字列のまま扱い、`Date` を経由しない（`setup-diary-foundation` design.md 決定11 と同じ理由）。

`written` は書き出したエントリ数を返す。

### 5. 削除は、書き出しの命名規則に一致するファイルだけを対象にする

DynamoDB 側で消えたエントリのファイルが書き出し先に残り続けると、「異なる時点の書き出し結果を比較すると、その間の追加・更新・削除だけが差分として現れる」という要件を満たさない。

一方で、書き出し先を丸ごと消して作り直す方式は採らない。`DIARY_EXPORT_DIR` は環境変数で上書きでき、誤って別のディレクトリを指した状態で走らせたときの被害が大きすぎる。

対象を `<年>/<YYYY-MM-DD>.md` の形に一致するファイルに限る。この形に一致しないファイルやディレクトリは、書き出し先の中にあっても触らない。空になった年のディレクトリは削除する（同じデータからは常に同じツリーになるようにするため）。

`removed` は削除したファイル数を返す。

### 6. 失敗はそのまま投げる

例外を握りつぶさない。`astro.config.ts` のフックは戻り値を待つだけで、投げられた例外はビルドの失敗として伝播する。「書き出しの失敗はサイト生成の失敗として扱う」という要件は、追加の仕掛けなしにこれで満たされる。

基底ディレクトリはエントリが0件でも作る。書き出しが走って対象がなかったのか、書き出しが走らなかったのかを跡から区別できるようにするためで、`setup-diary-foundation` の時点でそう決めてある。

### 7. `.gitignore` は `/export/` に限定する

先頭のスラッシュを付けると、リポジトリ直下の `export/` だけに一致する。今回ファイルを失った原因そのものであり、同じことが `src/export/` 以外の場所でも起きうる。

同じ理由で危ういパターンが他にないか確認する。`dist/`・`node_modules/`・`.astro/` は同名のディレクトリがどこに現れても除外したいものなので、そのままでよい。

## Risks / Trade-offs

- **書き出し先を消してから走らせると、削除の検知ができない** → 削除は「書き出し先に残っているファイル」と「今回のエントリ」の差として求めるため、書き出し先ごと消えていれば全件が新規作成になるだけで、壊れはしない。今回の初回実行はまさにこの状態になる。
- **`title` を JSON クォートで書くため、日本語のタイトルも常に引用符で囲まれる** → 読みやすさはわずかに落ちるが、エスケープ規則を自前で持つより安全である。引用符の中身はエスケープされないかぎりそのままの日本語で読める。
- **本文の末尾に改行を足さない** → ファイルによっては末尾に改行がない状態になる。本文をバイト単位でそのまま保つほうがバックアップとして正しいと判断した。
- **形式が以前の実装と違う可能性がある** → 以前の書き出し結果は存在しないため、突き合わせる対象がない。移行の問題は起きない。
