## Context

動機は [proposal.md](proposal.md) の Why にある。要件は [specs/visual-identity/spec.md](specs/visual-identity/spec.md)。見た目の基準は同じディレクトリの [mockup.html](mockup.html) の「B′ 採用案」タブで、以下で挙げる値は、この見本の値を実装へ移すことを前提にしている（見本には比較した3案と、本文書体・題の明朝の比較も残してある）。

現状の構造と、この変更に効いてくる制約は次のとおり。

- **基準値の出どころは既に1つある。** `src/styles/tokens.css`（色と寸法）と `src/styles/base.css`（字送りと本文要素）を、公開サイトと編集アプリケーションが共に import している。この構造は変えない。
- **書体を読み込む仕組みがない。** いまは OS の明朝とゴシックに任せている。
- **Astro 7.1 には Fonts API が含まれている。** `astro.config` の `fonts` と `<Font>` で、ビルド時に書体を取得し、`/_astro/fonts/` から配る。取得元は Google Fonts などのプロバイダから選ぶ。
- **Google Fonts の和文書体は、1つの太さが約120の断片に分かれている**（unicode-range による分割）。ブラウザはページに現れる文字を含む断片だけを読む。断片の CSS には subset の注記が付かないため、Fonts API の `subsets`（既定は `latin`）では絞られず、すべて取り込まれる（`unifont` の実装で確認した）。
- **実測した書体の大きさ**（Google Fonts の woff2）:

  | 書体 | 断片の数 | 合計 |
  | --- | --- | --- |
  | Zen角ゴシック New（1つの太さ） | 121 | 1.34 MB |
  | Zen Old Mincho（1つの太さ） | 122 | 2.65 MB |
  | Instrument Serif（normal / italic） | 4 | 0.06 MB |
  | Instrument Sans（500） | 2 | 0.02 MB |
  | 比較：しっぽり明朝（1つの太さ） | 122 | 3.60 MB |
  | 比較：Noto Serif JP（静的、1つの太さ） | 124 | 3.6 MB |
  | 比較：Noto Serif JP（可変、500–600） | 124 | 6.75 MB |

- **編集アプリケーションの配布物には上限が近い。** lambroll が zip を Lambda へ直接アップロードしており、その上限は 50 MB。いまの配布物は zip で 38.6 MB ある。

## Goals / Non-Goals

**Goals:**

- 見本 B′ の見た目を、公開サイトと編集アプリケーションで、同じ基準値から再現する。
- 使う書体と太さの一覧を1箇所に置き、公開サイトの自己配信と、編集アプリケーションの読み込みの両方をそこから作る。
- 訪問者が読む書体の量を抑える。和文は断片単位で配り、太さの数を絞る。
- 暗い設定の配色と、それに付随する写し（`theme-color` の暗い側）を残さない。

**Non-Goals:**

- 書体のファイルをリポジトリに入れて版を固定すること（決定2の代案C）。
- 編集アプリケーションの画面構成を変えること。部品の見え方だけを新しい基準に合わせる。
- 基準値を CSS 以外（TypeScript の定数など）へ移すこと。書体の一覧だけは、ビルド設定からも読むため TypeScript に置く（決定1）。

## Decisions

### 決定1：書体の一覧を `src/styles/fonts.ts` に置き、両アプリケーションはそこから読み込みを作る

一覧の各要素は、書体名・CSS 変数名・太さ・字形（normal / italic）・代わりの書体を持つ。

| 役割 | 書体 | 太さ | 書体の変数 |
| --- | --- | --- | --- |
| 題字・日付の数字・英字の見出し語 | Instrument Serif | 400（normal / italic） | `--font-instrument-serif` |
| 欧文のラベル（月・曜日の略記、導線の日付、ピル、一覧への導線） | Instrument Sans | 500 | `--font-instrument-sans` |
| 題（記事・一覧・導線の題、本文の `##`） | Zen Old Mincho | 600 | `--font-zen-old-mincho` |
| 本文・和文のラベル | Zen Kaku Gothic New | 400 / 500 | `--font-zen-kaku-gothic-new` |

- **公開サイト**：`astro.config.ts` の `fonts` に、この一覧を `fontProviders.google()` と組にして渡す。`src/layouts/Base.astro` に書体ごとの `<Font>` を置く。
- **編集アプリケーション**：同じ一覧から Google Fonts の CSS2 の URL を組み立てて `<link>` で読み、同じ名前の書体の変数を `:root` に定義する（決定2）。
- `tokens.css` は役割ごとの変数だけを持ち、その値を上の書体の変数から作る（決定5）。画面の CSS は役割の変数だけを参照し、書体の変数を直接は使わない。

**代案：両方の `Base.astro` に書体名を書く。** 採らない。どの書体をどの太さで使うかの出どころが2つになり、spec の「書体の差し替え」が守れない。

**題の明朝は Zen Old Mincho にする。** 本文の Zen角ゴシック New と同じ作者による、Zen のファミリーの明朝である。仮名の大きさや線の終わり方がそろうので、題と本文が並んでも字面がぶつからない。配信する書体も約 2.65 MB と、比べた候補の中で軽い（Context の表）。候補は見本（`mockup.html` の B′ の「題の明朝」の切り替え）でページごと見比べて決めた。

- **代案：Noto Serif JP（前回までの案）。** 採らない。仮名が大きく黒みが強いため、柔らかい Zen角ゴシック New の横で題だけが硬く見える。約 3.6 MB と重い。
- **代案：しっぽり明朝。** 採らない。端正で題が一段くっきりするが、同じファミリーほどには本文と字面がそろわない。約 3.6 MB と重い。
- **代案：Zen Antique。** 採らない。古い活字のような個性はあるが、太さが1つしかなく、一覧の小さな題（1rem）で黒く詰まる。

### 決定2：公開サイトは書体を自分で配り、編集アプリケーションは Google Fonts から読む

公開サイトは spec の「公開サイトの書体は公開サイト自身から届く」に従い、Fonts API で取り込んで `/_astro/fonts/` から配る。訪問者のブラウザが Google へ要求を送ることはない。

編集アプリケーションは Fonts API を使わない。使うと書体のファイル（決定3の構成で約 5.4 MB）が Lambda の配布物に入る。woff2 は圧縮済みで zip でもほとんど縮まないため、配布物は 38.6 MB から約 44 MB になり、直接アップロードの上限 50 MB に近づく。以後の依存の追加で上限を越えたとき、それはデプロイが通らないという形で表面化する。編集アプリケーションの利用者は書き手だけで、spec も第三者への要求を禁じていない。

どちらも Google を取得元にしていることには意味がある。公開サイトはビルドのたびに Google からその時点の版を取り込み、編集アプリケーションは表示のたびに同じ版を読む。プレビューと公開後で書体の版がずれるのは、Google で版が更新されてから次に公開するまでのあいだに限られる。

**代案A：編集アプリケーションも Fonts API で自分で配る。** 採らない。上の上限の問題による。

**代案B：編集アプリケーションが、公開サイトの `/_astro/fonts/` を読む。** 採らない。CloudFront に CORS の応答ヘッダを足す必要がある。Fonts API が生成する URL にはハッシュが付くため、別のアプリケーションから安定して指すこともできない。

**代案C：npm の Fontsource パッケージで、公開サイトの書体の版を固定する。** 採らない。版は固定できるが、Google から読む編集アプリケーションとは版が別々に動き、プレビューと公開後のずれが常に起きうる状態になる。CJK のパッケージは全太さを含み、`node_modules` も大きい。

### 決定3：和文は断片ごとに配り、太さの数を絞る

- **`subsets` は既定の `latin` のままにする。** Context のとおり、和文の断片は絞られずに取り込まれる。`latin-ext`・`cyrillic`・`vietnamese` は落ちるが、日記の本文にそれらの文字が現れても、代わりの書体で表示されるだけで欠けはしない。
- **題の書体（Zen Old Mincho）は 600 の1つに絞る。** 見本でも、記事・一覧・導線の題をすべて 600 で組んでいる。太さを2つ持つと、同じ文字でも太さごとに断片を読むことになる。題の文字は1ページに数十字あり、断片は1つ約 22 KB ある。Zen Old Mincho は同じ太さでも細身に見えるので、1つに絞るなら、記事の題（1.85rem）で見出しの強さが出る 600 にする。
- **本文の書体（Zen角ゴシック New）は 400 と 500 を持つ。** 500 は和文のラベル（ページの見出しのラベル、節の題、編集アプリケーションの部品）に使う。月と曜日は欧文の略記にしたので（決定7）、500 で現れる和文の字はごく少なく、読む断片も少ない。
- **`strong` は 500 にする。** 700 を持たないので、700 を指定するとブラウザが疑似的に太らせ、字面が崩れる。公開済みのエントリで `**` を使っているのは1件だけで、強調の差が小さくなる影響は限られる。
- **先読み（preload）は Instrument Serif の `latin`・`normal` だけにする。** 題字と大きな数字に使い、どのページでも最初に見える。和文の断片は、どれが要るかがページの文字で決まるため先読みしない。

### 決定4：読み込みを待たずに代わりの書体で示し、欧文書体の後ろには和文書体を続ける

- **`display` は Fonts API の既定の `swap` にする。** spec の「書体の読み込みを待つあいだ、文字を見えない状態にしてはならない」に対応する。
- **和文書体の代わりには、OS の和文書体を先に並べる。** Zen角ゴシック New には `"Hiragino Sans", "Yu Gothic", Meiryo, sans-serif`、Zen Old Mincho には `"Hiragino Mincho ProN", "Yu Mincho", serif`。差し替わる前の字面が、差し替わった後に近くなる。
- **欧文だけの書体（Instrument Serif / Sans）には、総称の代わり（`serif` など）を付けない。** 役割の変数では、欧文の書体の後ろに和文の書体を続ける（`--font-display` は Instrument Serif → Zen Old Mincho）。総称は、そこに現れない文字も含めてすべて受け止めてしまう。欧文の書体の直後に `serif` があると、題字に混ざった和文（編集アプリケーションの題「apkas-diary 編集」の「編集」など）が Zen Old Mincho まで届かず、OS の明朝で出る。

### 決定5：基準値（`tokens.css`）

変数名は、役割の変わらないものは保つ。名前を変えると、各画面の `<style>` に散った参照を書き換えることになり、書き漏らしても CSS はエラーを出さない。その宣言が無効になり、色の消えた画面がそのまま配信される（align-with-portfolio の決定1と同じ判断）。

| 変数 | 値 | 役割 |
| --- | --- | --- |
| `--bg` | `#ffffff` | 地 |
| `--surface` | `#ffffff` | 囲みの地。地と同じ白にし、囲みは罫線で分ける |
| `--fg` | `#111111` | 文字、強い罫線（ヘッダーの下、一覧の上） |
| `--fg-muted` | `#6a6a6a` | 淡い文字、入力欄の枠 |
| `--border` | `#e5e5e5` | 罫線 |
| `--accent` | `#c73e1d` | 朱 |
| `--font-display` | Instrument Serif → Zen Old Mincho | 題字・数字・英字の見出し語 |
| `--font-serif` | Zen Old Mincho | 題 |
| `--font-sans` | Zen角ゴシック New | 本文・和文のラベル・画面の地 |
| `--font-ui` | Instrument Sans → Zen角ゴシック New | 欧文のラベル |
| `--text-prose` | `0.9375rem`（15px）、幅 42.5rem 以上で `0.96875rem`（15.5px） | 本文の大きさ |
| `--page` | `40rem` | 本文の幅。変わらない |
| `--radius` | `2px` | 囲み・入力欄・`pre`・写真の縮小画像 |
| `--radius-pill` | `999px` | ピル・ボタン・一覧への導線 |

- **本文の大きさを切り替える幅は 42.5rem にする。** 本文の幅 40rem に左右の余白（1.25rem ずつ）を足した幅で、本文の列が最大幅に達するところにあたる。左右の余白は、見本に合わせていまの 1.5rem から 1.25rem にする。狭い画面で本文の列が 8px 広がる。
- **暗い設定のブロックを削る。** `html` の `color-scheme` は `light` にし、ブラウザが描く部品を明るい側に固定する。`theme-color` の `meta` は、`media` を持たない `#ffffff` の1つにする。
- **コントラストの実測値**（白地に対して）：文字 18.88、淡い文字 5.41、朱 5.08。朱はホバーのときに文字の色にもなるが、4.5 を上回る。文字でないもの（フォーカスの線、入力欄の枠）に求められる 3:1 も、朱と淡い文字は満たす。罫線（1.26）は飾りの区切りにだけ使い、入力欄の枠には使わない。
- **測った値は `tokens.css` にも書き残す。** これまでは出どころがポートフォリオにあったため書かなかったが、これからは日記が出どころなので、値を変えるときの根拠をそばに置く。

### 決定6：朱の使いどころ

spec の「配色は白い地の1通りとする」に従い、朱は面を塗らず、印と手応えにだけ使う。

| 場所 | 朱の現れ方 |
| --- | --- |
| 題字 | 右肩の小さな丸（常に） |
| 日別ページの日付 | 月・年の上の小さな丸（常に） |
| 本文の `hr`（`---`） | 1.6rem × 2px の短い線（常に） |
| 画像の説明 | 先頭の「—」（常に） |
| 一覧の行 | 日の数字が朱になり、題に朱の下線（ホバー） |
| 前後の導線 | `Newer` / `Older` が朱（ホバー） |
| ピル・一覧への導線・ボタン | 枠と字が朱（ホバー） |
| 本文のリンク | 字と下線が朱（ホバー） |
| フォーカス | 1px の朱の線（キーボードで辿ったとき） |
| 編集アプリケーション | 失敗を伝える囲みの左の線、「最新でない」の表示、ラジオの印 |

- **いま居る場所は朱ではなく黒で示す。** ピルの `aria-current` と、編集アプリケーションの選択中のタブは `--fg` で塗って白抜きにする。朱は手応えに使っているため、居場所にも使うと意味が重なる。
- **主となるボタン（`.primary`）は黒で塗る。** ホバーでは、塗りを朱に変えずに朱の輪（`box-shadow`）を出す。spec が朱で面を塗ることを禁じているためである。
- **失敗を伝える囲みの線に朱を使うのは、「朱を入れる」の朱である。** 誤りに印を付ける色として、日記の中で意味が通る。成功と通常の囲みの線は黒にする。
- **`:focus-visible` から `border-radius` の指定を外す。** この指定は輪郭線ではなく要素そのものの角丸を書き換えており、丸いピルがフォーカスした瞬間に角張る。いまのブラウザは、輪郭線を要素の角丸に沿って描く。

### 決定7：日付は英語の略記で見せ、読み上げには和文の日付を渡す

日付の表記は次の3つの形に限る。月と曜日の略記は、先頭だけを大文字にした形（Sep、Mon）で示す。

| 形 | 使う場所 | 見た目 | 読み上げ |
| --- | --- | --- | --- |
| 部品（大きな日の数字と2段の添え書き） | 一覧の行、日別ページの頭 | 20 ／ Sep 2026 ／ Sun（年を省く一覧では Sep ／ Sun） | 2026年9月20日（日） |
| 1行 | 前後の導線 | Mon, Sep 21, 2026 | 2026年9月21日（月） |
| 期間 | 年・月のピル、月別ページの大きな語 | 2026 ／ Sep | 2026年 ／ 9月 |

- **`src/lib/date.ts` に、月（Jan–Dec）と曜日（Sun–Sat）の略記と、日付を英語の部分に分けて返す関数を足す。** 読み上げの和文には既存の `formatDateJa` を使う。見た目の英語と読み上げの和文は、同じ日付の文字列から同じモジュールの関数で作る。片方だけを手で書く箇所を作らない。
- **略記は関数が返す形（`Sep` / `Mon`）のまま示し、体裁の側で大文字に変えない。** 大文字だけの形（SEP / MON）も見本で比べたうえで、小文字を交えた形にした。小さな字でも、語の形のまま読める。

部品のマークアップは、和文の日付を読み上げ専用に置き、英語の部分を読み上げから外す。

```html
<time class="date-block" datetime="2026-09-20">
  <span class="visually-hidden">2026年9月20日（日）</span>
  <span class="date-block-day" aria-hidden="true">20</span>
  <span class="date-block-meta" aria-hidden="true"><span>Sep 2026</span> <span>Sun</span></span>
</time>
```

見た目の並べ方（数字が左、月・年と曜日が右に2段）は CSS grid で行い、読み上げの順とは切り離す（spec の「欧文で示した日付の読み上げ」）。1行の形も、和文を読み上げ専用に置き、英語を `aria-hidden` にする同じ組み方にする。`.visually-hidden` は `base.css` に足す。

- **使う場所は、一覧の行（`EntryList`）と日別ページの頭。** 日別ページでは、タイトルの有無によらず同じ部品・同じ大きさで示す。タイトルのないときは `h1` がこの部品を包み、あるときは部品の下にタイトルの `h1` を置く。日付が1度だけ・同じ書式で現れることは変わらず、diary-site-pages の要件は保たれる。
- **朱の丸は日別ページの頭の部品にだけ付ける。** 一覧で行ごとに付けると、朱が行の数だけ並んで「印」でなくなる。
- **前後の導線の日付は1行の形にする。** 導線の中では日付は脇役で、大きな数字は要らない。
- **狭い画面の一覧では、月・年と曜日を1行に並べ、間に「·」を置く**（Sep 2026 · Mon）。2段にすると、題の行と合わせて行が3段になる。

**代案：英語の部分をそのまま読み上げさせる。** 採らない。日本語の読み上げ音声は `Sep` や `Mon` をうまく読めない（1字ずつ読む、ローマ字のように読むなど）。`lang="en"` を付ければ英語として読まれるが、和文のページの中で1語ずつ言語が切り替わる読み上げになる。

**代案：`<time>` の `aria-label` に和文を持たせる。** 採らない。役割を持たない要素の `aria-label` は、読み上げに使われない環境がある。

### 決定8：ページの見出しは「大きな語＋和文のラベル」の部品にする

飾りの大きな語（`aria-hidden`）と、和文の `h1`（小さなラベルの字面）を組にした部品を置く。大きな語は、期間で区切られたページではその期間を表す語（年は数字、月は略記。ローマン体）、それ以外のページでは英字の語（イタリック）にする。

| ページ | 大きな語 | `h1` |
| --- | --- | --- |
| トップ | *Recent* | 最近の日記 |
| 年別 | 2026 | 2026年の日記 |
| 月別 | Sep | 2026年9月の日記 |
| 過去の同じ日 | *On this day* | 9月20日の記録 |
| 見つからない | *Not found* | ページが見つかりません |

- 件数（「N 件」）は、いまと同じく見出しの下に淡い字で置く。
- **節の題（`.section-title`）は、ラベルと右へ伸びる罫線の組のまま残す。** トップの「年別」にだけ、飾りの *Archive* を前に添える。編集アプリケーションの節の題（直近の実行、プレビューなど）には英字を添えない。道具の画面で、飾りは読む速さの邪魔にしかならない。
- **日別ページはこの部品を使わない。** 日付の部品（決定7）がその役を担う。
- **年・月のピルは期間を表す語だけにする。** 年別のピルは数字だけ（2026）、年別ページの月のピルは略記（Sep）。「年」「月」は見た目から外し、`.visually-hidden` で読み上げに残す（spec の「欧文で示した導線の読み上げ」）。
- **一覧への導線も英語にする。** 日別ページの下は Sep 2026 / 2026 / On this day、月別ページの下は 2026。読み上げには「2026年9月の一覧」「2026年の一覧」「過去の同じ日」を渡す。
- **和文のまま残すもの。** ページの `h1`、文書の題（`<title>`。タイトルのない日は `formatDateJa`）、件数、編集アプリケーションの日付。`h1` と `<title>` は読み上げと検索に使われる文字で、和文のほうが日記の読み手に通じる。編集アプリケーションは道具の画面で、見た目の揃いより読み取りやすさを優先する。
- **見本で示したのはトップだけ**で、年別・月別・過去の同じ日・404 はこの規則を延長したものである（Risks を参照）。

### 決定9：本文の要素

- `.prose`：`--font-sans` の 400、`--text-prose`、行送り 2.0、字送り 0.04em、段落の間 1.3em。
- 本文の `h2`（Markdown の `##`、40件にある）：`--font-serif` の 600（決定3）、1.2rem。
- `hr`：決定6の朱の短い線。左に寄せ、前後を 2.6rem 空ける。区切りとしての広さは、いまの 3rem から少し詰める。
- **画像の説明（`figcaption` と、表の説明のセル）は左に寄せ、先頭に朱の「—」を付ける。** いまは中央寄せにしている。大きさは 0.78rem、淡い字。
- 本文のリンク：字は `--fg`、下線は `--fg-muted` の 1px（字からの距離 0.3em）。ホバーで字と下線が朱になる。色で見分けさせず、下線で見分けさせる。
- `strong`：500（決定3）。
- リスト・引用・`pre`：寸法はいまのまま、色だけ基準に従う。

### 決定10：部品の形

形で役割を分ける。押せるものは丸く、囲むものは角を立てる。

- **欧文のラベル**（月・曜日の略記、導線の日付、一覧への導線）：`--font-ui` の 500。字間を少し空け（値は見本に従う）、月と曜日は Sep / Mon の形のまま示す（決定7）。題字や見出し語の英字（*Recent*、*Newer* など）は Instrument Serif で組む。
- **ピル**：1px の `--fg` の枠、`--radius-pill`、`--font-ui` の 500。`.is-quiet` は枠を透明にし、`aria-current` は `--fg` で塗って白抜きにする。ホバーで枠と字が朱。
- **一覧への導線**（日別ページの下の Sep 2026 など）：`--border` の枠のピル、欧文のラベルの字面。ホバーで朱。
- **ボタン**：白地に 1px の `--fg` の枠、`--radius-pill`。`.primary` は `--fg` で塗って白抜き。ホバーで枠と字が朱（`.primary` は朱の輪）。無効のときは `--border` の枠と淡い字。
- **入力欄**：1px の `--fg-muted` の枠、`--radius`。
- **囲み**（通知・確認・`fieldset`）：1px の `--border` の枠、`--radius`。通知の左の線は `--fg`、失敗を伝えるものは朱。確認の囲みは `--fg` の枠。
- **ヘッダー**：題字「apkas-diary」を `--font-display` の 1.95rem で置き、下に 1px の `--fg` の線を引く。編集アプリケーションの題「apkas-diary 編集」も同じ字面にする。
- **フッター**：区切りの線をやめ、余白だけにする（見本のとおり）。中身を持たないことは変えない。

## Risks / Trade-offs

- **公開サイトの配信物が増える** → 書体のファイル約370個・約 5.4 MB が `dist/` に加わり、最初の `aws s3 sync` で転送される。ファイル名にはハッシュが付くので、書体の版が変わらない限り、次からは転送されない。
- **公開サイトのビルドが Google Fonts に依存する** → 公開手続き（CodeBuild）で Google Fonts に届かないとビルドが失敗する。失敗は公開手続きの失敗として編集アプリケーションに見え、配信中のサイトはそのまま残る。再実行で足りる。頻発するようなら、決定2の代案Cへ移す。
- **最初の表示で書体が差し替わり、行の折り返しが動く** → `swap` の帰結で、spec の「文字を見えない状態にしない」を優先した結果である。2ページ目からはブラウザの cache から読む。
- **題の明朝（Zen Old Mincho 600）が、一覧の小さな題で重く見える**（決定3）→ staging で、一覧の題（1rem）と前後の導線の題（0.95rem）を確かめる。重ければ 500 にする。その場合も太さは1つに保ち、600 を捨てて 500 にする。
- **英字の見出し語を、見本で見せていないページにも延ばしている**（決定8）→ 年別・月別・過去の同じ日・404 と、年別ページの月のピル（Sep）を staging で書き手に見せて確かめる。語を変えるだけなら、ページの側を直せば済む。
- **英語の略記を読み替える手間が増える** → 月と曜日の略記は広く見慣れたもので、日と年は数字のまま大きく残る。日付を読み取る手間はほとんど増えない。
- **見た目の英語と読み上げの和文が食い違う** → 両方を同じ日付の文字列から同じモジュールの関数で作る（決定7）。確認の段で、読み上げの文言も聞いて確かめる。
- **Windows での字面** → 本文は Regular 400 にしたので、Light で懸念していた「線が細くかすれる」ことは起きにくい。15px の Zen角ゴシック New が、Windows の拡大率 100% でも読めることを staging で確かめる。
- **編集アプリケーションのプレビューが Google に依存する** → 書き手の手元から Google Fonts に届かないと、プレビューが代わりの書体で出る。字面が明らかに違うので、書き手にはそれと分かる。
- **ポートフォリオから辿ると、別のサイトに見える** → 意図した変化で、spec からもその保証を外している。
- **公開ボタンとの競合** → これまでの変更と同じ形の危険がある。編集アプリケーションの「公開」は GitHub の `main` から作り直して配るため、この変更が `main` に入る前に手元から production へ配ると、ボタンが押された時点で公開サイトだけが古い体裁に戻る。Migration Plan の順で防ぐ。

## Migration Plan

1. staging に、公開サイト（`npm run build -- staging` → `npm run deploy -- staging`）と編集アプリケーション（`npm run deploy:editor -- staging`）を配って確かめる。見る点：
   - 公開サイトの書体の要求が、すべて自分のドメインに向いていること（開発者ツールのネットワーク）。
   - 暗い設定でも白地で出ること、ブラウザの枠が白いこと。
   - 狭い画面で、大きな日付・ピル・前後の導線がはみ出さないこと。
   - 写真の並び（`table`）、`##` を含むエントリ、リンクを含むエントリの見え方。
   - プレビューと公開後で、同じ幅の画面のときに字面が一致すること。
   - 読み上げで、日付・ピル・一覧への導線が和文で読まれること。
   - Windows の拡大率 100% での本文の読みやすさ。
2. `main` にマージする。
3. その後に production へ配る。マージ済みなので、「公開」ボタンが押されても配られるのは新しい体裁である。

**切り戻し**：revert して同じ経路で配り直す。触れるのは CSS・マークアップ・ビルドの設定だけで、データと URL には影響がない。書体のファイルは `--delete` 付きの同期で取り除かれる。
