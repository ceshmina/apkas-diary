## Context

動機は proposal.md の Why を、満たすべきことは specs/entry-editing/spec.md を参照。ここでは方式の選定に効く現状だけを挙げる。

- 記事の編集画面（`editor/src/pages/entries/[date].astro`）は**素の HTML フォーム1枚**である。「表示を確認」は `action=preview` としてフォームを POST し直し、サーバが整形した HTML を本文より下の `<section class="preview">` に描いて返す。整形結果は保存されない。
- 整形は `src/lib/markdown.ts` の `renderMarkdown()` が担う。中身は `@astrojs/markdown-satteri` の processor に、画像をキャプション付きの `figure` へ組み替える hast プラグインを1つ足したもので、**公開サイトの `.md` と同じ経路**である。「公開サイトと同じ解釈規則」は、同じ関数を通ることによって成り立っている。
- その processor の実体は **satteri（Rust の napi バインディング）** である。`node_modules/satteri` は `#binding` の条件で実装を切り替え、ブラウザ向けには `@bruits/satteri-wasm32-wasi` を読む。この WASM は optional dependency であり、いまの環境には入っていない。
- 編集アプリケーションは Lambda + API Gateway HTTP API。応答の上限は 30 秒。**すべての要求は `editor/src/middleware.ts` を通り**、未認証の GET はログインへ、それ以外は 401 になる。
- Astro の CSRF 判定（`security.checkOrigin`）が効いており、前段の `X-Forwarded-Proto` / `X-Forwarded-Host` を信じる相手は `astro.config.ts` の `allowedDomains` に挙げた2つのホストに限られる。**これが無いと POST が全部 403 になる**、と設定に書かれている。
- 画面のスクリプトは `CopyField.astro` の1つだけ。「1枚のスクリプトが画面上のすべてを受け持つ」形を採り、写せない環境でも記述そのものは残す作りになっている。
- 紙面の幅は `--page: 40rem`（`src/styles/tokens.css`）で、`Base.astro` が `header` と `main` の双方に当てている。**プロジェクトに画面の広さによる分岐（`@media (min-width: …)`）はまだ1つも無い**。あるのは `prefers-color-scheme` と `prefers-reduced-motion` だけ。
- 編集画面のスタイルは `src/styles/base.css`（本文要素）と `tokens.css`（色・寸法）を公開サイトと共有している。プレビューが公開後と同じに見えるのはこれによる。

## Goals / Non-Goals

**Goals:**

- 「公開サイトと同じ解釈規則」を**構造として**保つ。追随のために整形の実装をもう1つ持たない。
- 追随・分割・切り替えのいずれが働かなくても、**保存の前に整形結果を確かめられる状態**が残る。
- 画面の広さによる分岐を1か所に置き、この画面の外へ広げない。
- 入力中の本文とタイトルに触れる経路を増やさない。プレビューは読み取るだけで、書き戻さない。

**Non-Goals:**

- 整形をブラウザ側に持つこと（決定1を参照）。
- 入力と表示のスクロールの対応づけ（proposal の非目標）。
- プレビューの結果を跨いで持ち回ること（キャッシュ・下書きの自動保存のいずれも行わない）。
- 編集画面以外の幅・配置の変更。

## Decisions

### 決定1: 整形はサーバで行い、本文を送って HTML を受け取る

| 案 | 内容 | 判断 |
| --- | --- | --- |
| **A. サーバの経路に本文を送り、整形結果の HTML を受け取る** | `renderMarkdown()` をそのまま通す | **採用** |
| B. ブラウザで satteri を動かす | `@bruits/satteri-wasm32-wasi` を載せる | 却下 |
| C. 別の Markdown 実装をブラウザに載せる | marked などで整形する | 却下 |

C を最初に落とす。**「公開サイトと同じ解釈規則」が実装の同一性で担保されている**のが現状であり、別の実装を置いた時点でそれが「2つの実装が同じ結果を出すことを願う」に変わる。図版をキャプション付きの `figure` に組み替える処理も書き写すことになり、写真を貼った段落——**日記でいちばん確かめたい部分**——から食い違いが始まる。

B は同じ実装を使えるが、ブラウザに WASM の Markdown エンジンを運ぶことになる。編集画面を開くたびに数 MB が乗り、いまは入っていない optional dependency をビルドの依存に加えることになる。数百字の日記1本のために払う量として釣り合わない。

A の代償は**往復すること**である。入力のたびにネットワークを1回使い、Lambda を1回呼ぶ。ただし呼ぶのは整形だけで、DynamoDB にも S3 にも触れない。決定4 で間引き、決定6 で遅れと失敗を扱う。

### 決定2: 経路は `POST /api/preview`、本文をそのまま送り、HTML の断片を返す

- **場所**: `editor/src/pages/api/preview.ts`。`/entries/preview` に置くと `[date]` の動的経路と隣り合い、「日付ではない `/entries/…`」を1つ作ることになる。編集画面のための経路であって、エントリの1つではない。
- **要求**: `Content-Type: text/plain; charset=utf-8` で、**本文の Markdown をそのまま body に載せる**。JSON で包むと、送る側と受ける側の両方に「1つしかない値を取り出す」処理が生まれる。`text/plain` は Astro の CSRF 判定が見る content type に含まれるため、既存の `allowedDomains` の設定がそのまま効く（フォームの POST と同じ関門を通る）。
- **応答**: `text/html; charset=utf-8` の**断片**（`renderMarkdown()` の戻り値そのもの）。ページを返さないので、受け取った側は差し込むだけで済む。
- **認証**: middleware の内側に置く。未認証の POST は 401 が返る（既存の分岐のまま。新しい公開経路を作らない）。
- **上限**: 受け取る本文の大きさに上限を設ける（100KB）。超えたら 413 を返す。日記の本文はこの桁に届かず、届く要求は誤りである。
- **保存しない**: この経路は DynamoDB に触れない。`entry-editing` の「確認と保存の区別」は、**触る手段を持たないこと**で満たす。

### 決定3: プレビューの初期内容はサーバが描く

画面を開いた時点で、`[date].astro` が現在の本文を `renderMarkdown()` に通し、プレビューの面に**描いた状態で**返す。スクリプトはそこから引き継ぐ。

こうすると3つが同時に片付く。**(1)** スクリプトが動かない環境でも、開いた瞬間から整形結果が見えている。**(2)** 保存の失敗でフォームの値を描き直すとき（既存の分岐）も、その本文の整形結果が並ぶ。**(3)** 最初の1回の往復を待つあいだ空の面を見せずに済む。

代償はページを開くたびの整形1回だが、同じプロセスの中で完結する処理であり、この画面が既に行っている DynamoDB への問い合わせ（エントリ1件＋その日の写真）に比べれば小さい。

既存の「表示を確認」ボタン（`action=preview`）は**マークアップから消さない**。追随が始まった時点でスクリプトが隠す。押しても正しく働くものが、要らなくなったときに消える形にしておく。

### 決定4: 追随は「入力が止まってから」まとめて1回

- `input` イベントを拾い、**400ms** 手が止まったら送る（デバウンス）。一文字ごとには送らない。
- 直前に整形した本文と同じなら送らない。カーソル移動や、書いて消して元に戻した場合の往復を消す。
- 要求は**同時に1つ**。応答を待つあいだに新しい入力があれば、待っているものを捨てずに終わらせ、最新の本文でもう1回送る。
- 応答には通し番号を持たせ、**古い応答が新しい表示を上書きしない**ようにする。往復の時間は一定ではなく、順番に返る保証がない。

400ms は「打鍵の合間には送らず、手を止めたら待たされたと感じない」あたりで置いた値である。使ってみて動かす余地がある（Open Questions）。

### 決定5: 分割はフォームの外で組み、切り替えるのは入力とプレビューの面だけ

画面の骨格を次の形にする。プレビューの `<section>` は**フォームの外**に置き、`<form>` に `display: contents` を当てて、フォームの子とプレビューを1つの grid の上に並べる。

```
main
├─ 見出し・通知
├─ .editor  (grid)
│  ├─ form (display: contents)
│  │  ├─ タイトル            … 全幅
│  │  ├─ タブ帯（狭い画面のみ表示）… 全幅
│  │  ├─ 本文の入力          … 広い画面では左、狭い画面ではタブで選ばれたとき
│  │  ├─ 公開状態            … 全幅
│  │  └─ 操作（保存など）     … 全幅
│  └─ プレビュー             … 広い画面では右、狭い画面ではタブで選ばれたとき
└─ この日の写真（従来どおりフォームの外）
```

プレビューをフォームの中に入れない理由は、**本文に生の HTML を書けるから**である。Markdown は生の HTML を素通しするため、整形結果に `<button>` や `<input>` が現れうる。それがフォームの中にあると、押した瞬間に保存が走ったり、身に覚えのない値が送られたりする。起きる確率は低いが、**起きたときに壊れるのが保存**である。既にこの画面は「読み取り専用の要素はフォームの外に置く」という判断で写真の一覧を外に出しており、それに揃える。

切り替えるのは**本文の入力とプレビューの2面だけ**にする。タイトル・公開状態・保存の操作・写真の一覧は、どちらを見ていても画面にある（`entry-editing` の「並べ方が変わっても編集の操作は失われない」）。フォーム全体とプレビューを入れ替える案は、狭い画面でプレビューを見ているあいだ保存に手が届かなくなるため採らない。

`display: contents` を使わずに済ませる案（プレビューをフォームの中に入れる／左の列にフォームを丸ごと置く）は、いま述べた2つの理由でそれぞれ落ちる。

### 決定6: 遅れと失敗は、直前の描画を残したまま示す

- 要求を出してから応答が返るまで、プレビューには**直前の整形結果が残る**。空にしない。
- 送ってから 1 秒たっても返らない場合、面の見出しに「更新中」を出す。速いときには出さない。
- 失敗した場合（ネットワーク・500・413）、直前の整形結果を残したまま「**最新の内容ではない**」ことを示す。次の入力で改めて試みる。
- 401 が返った場合は「ログインが切れている」ことを示す。プレビューが更新できないだけでなく、**そのまま保存しても失敗する**状態なので、区別して伝える意味がある。
- どの経路でも `textarea` と `input` には触れない。プレビューは読むだけである。

### 決定7: 差し込みは `innerHTML`、差し込む値はサーバの整形結果に限る

受け取った断片は `innerHTML` で置く。差し込むのは**サーバが `renderMarkdown()` を通して返したものだけ**で、ブラウザで組み立てた文字列は混ぜない。

これは新しい露出面ではない。同じ HTML が保存を経て公開サイトに出るものであり、そこでも `set:html` で描かれている（この画面の既存のプレビューも同じ）。本文を書けるのは本人ひとりであり（`editor-access-control`）、他人の入力が流れ込む経路は無い。

### 決定8: 広い画面の基準は 60rem、そのときの紙面は 64rem

- 分割に切り替える基準を `@media (min-width: 60rem)` に置く。**プロジェクト初の幅の分岐**であり、値は `src/styles/tokens.css` に名前付きで置かず、この画面の `<style>` に閉じる。分岐が2つ目の画面に現れたときに共有へ引き上げる。
- 分割時の紙面は `64rem`。`Base.astro` に `wide` の prop を足し、指定された画面でのみ `header` と `main` の幅を広げる。`--page: 40rem` のまま2列にすると1列 19rem ほどになり、**書くにも読むにも足りない**。一覧・公開・写真の画面は 40rem のまま変えない。
- 分割時、2つの面は**高さを揃え、それぞれの中でスクロール**する。上端が揃っていないと、書いている段落と整形結果を目で往復するときに毎回探すことになる。高さは `clamp(28rem, 70vh, 46rem)`。このとき `textarea` の `resize` は止める（片方だけ伸びると対応が崩れる）。狭い画面では従来どおり、自然な高さで縦に伸びる。

### 決定9: タブは button と data 属性、働かなければ両方を出す

- タブは `<button type="button">` を2つ（編集／プレビュー）。`role="tablist"` と `aria-selected` を付ける。押されると `.editor` の `data-active` が `edit` / `preview` に変わる。
- **どちらを隠すかは CSS が決める**。狭い画面のときだけ `data-active` に従い、広い画面では両方を出す。要素に直接 `hidden` を付けると、広い画面での「両方見える」を JS が知っている必要が出てくる。幅の知識は CSS に閉じる。
- 既定は `edit`。開いた直後は書ける状態にする。
- スクリプトが動かない場合、タブ帯そのものを出さない（マークアップ上は `hidden` で置き、スクリプトが外す）。このとき狭い画面では2つの面が縦に並ぶ——**いまと同じ姿**である。追随もしないが、開いた時点の整形結果は決定3 により見えており、「表示を確認」も従来どおり働く。`entry-editing` の「切り替えが働かない環境」「追随が働かない環境」はこれで満たす。

ラジオボタンと CSS だけでタブを組む案（`:has()` を使う）は、状態を持つ要素が保存のフォームの中に入り、送信されるフィールドが1つ増える。追随のためにどのみちスクリプトが要る以上、切り替えだけを無理に JS 無しに寄せる利得が小さい。

## Risks / Trade-offs

- **往復のたびに Lambda を呼ぶ（回数の増加）** → 400ms の間引きと「変わっていなければ送らない」で、打鍵ごとではなく段落の切れ目ごとの頻度に落ちる。1本の記事を書くあいだで数十回の桁。整形だけの処理で、DynamoDB にも S3 にも触れない。使っていない時間の費用は変わらない（`editor-hosting`）。副次的に、書いているあいだ実行環境が温まり、**保存そのものが速くなる**。
- **コールドスタートで最初の更新が数秒遅れる** → 決定3 により、開いた時点の整形結果は既に画面にある。1 秒を超えたら「更新中」を出し、無反応に見えないようにする。
- **回線が細い・切れている環境では追随しない** → 直前の結果を残し、最新でないことを示す（決定6）。編集と保存の可否には影響しない。
- **`display: contents` をフォームに当てる** → 送信の挙動は変わらないが、描画の箱が消えるため `form` に当てていた `gap` などは効かなくなる（grid 側で持つ）。もし支援技術との相性で問題が出た場合は、プレビューをフォームの中へ戻し、決定5 で述べた生の HTML の危険を「本文に生の対話的要素を書かない」という運用の前提に置き換える形へ後退できる。
- **この画面だけ紙面が広い** → 一覧から編集へ移ると幅が変わる。`Base` の prop に閉じ、広げる画面を明示的に選ぶ形にすることで、意図しない画面へ広がらないようにする。
- **プレビューの列が公開サイトより狭い** → 64rem を2列に割ると1列あたり 30rem 前後で、公開サイトの 40rem より狭い。折り返しの位置は公開後と一致しない。**整形の解釈は一致するが、行の折り返しまでは一致しない**という限界であり、これは分割表示を選んだ時点で受け入れる（狭い画面のタブでも同じことが起きる）。
- **本文が非常に長い記事での往復** → 100KB の上限を置く。数万字の記事でも 1 要求あたり数十 KB で収まる。

## Migration Plan

- 1画面の変更であり、データにも権限にも触れない。デプロイは既存の `npm run deploy:editor`。
- 戻すのはリバートのみ。プレビューの経路（`/api/preview`）を消しても、決定3 により**開いた時点の整形結果と「表示を確認」は残る**ため、部分的に戻しても確認の手段は失われない。
- staging（`admin.dev.apkas.net`）で、広い画面・狭い画面・スクリプトを止めた状態の3つを確認してから production へ出す。

## Open Questions

- 追随の間隔 400ms は、実際に書いてみてから詰める。速すぎれば呼び出しが増え、遅すぎれば手を止めたときに待たされる。仕様にも作りにも影響しない範囲の調整である。
- 分割時の高さ `clamp(28rem, 70vh, 46rem)` も同様に、使ってみて動かす。
