## Why

編集アプリケーションから日記を書いても、公開サイトは変わらない。反映には手元で `npm run build` / `npm run deploy` を実行する必要があり、**ブラウザから書ける利点が最後の一歩で失われている**。外出先で書いた記事は、手元の環境に戻るまで公開できない。

書く手段をブラウザに広げた以上、公開する手段も同じところに置く。手元の CLI からのデプロイは、これまでどおり残す。

## What Changes

- 公開サイトの再生成と配信への反映を、**手元ではなくクラウド側で実行できる**ようにする。実行の定義は環境ごとに1つとし、どの起動口から始めても同じ手順が動く。
- 編集アプリケーションに**デプロイの起動と状況表示**を置く。押すと再生成が始まり、進行中・成功・失敗が画面で分かる。
- 編集アプリケーションには**配信先への書き込み権限を与えない**。与えるのは公開手続きを起動する権限と、その状況を読む権限だけで、S3 と CloudFront に触れるのは実行側の権限に限る。
- ビルドが読むソースは **GitHub の main ブランチ**とする。ボタンが配るのは常に main の内容であり、手元の未コミットの変更は配られない。
- **BREAKING**（仕様上）: `site-delivery` の「デプロイはローカルの操作で完結する。CI/CD への依存を持ってはならない」を書き換える。ローカルからの経路は残すが、それが唯一の経路であるという制約を外す。

明示的に含めないもの（非目標）:

- **コード変更時の自動ビルド**。仕組み（起動口）は共通なので後から足せる。この change では起動口を用意するところまでとする。
- **CI（型検査・Lint・テスト）**。公開手続きの実行環境はビルドとデプロイだけを担い、CI は GitHub Actions 側に置く。片方の都合でもう片方が止まらないよう、最初から分けておく。
- **production の自動デプロイ**。production への反映は、どの起動口からでも人の意思を要求する。

## Capabilities

### New Capabilities

- `site-publishing`: 公開サイトの再生成と配信への反映を、起動口から独立した1つの手続きとして定めるもの。起動する権限と配信先へ書き込む権限の分離、多重起動の抑制、進行状況の可観測性、失敗時に配信中の内容を壊さないこと、待機時の費用が発生しないことを含む。

### Modified Capabilities

- `site-delivery`: 「デプロイはローカルの操作で完結する」の要件を書き換える。ローカルからの実行は引き続き可能でなければならないが、CI/CD への依存を禁じる制約を外し、クラウド側からの実行を認める。
- `editor-hosting`: 「実行基盤の権限は自環境の日記データに限られる」の要件を書き換える。公開手続きを**起動する**権限は認めるが、配信元ストレージと CDN への直接の権限は引き続き与えない。
- `deployment-environments`: 「すべてのリソースはコードで管理される」の例外の一覧に、**ソースコード基盤との接続**を加える。接続の確立には基盤側での認可が要り、構成管理コードだけでは完結しない。

## Impact

- **Terraform**: 公開手続きを担うモジュールを新設し、環境ごとの root から呼ぶ。配信先バケット・ディストリビューション ID・テーブル名は、既に output として存在する値をそのまま実行環境へ渡す（config への転記を増やさない）。編集アプリケーションの IAM ポリシーに、起動と状況取得の権限を1つのプロジェクトに限って足す。
- **編集アプリケーション**: デプロイの起動と状況表示の画面・経路を追加。AWS SDK の CodeBuild クライアントを依存に加える。`function.jsonnet` に対象プロジェクト名を足す。
- **ビルド手順**: `scripts/build.sh` / `scripts/deploy.sh` が行っている手順を、クラウド側の実行定義からも同じ内容で辿れるようにする。手順が2箇所で食い違うと、ボタンから配ったものと手元から配ったものが変わる。
- **セットアップ**: 環境ごとに1度だけ、AWS と GitHub の接続を人が承認する手順が増える（README に追記）。
- **README**: 公開の手順に、ブラウザからの経路を追記する。
