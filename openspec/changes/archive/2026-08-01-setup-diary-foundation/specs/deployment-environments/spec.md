## Purpose

staging と production を互いに独立に保ち、片方への操作が他方に波及しないことを担保する。本番の日記データは再取得が不可能であるため、環境の取り違えを事故として起きうるものとみなし、仕組みで防ぐ。

## ADDED Requirements

### Requirement: staging と production は独立して存在する

システムは staging と production の2環境を持ち、両者はリソースを共有してはならない（MUST NOT）。

#### Scenario: 片方の環境への変更

- **WHEN** staging に対してインフラの変更を適用する
- **THEN** production のリソースはいっさい変化しない

#### Scenario: データの独立

- **WHEN** staging のデータストアにエントリを登録する
- **THEN** production のサイトにはそのエントリが現れない

### Requirement: 環境は認証情報の切り替えによって選択される

操作対象の環境は AWS の named profile によって切り替えられなければならない（MUST）。

#### Scenario: profile による環境の選択

- **WHEN** 環境に対応する profile を指定してインフラの操作を実行する
- **THEN** その環境のリソースのみが操作の対象になる

### Requirement: 意図しない環境への適用を拒否する

適用先の環境と、与えられた認証情報が指すアカウントが一致しない場合、操作は実行前に失敗しなければならない（MUST）。

#### Scenario: 認証情報の取り違え

- **WHEN** production の設定に対して staging の認証情報を与えて適用を試みる
- **THEN** リソースがひとつも変更されないまま操作が失敗し、不一致が報告される

#### Scenario: 認証情報の未指定

- **WHEN** 環境を特定できる認証情報を与えずに適用を試みる
- **THEN** 操作が失敗する

### Requirement: リソース名から環境が判別できる

各環境に属するリソースは、名前から所属する環境が判別できなければならない（MUST）。

#### Scenario: リソース名の確認

- **WHEN** 管理コンソールなどでリソースの一覧を見る
- **THEN** それぞれのリソースがどちらの環境に属するかが名前から判別できる

### Requirement: インフラの状態は環境ごとに分離し、同時操作から保護する

インフラの状態は環境ごとに独立して保存されなければならない（MUST）。また、同一環境に対する同時の変更操作は排他制御されなければならない（MUST）。

#### Scenario: 状態の分離

- **WHEN** 一方の環境の状態が破損または失われる
- **THEN** もう一方の環境の状態と管理は影響を受けない

#### Scenario: 同時実行

- **WHEN** 同一環境に対する変更操作が並行して実行される
- **THEN** 後発の操作は先行する操作の完了を待つか、ロックの存在を報告して失敗する

### Requirement: すべてのリソースはコードで管理される

この change で作成されるすべてのクラウドリソースは、構成管理コードによって定義されなければならない（MUST）。管理コンソールでの手動作成に依存してはならない（MUST NOT）。ただし、状態の保存先そのものは自己参照を避けるため例外とし、その作成手順が文書化されていなければならない（MUST）。

#### Scenario: 環境の再構築

- **WHEN** 状態の保存先が用意された空のアカウントに対して構成管理コードを適用する
- **THEN** サイトの配信とデータの保持に必要なリソースがすべて作成される

#### Scenario: 状態の保存先の準備

- **WHEN** 新しい環境を初めて構築する
- **THEN** 状態の保存先を用意する手順が文書化されており、それに従って準備できる
