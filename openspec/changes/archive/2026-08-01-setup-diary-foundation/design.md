## Context

リポジトリは README のみの空の状態で、既存の制約はない。動機と範囲は proposal.md を参照。要求は `specs/` 配下の5つの capability に定義済み。

設計を規定する制約は3つ。

1. **データの正は DynamoDB に置く**。将来スマホから編集するため、ファイルではなく DB を正とする。
2. **配信は静的**。ローカルでビルドし S3 + CloudFront で配信する。実行時のサーバは持たない。
3. **日記は再取得不可能**。誤操作・サービス障害・アカウント喪失のいずれでも本文が失われない構成にする。

前提ツールは Node.js 22、Terraform 1.10 以降、AWS CLI と2つの named profile。

## Goals / Non-Goals

**Goals:**

- 「DB が正・配信は静的」という非対称な構成を、破綻なく最小構成で成立させる
- 下書きが公開サイトに漏れる経路を、運用の注意ではなく仕組みで塞ぐ
- 環境の取り違えを、運用の注意ではなく仕組みで塞ぐ
- 将来の書き込み経路（管理画面・スマホ）を足すときに、データモデルを作り直さずに済む形にする

**Non-Goals:**

- 書き込み性能・読み取り性能の最適化（個人利用の規模では律速しない）
- 汎用的な CMS としての抽象化。日記という単一の用途に閉じて設計する
- 独自ドメインの設定（Open Questions 参照）

## Decisions

### 1. DynamoDB のキースキーマ

シングルテーブル設計とし、パーティションキー `pk`・ソートキー `sk` を持つ。テーブル名は `apkas-diary-{env}`、課金はオンデマンド（PAY_PER_REQUEST）、PITR を有効化する。

エントリのアイテム構成:

| 属性 | 例 | 用途 |
| --- | --- | --- |
| `pk` | `ENTRY#2026` | 年でパーティションを切る |
| `sk` | `2026-08-01` | 年内で日付順に並ぶ |
| `type` | `entry` | アイテム種別。将来の種別追加に備える |
| `date` | `2026-08-01` | JST の暦日 |
| `title` | `...` | タイトル |
| `body` | `...` | 本文（Markdown のまま保持） |
| `status` | `published` / `draft` | 公開状態 |
| `createdAt` / `updatedAt` | `2026-08-01T13:45:00Z` | UTC の ISO 8601 |
| `gsi1pk` | `ENTRY`（定数） | **公開時のみ書く** |
| `gsi1sk` | `2026-08-01` | **公開時のみ書く** |

GSI1 は `gsi1pk` / `gsi1sk`、プロジェクションは ALL。

アクセスパターンの対応:

| 要求 | 操作 |
| --- | --- |
| 特定日 | `GetItem(pk="ENTRY#2026", sk="2026-08-01")` |
| 年別 | `Query(pk="ENTRY#2026")` |
| 月別 | `Query(pk="ENTRY#2026", sk begins_with "2026-08")` |
| 最新N件 | `Query(GSI1, gsi1pk="ENTRY", 降順, Limit=N)` |
| 公開分の全件 | `Query(GSI1, gsi1pk="ENTRY")` |
| 下書き含む全件 | `Scan(FilterExpression: type="entry")` |

**年をパーティションキーにした理由**: URL に年が含まれるため、特定日の取得が Query ですらなく `GetItem` で済む。年別・月別の絞り込みもベーステーブルだけで完結し、専用の GSI を必要としない。1パーティションは最大366アイテムで、サイズ上限に対して十分小さい。

**代替案**: 日付そのものをパーティションキーにする案（`pk="ENTRY#2026-08-01"`）。特定日の取得は同じく `GetItem` で済むが、年別・月別の一覧に別の GSI が必要になるため採らない。

### 2. GSI1 のパーティションキーを定数にする

`gsi1pk` は常に `ENTRY` という単一の値を取る。一般には書き込みが1パーティションに集中する反パターンだが、**書き込みが1日1件程度の個人日記では成立しない**。DynamoDB のパーティションあたりの上限は 1000 WCU で、桁が3つ以上離れている。

定数キーを避けようとすると、最新N件と全件取得のために日付を分散させた人工的なキーを持ち込むことになり、複雑さに見合う利益がない。規模が変わった場合はシャーディング（`ENTRY#<0-9>`）に移行できるが、この用途では起きない。

### 3. 下書きの除外は sparse index で行う

`status` が `draft` のあいだは `gsi1pk` / `gsi1sk` の**属性そのものを書かない**。DynamoDB の GSI はキー属性を持たないアイテムを索引に載せないため、下書きは GSI1 から自動的に外れる。

これにより、公開サイトの生成は GSI1 を Query するだけで公開分のみを得る。**取得側にフィルタ処理が存在しないため、フィルタのバグによる下書き漏洩が起こりえない**。`status` 属性での絞り込みに頼る設計だと、この保証はコードの正しさに依存することになる。

代償は書き込み側の複雑さで、公開状態を変更するたびに GSI キー属性の付与・削除が必要になる。書き込み経路を1箇所に集約することで対処する（決定7）。

### 4. GSI2（「N年前の今日」用）は作らない

月日を横断するクエリ用の GSI は、この change では作成しない。

静的サイトでは「今日」がビルド時刻に固定されてしまうため、月日ページは**366通りすべてを事前生成する**（決定6）。生成時には全エントリが手元にあるため、月日での索引は不要になる。この GSI が必要になるのは、全件をロードしない将来のクライアント（管理画面・スマホ）が「N年前の今日」を表示するときで、そのときにオンラインで追加できる（既存アイテムは自動でバックフィルされる）。

用途が確定していない段階でインデックスを作ると、必要な射影やキー形式を推測で決めることになる。実際の利用側ができてから決めるほうが誤らない。

### 5. フロントエンドは Astro

**Next.js の static export（`output: 'export'`）を採らない理由**: static export は API Routes・Middleware・画像最適化・ISR を無効化する。これらは将来スマホ編集を足す段階でまさに欲しくなる機能で、そのとき「OpenNext で Lambda に載せ替える」か「別に API を建てる」かの選択を迫られる。後者を選ぶなら Next.js である必然性がほぼ残らない。

**Astro を選ぶ理由**: ビルド時のデータ取得がフロントマターの素の async コードで書ける。デフォルトで JS を出力しないため CloudFront から配信する量が小さい。そして island アーキテクチャにより、将来の検索窓・エディタ・「今日の分」への導線といった部分的な動的要素を、サイト全体の構成を変えずに追加できる。この日記の育ち方（今は完全静的、将来ここだけ動的）と一致する。

**その他の代替案**: Eleventy は最軽量だが将来のエディタ UI で力不足。SvelteKit の adapter-static も成立するが、コンテンツサイト向けの機能（コンテンツコレクション、Markdown 統合）は Astro のほうが揃っている。

### 6. 「N年前の今日」は366ページの事前生成で解決する

`/on-this-day/MM-DD` を、閏日を含む366通りすべてについて生成する。生成時には全エントリがメモリ上にあるため、月日でグルーピングするだけで追加のデータ取得は発生しない。

「訪問した日の分」への導線のみ、クライアント側の小さなスクリプトで訪問時刻から `MM-DD` を解決してリンク先を決める。これが唯一の実行時ロジックになる。

**代替案**: 毎日リビルドして「今日」のページを1枚だけ生成する案。日次の実行基盤が必要になり、ビルドが止まると表示が古くなる。事前生成なら壊れる余地がない。

### 7. 書き込みは単一のスクリプトに集約する

この change では管理画面を作らないが、**エントリを登録する最小のスクリプトは含める**。マネジメントコンソールでの手入力は Markdown 本文の投入に耐えず、これがないと成果物が実際には使えないため。

スクリプトは Markdown ファイルと日付を受け取り、GSI キー属性の付与・削除（決定3）と `createdAt` / `updatedAt` の管理を担う。**キー属性の扱いを知る場所をここ1箇所に閉じる**ことで、将来 API を足すときも同じロジックを再利用できる。

### 8. ビルド時のデータ取得は2回に分ける

サイト生成とエクスポートで、取得経路を意図的に分ける。

```
ビルド ─┬─ Query(GSI1) ──── 公開分のみ ──▶ Astro ──▶ 静的サイト ──▶ S3
        └─ Scan(type=entry) ─ 下書き含む ──▶ Markdown 書き出し ──▶ ローカル（バージョン管理対象外）
```

1回の Scan で取得してメモリ上で振り分けるほうが読み取りは少なく済む。それでも分けるのは、**サイト生成の入力に下書きが最初から存在しない**という決定3の保証を守るため。1回に統合すると、下書きの除外がコード上のフィルタに戻り、保証がコードの正しさ依存になる。個人日記の規模では2回読んでも従量課金の下限付近に留まるため、保証を優先する。

### 9. Terraform の構成

```
terraform/
├── modules/
│   ├── storage/       # DynamoDB テーブル + GSI1 + PITR
│   └── delivery/      # S3 + CloudFront + OAC
└── envs/
    ├── staging/       # AWS_PROFILE=<staging>
    └── production/    # AWS_PROFILE=<production>
```

**workspace を使わず環境ごとにディレクトリを分ける**: 環境が AWS_PROFILE で分かれる、つまりアカウントが分かれる可能性が高い。workspace は単一の backend 設定を共有する前提のため、アカウントをまたぐ運用と相性が悪い。ディレクトリを分ければ backend も provider も環境ごとに独立して書ける。冗長さは、参照するモジュールを共通化することで抑える。

**state のロックに DynamoDB テーブルを使わない**: Terraform 1.10 以降の S3 backend は `use_lockfile = true` によりロックをネイティブに扱える。従来必要だったロック用テーブルは作らない。

**誤爆の防止**: provider に `allowed_account_ids` を設定する。適用先の設定と認証情報のアカウントが一致しない場合、リソースを変更する前に失敗する。これが `deployment-environments` の「意図しない環境への適用を拒否する」要求の実装になる。

**state バケットの bootstrap**: state の保存先自体は Terraform で作れない（自己参照になる）。AWS CLI での作成手順を README に記載し、環境の新規構築時に手で1度だけ実行する。

### 10. 配信とキャッシュ

S3 バケットはパブリックアクセスを全ブロックし、CloudFront の OAC（Origin Access Control）からのみ読めるバケットポリシーを与える。ビューアプロトコルは HTTPS へのリダイレクトを強制する。

デプロイは `aws s3 sync --delete` で生成物を反映したのち、CloudFront に `/*` の invalidation を発行する。`--delete` により、前回存在して今回なくなったページが残らない（`site-delivery` の要求）。invalidation は月1000パス無料で、`/*` は1パスとして数えられるため実質無償。

Astro が出力するアセットは内容ハッシュ付きのファイル名になるため長期キャッシュでよいが、HTML はデプロイのたびに変わる。個人サイトの規模では両者を細かく作り分ける利益が小さいため、**invalidation で一括して片付ける**方針を採る。

### 11. 日付の扱い

`date` は JST の暦日を表す `YYYY-MM-DD` の**文字列**として保持し、比較・整列・グルーピングはすべて文字列として行う。`Date` 型への変換を経由すると、実行環境のタイムゾーン設定によって前後の日にずれる事故が起きる。ビルドを実行するマシンのタイムゾーンに結果が依存してはならない。

`createdAt` / `updatedAt` は UTC の ISO 8601 とし、表示に使う場合のみ JST に変換する。

### 12. エクスポートの配置先は、当面ローカルのみとする

書き出した Markdown はバージョン管理の対象外のローカルディレクトリに置き、リポジトリにコミットしない。

**git にコミットしない理由**: 将来 GitHub Actions でビルドするようになると、CI からのコミットは書き込み権限・push ループ（コミットがビルドを再発火させる）・並行実行時の競合の対処を抱え込む。エクスポートは日々更新されるため、この負担が恒常的に発生する。

**CI に移行したときの配置先は GitHub Release とする**。ローリングタグ（例 `backup`）に zip を `--clobber` で上書きし、常に最新の1本を保持する。

| 選択肢 | 評価 |
| --- | --- |
| リポジトリへのコミット | push ループと競合の対処が要る |
| **Release のアセット** | **採用**。アセットの追加は push ではないため `on: push` を再発火させず、ループが起きない。`--clobber` で並行実行も後勝ちに収束する |
| Actions の artifact | 保持期間が最長90日で、長期保全にならない |
| S3 の別バケット | 「AWS を失っても残る」という目的を満たさない |

補足の判断:

- **形式は zip**。tar.gz のほうが Unix 系では自然だが、この成果物の目的は10年後に開けることにある。zip は追加のツールなしにどの OS でも開ける。
- **`--prerelease` を付ける**。リポジトリのトップに「Latest release」として表示されず、バックアップ用のタグが目立たない。
- **履歴は最新のみでよい**。版管理は DynamoDB の PITR が担っており、このエクスポートの役目は AWS の外にテキストを出しておくことにある。
- **下書きも公開される**。Release のアセットは public リポジトリでは誰でも取得でき、エクスポートは下書きを含む。これは許容する前提で採用している。公開サイトへの下書きの露出を防ぐ決定3とは目的が異なる（あちらは意図しない公開の防止であり、こちらは意図した保全先の選択）。
- **単一障害点は移動するだけ**。Release は GitHub アカウントに依存するため、AWS 喪失には備えられるが GitHub 喪失には備えられない。ローカルの書き出しが残ることで、実質は AWS・GitHub・ローカルの3箇所になる。

Release への配置は CI 化の change で実装する。この change ではローカルへの書き出しまでを対象とする。

## Risks / Trade-offs

- **DB を正にしたことで、プレーンテキストが手元に残る性質を失う** → ビルドの副産物として Markdown をローカルに書き出す（`content-export`）。加えて PITR で誤操作からの復旧を担保する。
- **現時点では開発者のマシンがエクスポートの唯一の複製になる** → この change の時点ではビルドがローカルでしか走らないため、書き出しもローカルにしか存在しない。CI 化の change で GitHub Release への配置（決定12）を実装した時点で解消される。それまでは production のデータ保全を PITR に依存する期間があることを許容する。
- **手動登録では書き込みの検証が弱い** → 登録スクリプトを単一の経路にし、日付形式・公開状態・キー属性の整合をそこで担保する。将来 API を足すときも同じロジックを通す。
- **書き込みから公開までにビルドが挟まる** → 現時点では登録が手動なので、ビルドを続けて実行すればよく実害がない。スマホ編集を足す段階で、手動リビルド → DynamoDB Streams 起点の自動リビルド、と段階的に解消する。
- **2環境ぶんの CloudFront ディストリビューションを持つ** → 作成・更新に数分かかり、料金も2倍になる。ただし個人利用の転送量では従量課金の下限付近に留まり、環境分離の利益が上回る。
- **staging に本番同等のデータがない** → staging は構成の検証用と位置づけ、データの一致は求めない。表示崩れの確認にはダミーのエントリを使う。
- **エントリのサイズ上限（400KB）** → 通常の日記本文では到達しない。写真を扱う後続の change では本体ではなく S3 のキーを保持する方針とし、上限に近づけない。

## Migration Plan

新規構築のため移行対象はない。構築の順序のみ規定する。

1. **state バケットの bootstrap**（環境ごとに1度、AWS CLI）
2. **staging へ Terraform を適用** — DynamoDB・S3・CloudFront を作成
3. **staging でエンドツーエンドの確認** — 登録スクリプトでダミーのエントリを投入 → ビルド → デプロイ → CloudFront 経由で表示、S3 直接アクセスが拒否されることを確認
4. **production へ Terraform を適用**
5. **production へ最初のエントリを投入しデプロイ**

**ロールバック**: この change の時点では production に実データがないため、`terraform destroy` で環境ごと破棄できる。実データ投入後は破棄せず、サイトの内容は前回の生成物を再デプロイすることで戻す（書き出された Markdown が git にあるため、生成物は再現できる）。

## Open Questions

- **独自ドメインを使うか**。当面は CloudFront のデフォルトドメインで要求を満たせる。独自ドメインにする場合、ACM 証明書（us-east-1）と DNS の設定が加わるが、`delivery` モジュールへの追加で済み、データモデルにもページ構成にも影響しない。ドメインを取得する意思が固まった時点で別の change として扱える。
- **トップページに表示する件数**。表示上の調整であり、仕様にも構成にも影響しない。実装時に暫定値を置き、実際の見た目を見て決める。
