## Context

動機は proposal.md - Why を参照。

いまのエントリは `date` / `title` / `body` / `status` / `createdAt` / `updatedAt` の6属性で、書き込みは `putEntry()` の1箇所に集約されている（`src/lib/store/put.ts`）。省略されたフィールドは `??` で既存値を引き継ぐ。属性が増えるのは基盤を作って以来はじめてで、**書き込み・書き出し・表示・編集・取り込みの5経路すべてが同じ属性を知る必要がある**。

取り込み元は `../eskarun` のクローン。frontmatter に `location: Osaka, Japan` の形で107件、33地点。未指定の記事について旧サイトは表示・集計の上で `Tokyo, Japan` とみなしていたが、ファイルには書かれていない。

**制約が1つある。** 移行後に `migrate-legacy-photos` が production の720件の本文を書き換えている（旧ホストの URL 2,365箇所 → `photos.apkas.net`）。旧サイトのファイルの本文はその書き換え前のものなので、**取り込みが本文に触れると 2,365箇所が巻き戻る**。

## Goals / Non-Goals

**Goals:**

- 場所という属性を、書ける・読める・保全されるの3つが揃った状態で加える。
- 107件の取り込みが、本文・タイトル・公開状態・`createdAt` のいずれにも触れないこと。
- 「持たない」を1つの状態として扱い、空文字との2重の表現を作らないこと。

**Non-Goals:**

- 場所別の一覧・集計、表記の正規化（proposal.md - スコープ外）。
- 既存の6属性の扱いの変更。今回の変更で `title` や `status` の意味は変わらない。

## Decisions

### 決定1: 1つの文字列として持ち、持たないときは属性そのものを書かない

`Entry` に `location?: string` を加える。DynamoDB アイテムには、場所を持つときだけ `location` 属性を書く。空文字を書いて「無い」を表すことはしない。

`status` が `draft` のとき `gsi1pk` / `gsi1sk` を**書かない**のと同じ流儀である。不在を不在として表すほうが、あとから読む側に解釈を求めない。`fromItem()` は文字列でなければ `undefined` を返す、という1行で済む。

代替として都市と国に分けて持つ形（`city` / `country`）も考えたが、採らない。旧サイトの33地点はすべて `<都市>, <国>` の形をしているものの、それは書き手がそう書いていたというだけで、将来もそう書くとは限らない。分解は表記に構造を仮定することであり、**集計の都合を、保存の形に先に持ち込むことになる**。集計が要るとなったときに、そのときの必要に合わせて分解すればよい。値は保存されている。

### 決定2: 書き込みでは `undefined`（据え置き）と `null`（削除）を分ける

`PutEntryInput` に `location?: string | null` を加える。

| 与えるもの | 結果 |
| --- | --- |
| 指定なし（`undefined`） | 既存の値を保つ |
| 文字列 | その値にする（前後の空白は落とす） |
| 空文字・空白のみ | 場所を持たない状態にする |
| `null` | 場所を持たない状態にする |

既存の `title` / `body` / `status` は `??` で据え置きを表すだけで、削除の意味を持つ値がない（空タイトルは空文字として正しく保存される）。場所は「持たない」が正当な状態なので、据え置きと削除を区別できなければ、一度付けた場所を編集画面から外せなくなる。

正規化（trim して空なら持たない）は `putEntry()` の中に1箇所だけ置く。HTML フォームは未入力を空文字として送るため、編集画面・CLI・取り込みのどこから来ても同じ結論になる場所に置く必要がある。呼び出し側それぞれで空文字を弾く形にすると、弾き漏らした経路からだけ空文字が入る。

### 決定3: 表示は見出しの外に、日付とは別の1行として置く

日別ページの頭は、タイトルの有無で形が2つに分かれている（タイトルあり: 日付行 + `h1`、なし: `h1` が日付）。場所をこの分岐の中に入れると、2つの形それぞれに場所ありなしが掛かって4通りになる。

そこで**場所は見出しの中に入れず、頭のまとまりの最後に独立した1行として置く**。分岐の外に出るので、タイトルの有無によらず同じ位置・同じ書式になり、spec の「タイトルの有無によって場所の書式や位置を変えてはならない」を形から満たす。日付の表示（`DateBlock`）には触れないので、「日付はページに1度だけ」も保たれる。

値は書かれたまま（`Osaka, Japan`）出す。和訳も整形もしない。読み上げのための和文を別に持つ `DateBlock` とは扱いが違うが、場所は固有名であり、英字がそのまま読まれて困るものではない。

### 決定4: 書き出しは frontmatter に行を足し、持たないときは行ごと出さない

`title` と同じく `JSON.stringify()` で二重引用符スカラーとして書く（`: ` を含む値が素で書くと壊れるため。`Osaka, Japan` は該当しないが、値は自由入力である）。

持たないエントリでは `location:` の行そのものを出さない。`location: ""` と書くと、空文字を持つエントリと持たないエントリが同じ見た目になり、**書き出しから復元したときに区別が失われる**。属性の並びは固定で、`status` の次に置く。

行を出さないことで、場所を持たない1,000件あまりの書き出し結果は今とバイト単位で同一になる。取り込み後の書き出しの差分が107件だけになり、**やったことと差分が一致する**。

### 決定5: 取り込みは「場所だけを埋める」専用の経路にする

`import-legacy` に `--location-only` を足す。このモードでは `putEntry({ date, location })` だけを呼び、`title` / `body` / `status` を渡さない。渡さなければ決定2により既存値が保たれる。

本文を巻き戻さないことは、この change で最も壊しやすいところである（Context の制約）。通常の取り込みモードを使い回して「本文は同じはずだから上書きしてよい」とはしない。**同じでないことが分かっているものを、同じだと仮定する形の再利用をしない。**

`--dry-run` では、対象の日付・入る値・現在の値を並べて出す。33地点の一覧も出し、表記の揺れがあれば取り込み前に目視で気づけるようにする。

### 決定6: 編集画面の入力欄はタイトルの隣に置く

1行のテキスト入力を、既存のフォームの `title` の領域と同じ行に置く（grid の領域を1つ足す）。本文でも公開状態でもないものは頭のほうにまとまっているほうが探しやすく、保存は既存の `form` が1つあるだけなので経路は変わらない。プレビューは本文だけを対象とするので、場所はプレビューに関わらない。

未入力を空文字として POST しても、決定2の正規化が「持たない」に倒す。編集画面側に判定を置かない。

## Risks / Trade-offs

- **取り込みが本文を巻き戻す** → 決定5の専用モード。加えて staging で先に通し、production でも `--dry-run` の差分を確認してから実行する。事故が起きても `migration/production/snapshots/` に書き換え前の本文があり、写真の移行のロールバックとは逆向きに復旧できる。
- **107件の `updatedAt` が更新される** → `createdAt` は保たれる。`updatedAt` は「データストア上の最終更新」であって「日記を書いた日」ではないので、更新されて困るものではない。書き出しの差分は107件に出る（決定4により、それ以外には出ない）。
- **場所の表記に揺れが入りうる** → 仕組みで縛らない（proposal.md - スコープ外）。書き手は1人で、旧サイトの33地点に揺れは無い。揺れが実際に困りはじめたときに、候補からの選択を足すほうが軽い。
- **属性が増えることで、次に属性を足すときの手数も増える** → 今回さわる5経路（書き込み・書き出し・表示・編集・取り込み）が、属性を足すときに通る経路のすべてである。この change はその一覧を作る役目も持つ。

## Migration Plan

1. コードを staging に反映し、staging のエントリで付ける・書き換える・外すを一通り確認する。
2. staging で `--location-only --dry-run` を確認してから取り込む（staging は代表16件のみなので該当は数件）。
3. production で `--dry-run` の差分を確認し、107件を取り込む。
4. 公開サイトを再生成してデプロイし、場所を持つ日のページと持たない日のページを確認する。
5. 書き出しの差分が107件だけであることを確認する。

**ロールバック**: 対象の107件から場所を取り除けば元に戻る。本文には触れていないので、巻き戻すものが他に無い。取り込み元の `../eskarun` も残る。
