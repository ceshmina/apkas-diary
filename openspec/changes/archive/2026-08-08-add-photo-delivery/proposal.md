## Why

日記の本文に出ている写真 2369 枚は、すべて `photos.old.apkas.net` にある。旧サイトのホストであり、**このリポジトリが管理していない**。Terraform の管理下になく、`openspec/specs/` にもその存在は書かれていない。日記本文は DynamoDB を正とし Markdown にも書き出して長期保全を担保しているのに、写真だけがその外側の、作り直せない場所にぶら下がっている。

そして今後書く日記の写真を置く場所がない。新しい写真を1枚も本文に出せない状態が続いている。

自分の管理下に写真の配信経路を作る。旧ホストからの移行は後続の change に譲り、この change では**まず新しい写真を置いて配信できる状態**を作る。

## What Changes

- **アップロード用と配信用で S3 バケットを分ける。** 元写真を置くバケットと、公開される派生画像を置くバケットは別のものにする。配信用バケットに人が直接書き込む経路を作らないことで、公開されるものが「元写真から機械的に作られたもの」だけであることを構造で担保する。
- **元写真が上がると Lambda が派生画像を作る。** アップロード用 S3 のイベントで起動し、4つのサイズを生成して配信用 S3 に置く。人が呼び出す手順はない。
- **サイズは長辺で thumbnail 240px / small 960px / medium 1920px / large 3840px の4つ。** medium と large は旧ホストの規約を引き継ぐ。元写真より大きいサイズを求められたときは拡大せず、元の大きさのまま作る。4つの URL は常に存在する。
- **形式は webp に統一する。** 配信物の拡張子は `.webp` になる。
- **配信される写真から EXIF をすべて落とす。** 撮影日時・機材・そして GPS による撮影場所が、公開されるファイルに残らない。ただし**向きの情報だけは、落とす前に画素そのものへ反映する**。単に消すと、縦位置で撮った写真が横倒しで配信される。
- **元写真はアップロード用 S3 に永続保管する。** サイズを足したくなったとき、品質を変えたくなったとき、将来 AVIF に移りたくなったときに、手元から再アップロードせずに作り直せる。
- **配信は `photos.dev.apkas.net`（staging）/ `photos.apkas.net`（production）で行う。** 既存のサイト配信と同じく、S3 は直接公開せず CloudFront の OAC 経由に限る。
- **写真を投入する CLI を足す（`npm run photo`）。** 既存の `npm run entry` と同じく環境名を第1引数に取り、対象環境を明示しないと実行できない。

### スコープ外

- **旧ホストからの写真の移行**、および本文中の 2369 参照の書き換え。この change は新しい配信経路を作るところまでとし、`photos.old.apkas.net` を指す本文は据え置く。基盤の正しさを、2369 枚の移行の成否と切り離して確かめられるようにする。
- **写真の削除。** アップロード用 S3 から元写真を消しても、配信中の派生画像は消えない。削除は当面ふたつのバケットに対する手作業とする。連鎖して消す仕掛けを最初から持つと、原本を1つ消し損ねた操作が配信物まで巻き込む。日記の本文から参照が消えた写真が配信され続けても実害はなく、逆は取り返しがつかない。
- **写真の一覧・管理画面。** どの写真がどこにあるかは、アップロード用 S3 のキーがそのまま答えになる。
- **本文への写真の埋め込みを助ける仕掛け**（Markdown の生成、日記との紐付け）。写真は URL として本文に書く。
- **AVIF・動画・署名付き URL**。いずれも今必要としていない。

## Capabilities

### New Capabilities

- `photo-ingest`: 元写真を受け取ってから配信可能な派生画像になるまで。生成されるサイズ、形式、EXIF の除去、元写真の保管、同じ写真を再度投入したときの振る舞い
- `photo-delivery`: 派生画像を閲覧者に届ける経路。独自ドメイン、URL 規約、配信元ストレージへの直接アクセスの禁止

### Modified Capabilities

なし。

`deployment-environments` の既存要件（リソース名から環境が判別できる／すべてのリソースはコードで管理される／環境の DNS は自環境のアカウント内で完結する）は、この change で増えるリソースにもそのまま適用される。新しい要件を足す必要はない。

`site-delivery` は「生成された静的サイトを訪問者に届ける経路」を対象としており、写真はその生成物ではない。配信のドメインも CloudFront ディストリビューションも別になるため、既存要件は変更せず、写真の配信は独立した capability として立てる。

## Impact

**インフラ（Terraform）**

- 新しい module を1つ足す。アップロード用 S3、配信用 S3、CloudFront、OAC、ACM 証明書、Route53 レコード、Lambda の実行ロールと関数の枠、S3 イベント通知。
- 既存の `modules/delivery` は触らない。証明書とドメインの作り方は同じ形をなぞることになる。
- `envs/staging` と `envs/production` から新しい module を呼ぶ。ドメインはそれぞれ `photos.dev.apkas.net` / `photos.apkas.net` で、既存のサイトと同じホストゾーン（`dev.apkas.net` / `apkas.net`）に収まる。新しいホストゾーンは要らない。

**Lambda のデプロイ**

- **関数のコードとその実行時設定は Terraform の管理外に置き、lambroll でデプロイする。** インフラの形と関数の中身は変わる頻度が違うため、コードを1行直すために state を触る操作を通さずに済むようにする。Terraform が持つのは関数の存在と、S3 からの呼び出し配線だけになる。
- lambroll が必要とする値（ロール ARN、配信先バケット名、ディストリビューション ID）は Terraform の state から直接読む。転記は増えない。
- 前提とするツールに lambroll が加わる。

**アプリケーション**

- Lambda の実装を新しく置く。画像処理ライブラリ（sharp）に依存する。この依存は Lambda の中だけで完結し、サイト生成の依存には入れない。
- 投入 CLI を足す。既存の `scripts/` と `src/cli/` の形に合わせる。

**設定とドキュメント**

- `config/<環境>.env` に、投入先バケットと写真の配信 URL を足す（投入 CLI が使う値。lambroll のための値は含まない）。
- README の「必要なツール」に lambroll を足す。
- README に、写真のキー規約と投入手順、それに Lambda のデプロイ手順を書く。

**配信物**

- 日記サイトの生成物は1バイトも変わらない。本文の参照は据え置くため、この change の適用によって見た目が変わるページはない。

**運用コスト**

- 個人の規模では、S3 のストレージ（元写真＋派生4サイズ）と Lambda の実行がわずかに増えるだけになる見込み。CloudFront は既存のサイトと同じく従量課金の下限付近に収まる。ディストリビューションが1つ増えても固定費は生じない。

**前提**

- ACM 証明書の DNS 検証が必要になるため、既存のサイトと同じく適用に数分かかる。
- production の `photos.apkas.net` を作る時点で、旧ホスト `photos.old.apkas.net` とは別の名前になる。旧ホストのレコードには触れない。
