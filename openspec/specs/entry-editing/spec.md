# entry-editing Specification

## Purpose
ブラウザだけで日記を書き、下書きとして寝かせ、公開へ切り替えるところまでを完結させる。CLI と同じデータストアを正とし、どちらから書いても同じエントリになることで、書く手段が増えても日記が二重に存在しない状態を保つ。
## Requirements
### Requirement: エントリの一覧を下書きを含めて得られる

編集アプリケーションは、下書きと公開の双方を含むエントリの一覧を、日付の降順で提示しなければならない（MUST）。一覧の各項目からは、日付・タイトル・公開状態が判別できなければならない（MUST）。

#### Scenario: 一覧の表示

- **WHEN** 利用者が編集アプリケーションのエントリ一覧を開く
- **THEN** 下書きと公開の双方のエントリが、日付の新しい順に、それぞれの公開状態がわかる形で並ぶ

#### Scenario: エントリが1件もない

- **WHEN** エントリが1件も存在しない状態で一覧を開く
- **THEN** 空であることが示され、そこから新規作成に進める

### Requirement: 日付を指定してエントリを作成する

編集アプリケーションは、日付を指定して新しいエントリを作成できなければならない（MUST）。指定できる日付は JST の暦日を表す `YYYY-MM-DD` 形式でなければならない（MUST）。既にエントリが存在する日付を指定した場合、2件目を作らず既存エントリの編集として扱わなければならない（MUST）。

#### Scenario: 未登録の日付を指定する

- **WHEN** エントリのない日付を指定して作成する
- **THEN** その日付の新しいエントリとして保存される

#### Scenario: 登録済みの日付を指定する

- **WHEN** 既にエントリのある日付を指定して作成しようとする
- **THEN** 新しい空のエントリではなく、既存エントリの内容が読み込まれた編集画面になる

#### Scenario: 既定の日付

- **WHEN** 利用者が新規作成を始める
- **THEN** JST における当日の日付が既定として入っており、必要なときだけ変更すればよい

### Requirement: 本文は Markdown のまま保存される

編集アプリケーションは、利用者が入力した Markdown をそのまま保存しなければならない（MUST）。保存の前後で HTML への変換や整形を行ってはならない（MUST NOT）。

#### Scenario: 入力した本文の保存

- **WHEN** Markdown 記法を含む本文を入力して保存する
- **THEN** 入力した文字列がそのまま保持され、再度開いたときに同じ文字列が現れる

### Requirement: 下書きと公開を切り替えられる

編集アプリケーションは、エントリの公開状態を下書きと公開のあいだで双方向に切り替えられなければならない（MUST）。切り替えの結果は、次回の公開サイトの生成に反映されなければならない（MUST）。

#### Scenario: 下書きを公開にする

- **WHEN** 下書き状態のエントリを公開状態に切り替える
- **THEN** 公開サイト向けの取得にそのエントリが含まれるようになる

#### Scenario: 公開を下書きに戻す

- **WHEN** 公開状態のエントリを下書き状態に戻す
- **THEN** 公開サイト向けの取得にそのエントリが含まれなくなる

#### Scenario: 現在の状態の判別

- **WHEN** 利用者がエントリの編集画面を開く
- **THEN** そのエントリが下書きか公開かが、切り替えを行う前に判別できる

### Requirement: 保存の前に公開後の表示を確認できる

編集アプリケーションは、保存の前に本文の表示結果を確認する手段を提供しなければならない（MUST）。その表示は公開サイトと同じ Markdown の解釈規則に従わなければならない（MUST）。

#### Scenario: 表示の確認

- **WHEN** 本文を入力した状態で表示の確認を行う
- **THEN** 公開サイトに現れるものと同じ解釈で整形された結果が表示される

#### Scenario: 公開サイトとの一致

- **WHEN** 確認した内容をそのまま公開し、公開サイトを生成して同じエントリを見る
- **THEN** 確認時と同じ解釈結果が表示される

### Requirement: 保存の失敗によって書いた内容を失わない

保存が失敗した場合、編集アプリケーションは失敗した旨を利用者に伝えなければならない（MUST）。このとき、利用者が入力した内容を破棄してはならない（MUST NOT）。

#### Scenario: 保存が失敗する

- **WHEN** データストアへの書き込みが失敗する
- **THEN** 失敗したことが利用者に示され、入力していた本文は編集画面に残ったまま再試行できる

#### Scenario: 保存の成否の判別

- **WHEN** 利用者が保存を実行する
- **THEN** 保存が完了したのか失敗したのかが、利用者にとって曖昧でない形で示される

### Requirement: エントリを削除する手段を持たない

編集アプリケーションは、エントリを削除する操作を提供してはならない（MUST NOT）。公開サイトから取り下げる必要がある場合は、下書きへの切り替えによって行う。

#### Scenario: 削除操作の不在

- **WHEN** 利用者が編集アプリケーションの画面を通じて操作しうるすべてを確認する
- **THEN** エントリを削除する操作は存在しない

#### Scenario: 公開の取り下げ

- **WHEN** 公開済みのエントリを人目から外したい
- **THEN** 下書きへ切り替えることで公開サイトから外れ、本文は保持されたままである

### Requirement: CLI と編集アプリケーションは同じエントリを扱う

編集アプリケーションと既存の CLI は、同一のデータストアの同一のエントリを読み書きしなければならない（MUST）。一方で行った変更が他方から見えない状態を作ってはならない（MUST NOT）。

#### Scenario: 編集アプリケーションで書いたものを手元から見る

- **WHEN** 編集アプリケーションでエントリを保存したのち、手元でサイトを生成する
- **THEN** 保存した内容が生成物と書き出しに反映されている

#### Scenario: CLI で書いたものを編集アプリケーションから見る

- **WHEN** CLI でエントリを登録したのち、編集アプリケーションの一覧を開く
- **THEN** そのエントリが一覧に現れ、編集できる

#### Scenario: 作成日時と更新日時

- **WHEN** 編集アプリケーションからエントリを保存する
- **THEN** CLI から保存した場合と同じ規則で作成日時と更新日時が記録される

### Requirement: 写真の投入へ進んでも書きかけの内容を失わない

編集アプリケーションは、エントリを編集している状態から写真の投入へ進む手段を提供しなければならない（MUST）。その移動によって、利用者が入力していたタイトルと本文が失われてはならない（MUST NOT）。

移動にあたって内容が保存される場合、保存が行われることが**操作を行う前に**分かる形でなければならない（MUST）。利用者の知らないうちに保存が起きてはならない（MUST NOT）。

写真を入れるのは文章を書いている途中である。「写真を1枚入れたら、書きかけの段落が消えた」は、保存の失敗と同じだけ失われるものが大きい。

#### Scenario: 書きかけからの移動

- **WHEN** 本文を入力した状態から写真の投入へ進み、投入を終えて編集画面に戻る
- **THEN** 入力していたタイトルと本文がそのまま編集画面にある

#### Scenario: 保存が起きることの明示

- **WHEN** 利用者が編集画面から写真の投入へ進む操作を見る
- **THEN** その操作が内容の保存を伴うかどうかが、押す前に分かる

### Requirement: 投入した写真は本文に貼れる形で示される

写真の投入を終えた利用者に対して、編集アプリケーションは日記の本文にそのまま貼れる記述を示さなければならない（MUST）。利用者が URL の組み立て規約や本文での書き方を覚えている必要があってはならない（MUST NOT）。

既定として示される記述は、公開サイトの日別ページにおける**拡大表示が成り立つサイズ**を用いなければならない（MUST）。

あわせて、生成されるすべてのサイズの URL が示されなければならない（MUST）。既定とは別のサイズを使いたいとき、URL を自分で組み立てる必要があってはならない（MUST NOT）。

#### Scenario: 投入の完了

- **WHEN** 写真の投入が完了する
- **THEN** 本文に貼れる記述が示され、そのまま貼って公開すると公開サイトで写真が表示される

#### Scenario: 拡大表示との整合

- **WHEN** 示された記述をそのまま本文に貼って公開し、日別ページでその写真を開く
- **THEN** より大きなサイズによる拡大表示が成り立つ

#### Scenario: 別のサイズの利用

- **WHEN** 既定とは別のサイズを本文で使いたい
- **THEN** すべてのサイズの URL が画面に示されており、そこから選べる

#### Scenario: 複数枚の投入

- **WHEN** 複数の写真をまとめて投入する
- **THEN** 写真ごとに貼れる記述が示される

### Requirement: 投入した写真をその場で目で確かめられる

写真の投入を終えた利用者に対して、編集アプリケーションは**生成された写真そのもの**を表示しなければならない（MUST）。意図した写真が入ったかを確かめるために、示された URL を1つずつ開く必要があってはならない（MUST NOT）。

表示は生成が終わったものに限らなければならない（MUST）。まだ生成の終わっていない写真を表示しようとしてはならない（MUST NOT）。

取り違えは投入した直後にしか気づけない。日付を間違えた、向きが倒れている、まったく別の写真を選んでいた——いずれも本文に貼ってから公開サイトで気づくのでは遅い。

#### Scenario: 投入の確認

- **WHEN** 写真の投入と生成が終わる
- **THEN** その写真が画面に表示され、意図したものかどうかを目で判断できる

#### Scenario: 複数枚の確認

- **WHEN** 複数の写真をまとめて投入する
- **THEN** 生成が終わったものから順に、それぞれが画面に表示される

#### Scenario: 生成前の表示

- **WHEN** まだ生成が終わっていない写真がある
- **THEN** その写真は表示されず、まだであることが示される

### Requirement: 編集中のエントリの日に属する写真を一覧できる

編集アプリケーションは、エントリの編集画面において、そのエントリの日付に属する写真を提示しなければならない（MUST）。提示は投入の直後に限られてはならない（MUST NOT）。

提示される写真は目で判別できなければならない（MUST）。ファイル名の一覧だけを示してはならない（MUST NOT）。

派生画像の生成が終わっていない写真を、終わったものとして提示してはならない（MUST NOT）。

投入した直後の画面を閉じると写真に辿り着けなくなる、という状態を残さない。**日記は書き終わるまでに何度も開き直される**ものであり、写真を足すたびに投入し直すことを求めない。

#### Scenario: 過去に投入した写真の参照

- **WHEN** 前日までに写真を投入した日付のエントリを、時間を空けてから開く
- **THEN** その日に投入した写真が編集画面に並んでいる

#### Scenario: 写真のない日

- **WHEN** 写真を1枚も投入していない日付のエントリを開く
- **THEN** 写真が無いことが示され、そこから投入へ進める

#### Scenario: 生成が終わっていない写真

- **WHEN** 投入したばかりで派生画像がまだ生成されていない写真がある状態で編集画面を開く
- **THEN** その写真はまだであることが示され、生成済みのものと区別できる

### Requirement: 一覧からも本文に貼れる記述が得られる

編集画面に提示された写真それぞれについて、本文にそのまま貼れる記述が示されなければならない（MUST）。既定として示される記述は、投入の直後に示されるものと同じでなければならない（MUST）。

あわせて、生成されるすべてのサイズの URL が得られなければならない（MUST）。利用者が URL の組み立て規約を覚えている必要があってはならない（MUST NOT）。

写真を貼る手段が「投入の直後の画面」と「編集画面の一覧」で違うと、貼り方を2通り覚えることになる。**得られるものを同じにする。**

#### Scenario: 一覧からの貼り付け

- **WHEN** 編集画面に並んだ写真から記述を取り、本文に貼って公開する
- **THEN** 公開サイトでその写真が表示される

#### Scenario: 投入直後との一致

- **WHEN** 同じ写真について、投入直後の画面と編集画面の一覧が示す記述を比べる
- **THEN** 同じ記述である

#### Scenario: 別のサイズの利用

- **WHEN** 既定とは別のサイズを本文で使いたい
- **THEN** 編集画面の一覧からすべてのサイズの URL が得られる

### Requirement: 示された記述は1つの操作で写せる

編集アプリケーションは、本文に貼れる記述を1つの操作で複製する手段を提供しなければならない（MUST）。利用者が記述の範囲を選び直す必要があってはならない（MUST NOT）。

この手段は、写真の投入を終えた画面と記事の編集画面の**双方**で得られなければならない（MUST）。

複製の手段が働かない場合でも、記述そのものは読み取れる形で画面に残っていなければならない（MUST）。**写せないことによって、貼れる記述が得られない状態になってはならない（MUST NOT）。** 複製は手数を減らすものであり、記述を得る唯一の経路にはしない。

複製を行ったかどうかが利用者に分からなければならない（MUST）。押しても何も起きないように見える状態を作ってはならない（MUST NOT）。

#### Scenario: 記述の複製

- **WHEN** 写真に添えられた複製の操作を行い、本文に貼り付ける
- **THEN** その写真の記述が本文に入る

#### Scenario: 複数の写真が並んでいる場合

- **WHEN** 複数の写真が並んだ中の1枚について複製の操作を行う
- **THEN** その写真の記述だけが得られ、他の写真のものは混ざらない

#### Scenario: 双方の画面での一致

- **WHEN** 投入を終えた画面と記事の編集画面のそれぞれで同じ写真の記述を複製する
- **THEN** 得られる記述は同じである

#### Scenario: 複製が使えない環境

- **WHEN** 複製の手段が働かない状態で画面を開く
- **THEN** 記述は画面に読み取れる形で残っており、手で選んで写せる

### Requirement: 写真の提示は編集中の内容を失わせない

写真の一覧を見る操作、および一覧から記述を取る操作は、入力中のタイトルと本文を失わせてはならない（MUST NOT）。

これらの操作が内容の保存を伴う場合、保存が行われることが**操作を行う前に**分かる形でなければならない（MUST）。

#### Scenario: 一覧を見たあとの本文

- **WHEN** 本文を入力した状態で、その日の写真の一覧を見る
- **THEN** 入力していたタイトルと本文はそのまま残っている

#### Scenario: 記述を取ったあとの本文

- **WHEN** 本文を入力した状態で、一覧から貼れる記述を取る
- **THEN** 入力していたタイトルと本文はそのまま残っている
