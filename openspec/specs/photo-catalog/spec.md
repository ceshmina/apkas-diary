# photo-catalog Specification

## Purpose
投入された写真1枚ごとの記録を保持し、投入した直後の画面を閉じたあとでも写真に辿り着けるようにする。撮影に関する情報を、配信物から除去する前に読み取って残すことで、公開されるものを汚さないまま日記の側で使えるようにする。
## Requirements
### Requirement: 投入された写真は目録に記録される

元写真が投入されたとき、その写真は目録に記録されなければならない（MUST）。記録のために人が行う操作を要求してはならない（MUST NOT）。

記録は投入の経路によらなければならない（MUST）。手元の CLI から投入したものと、ブラウザから投入したものとで、記録の有無や内容が変わってはならない（MUST NOT）。

対象となるのは、日付の規約（`YYYY/MM/DD/<ファイル名>`）に沿って置かれた元写真である。手元の CLI にはキーを直接指定して**日付という軸から外れた場所へ置く**入口があり、そこへ置かれたものは属する日を持たない。日を持たないものを目録に載せてはならない（MUST NOT）。記録されなかったことは投入した者に示されなければならない（MUST）。黙って落としてはならない（MUST NOT）。

投入したものが目録に無い状態を作らないのは、「入れたはずの写真が見つからない」という形の失われ方を避けるためである。写真がどこにあるかを人が覚えていなければならない状態に戻さない。

#### Scenario: CLI からの投入

- **WHEN** 手元の CLI から日付を指定して写真を投入する
- **THEN** その写真が目録に記録される

#### Scenario: 日付の軸から外れたキーへの投入

- **WHEN** 手元の CLI からキーを直接指定して、日付の規約に沿わない場所へ写真を置く
- **THEN** 派生画像は通常どおり生成され、目録には記録されず、記録しなかったことが投入した者に示される

#### Scenario: ブラウザからの投入

- **WHEN** 編集アプリケーションから写真を投入する
- **THEN** その写真が目録に記録される

#### Scenario: 登録の操作の不在

- **WHEN** 写真を目録に登録するための操作を探す
- **THEN** そのような操作は存在せず、投入したことがそのまま記録になっている

### Requirement: 写真は変わらない識別子を持つ

目録の各記録は、その写真を指す識別子を持たなければならない（MUST）。識別子は写真ごとに一意でなければならない（MUST）。

同じ元写真のキーへの再投入は、2件目の記録を作ってはならない（MUST NOT）。既存の記録の更新として扱われなければならない（MUST）。このとき識別子が変わってはならない（MUST NOT）。

識別子は元写真のキーからも配信 URL からも独立していなければならない（MUST）。置き場所や URL の規約が将来変わっても、同じ写真を指し続けられるようにするためである。**識別子は目録の中の識別子であり、配信 URL の組み立てには用いられない。**

#### Scenario: 識別子の付与

- **WHEN** 写真を投入して目録の記録を見る
- **THEN** その写真を指す識別子が付いている

#### Scenario: 同じキーへの再投入

- **WHEN** すでに記録のあるキーへ別の内容の元写真を投入する
- **THEN** 記録は1件のままで、識別子は投入前と同じである

#### Scenario: 識別子と配信 URL の独立

- **WHEN** ある写真の識別子と配信 URL を比べる
- **THEN** 配信 URL から識別子は導けず、識別子は URL の組み立てに現れない

### Requirement: 記録は配信 URL と元写真のキーを持つ

各記録は、その写真の配信 URL と、元になった元写真のキーを持たなければならない（MUST）。

配信 URL を持つのは、参照する側が URL の組み立て規約を知らずに済ませるためである。組み立ての規約は `photo-delivery` が定めており、**目録はその結果を写して持つ**。

#### Scenario: 記録からの参照

- **WHEN** 目録の記録を読む
- **THEN** その写真の配信 URL が含まれており、組み立て直さずにそのまま参照できる

#### Scenario: 元写真への辿り

- **WHEN** 目録の記録を読む
- **THEN** 元になった元写真のキーが含まれており、投入し直すべき対象を特定できる

### Requirement: 写真は日付によって日記のエントリに紐づく

各記録は、その写真が属する JST の暦日を持たなければならない（MUST）。日記のエントリは暦日に対して一意であるため、この日付がそのままエントリとの紐付けになる。

紐付けのために、投入時の指定に加えて新しい入力を要求してはならない（MUST NOT）。

#### Scenario: 投入時の日付

- **WHEN** 日付 `2026-08-13` を指定して写真を投入する
- **THEN** その記録は `2026-08-13` に属し、同じ日付のエントリに紐づく

#### Scenario: 紐付けのための追加入力

- **WHEN** 写真の投入で求められる入力をすべて確認する
- **THEN** エントリとの紐付けを指定するための入力は存在しない

### Requirement: 日付を指定して写真を引ける

目録は、指定した日付に属する写真を、他の日の写真を走査することなく返さなければならない（MUST）。

同じ日に属する写真の並びは、読み出すたびに同じでなければならない（MUST）。

#### Scenario: 特定の日の写真の取得

- **WHEN** 日付を指定して写真を取得する
- **THEN** その日に属する写真のみが返り、他の日の写真は読み取られない

#### Scenario: 写真のない日

- **WHEN** 写真が1枚も投入されていない日付を指定して取得する
- **THEN** 空の結果が返り、失敗にはならない

#### Scenario: 並びの安定

- **WHEN** 同じ日付に対する取得を2度行う
- **THEN** 2度とも同じ順で並ぶ

### Requirement: 撮影に関する情報が記録される

目録は、元写真に記録されていた撮影に関する情報を保持しなければならない（MUST）。対象は、撮影機材の名称・レンズの名称・焦点距離・絞り・シャッター速度・ISO 感度・撮影日時である。

これらの情報は、元写真から派生画像を作る過程で読み取られなければならない（MUST）。**派生画像から情報が除去されること（`photo-ingest`）は変わらない。** 読み取りは除去の前に行われ、読み取った結果は公開される配信物には現れない。

元写真に情報が含まれていない場合、あるいは読み取れない場合、その項目は欠けたままでよい（MAY）。**情報が欠けていることを理由に、記録そのものを作らないでいてはならない（MUST NOT）。**

#### Scenario: 機材情報を持つ写真

- **WHEN** 機材名とレンズ名を含む写真を投入し、目録の記録を読む
- **THEN** 機材名とレンズ名が記録されている

#### Scenario: 撮影条件

- **WHEN** 焦点距離・絞り・シャッター速度・ISO 感度を含む写真を投入し、目録の記録を読む
- **THEN** それらが記録されている

#### Scenario: 情報を持たない写真

- **WHEN** 撮影に関する情報を持たない画像を投入する
- **THEN** 記録は作られ、撮影に関する項目だけが欠けている

#### Scenario: 配信物への非出現

- **WHEN** 記録に機材名がある写真の派生画像から付随情報を読み出す
- **THEN** 機材名は含まれていない

### Requirement: 位置情報は記録されない

目録は、元写真に含まれていた位置情報を保持してはならない（MUST NOT）。緯度・経度・高度・方位のいずれも、記録から読み取れてはならない（MUST NOT）。

保存しないことによって、公開側へ漏れる経路が最初から存在しない状態にする。**除去の担保を、保存したうえでの取り扱いの正しさに置き換えない。** 日記に位置情報を使う用途がない以上、持たないことがいちばん確かである。

#### Scenario: 位置情報を持つ写真

- **WHEN** GPS 情報を含む写真を投入し、目録の記録を読む
- **THEN** 座標はいっさい含まれていない

#### Scenario: 記録の全項目

- **WHEN** 目録が保持しうる項目をすべて確認する
- **THEN** 位置に関する項目は存在しない

### Requirement: 目録は配信の正ではない

目録の記録の有無が、写真の配信を変えてはならない（MUST NOT）。記録が失われても、既に配信されている写真は配信され続けなければならない（MUST）。

記録が存在することをもって、派生画像が配信可能であるとみなしてはならない（MUST NOT）。生成が終わったかどうかは、記録とは別に確かめられなければならない（MUST）。

目録は**配信されているものの写し**である。写しが正になると、写しの側の失敗が配信の欠落として現れるようになる。写真が配信される条件は、これまでどおり派生画像が配信先に存在することだけとする。

#### Scenario: 記録のない写真の配信

- **WHEN** 目録に記録のない写真の配信 URL を要求する
- **THEN** 派生画像が存在する限り、これまでどおり配信される

#### Scenario: 記録の直後の参照

- **WHEN** 記録はあるが派生画像の生成がまだ終わっていない写真の URL を要求する
- **THEN** 画像は返らない。記録があることは配信可能であることを意味しない

#### Scenario: 生成の完了の判別

- **WHEN** ある写真の派生画像が配信可能になったかを確かめる
- **THEN** 目録の記録の有無ではなく、派生画像そのものによって判別される

### Requirement: 目録へ書けるのは投入と変換だけ

目録に記録を書けるのは、写真を投入する経路と、派生画像を生成する処理に限らなければならない（MUST）。それ以外の経路から目録を書き換えられてはならない（MUST NOT）。

派生画像を生成する処理に与える権限は、目録の記録を書くことに限らなければならない（MUST）。同じデータストアにある日記のエントリを、この処理が読み書きできてはならない（MUST NOT）。

写真の記録を足すために、日記の本文を書き換えられる主体を増やさない。**日記はこのシステムでいちばん失いたくないものであり、それに触れる主体の数は増やさない側に倒す。**

#### Scenario: 変換によるエントリへの到達

- **WHEN** 派生画像を生成する処理が日記のエントリの読み書きを試みる
- **THEN** 権限がなく拒否される

#### Scenario: 変換による目録への書き込み

- **WHEN** 派生画像を生成する処理が目録の記録を書く
- **THEN** 書き込める

#### Scenario: 目録を書き換える操作の不在

- **WHEN** 投入を伴わずに目録の記録を書き換える手段を探す
- **THEN** そのような手段は存在しない
