# diary-entry-store Specification

## Purpose
日記エントリを唯一の正として長期に保持し、公開サイトの生成と将来の編集クライアントの双方が必要とする読み取りを、全件走査に頼らずに満たすためのデータストア。日記はアプリケーションのコードより寿命が長い前提で設計する。
## Requirements
### Requirement: エントリは1日1件

システムは日記エントリを暦日に対して一意に保持しなければならない（MUST）。同一日付への登録は新しい別エントリではなく、既存エントリの更新として扱われる。

#### Scenario: 未登録の日付に登録する

- **WHEN** 既存エントリのない日付でエントリを登録する
- **THEN** その日付のエントリとして新規に保存される

#### Scenario: 既に登録済みの日付に登録する

- **WHEN** 既にエントリが存在する日付でエントリを登録する
- **THEN** 同じ日付に2件目が作られるのではなく、既存エントリが更新される

### Requirement: 日付は JST の暦日、時刻は UTC で保持する

エントリの所属日は日本標準時（JST）における暦日として `YYYY-MM-DD` 形式で保持しなければならない（MUST）。作成日時と更新日時は UTC の ISO 8601 形式で保持しなければならない（MUST）。

#### Scenario: 日付をまたぐ深夜に書かれたエントリ

- **WHEN** JST の 2026-08-02 01:00 に書かれたエントリを 2026-08-01 の日記として登録する
- **THEN** 所属日は登録時に指定された `2026-08-01` となり、書かれた時刻によって前後の日に移動しない

#### Scenario: 作成時刻の記録

- **WHEN** エントリが保存される
- **THEN** 作成日時と更新日時が UTC の ISO 8601 形式で記録される

### Requirement: 下書きと公開を区別する

各エントリは「下書き」または「公開」のいずれかの状態を持たなければならない（MUST）。公開サイト向けの一括取得は公開状態のエントリのみを返さなければならない（MUST）。

#### Scenario: 下書きは公開向けの取得に現れない

- **WHEN** 下書き状態のエントリが存在する状態で、公開サイト向けの一括取得を行う
- **THEN** そのエントリは結果に含まれない

#### Scenario: 公開に切り替えたエントリ

- **WHEN** 下書き状態のエントリを公開状態に変更したのち、公開サイト向けの一括取得を行う
- **THEN** そのエントリが結果に含まれる

#### Scenario: 取得側でのフィルタを要さない

- **WHEN** 公開サイト向けの一括取得を行う
- **THEN** 取得結果に下書きが混入しないことがストア側で保証され、呼び出し側での状態による絞り込みを必要としない

### Requirement: 必要な読み取りパターンを全件走査なしに満たす

ストアは以下の読み取りを、対象外のエントリを走査することなく満たさなければならない（MUST）。

#### Scenario: 特定の日のエントリを取得する

- **WHEN** 日付を指定してエントリを1件取得する
- **THEN** 該当エントリのみが返り、他の日のエントリは読み取られない

#### Scenario: 指定した年のエントリを取得する

- **WHEN** 年を指定してエントリを取得する
- **THEN** その年に属するエントリのみが日付順で返る

#### Scenario: 指定した年月のエントリを取得する

- **WHEN** 年と月を指定してエントリを取得する
- **THEN** その月に属するエントリのみが日付順で返る

#### Scenario: 最新のエントリを取得する

- **WHEN** 件数を指定して最新のエントリを取得する
- **THEN** 公開状態のエントリが日付の降順で、指定件数まで返る

#### Scenario: 公開エントリを全件取得する

- **WHEN** 公開サイトの生成のために全エントリを取得する
- **THEN** 公開状態のエントリが日付順で漏れなく返る

### Requirement: エントリ以外のものはエントリの読み取りに現れない

同じデータストアにエントリ以外の種類のものが保持されていても、エントリの読み取りの結果にそれが現れてはならない（MUST NOT）。

対象となるのは、日を指定した取得・年別の取得・月別の取得・最新の取得・公開エントリの全件取得、および下書きを含む全件の取得のすべてである。**書き出しと公開サイトの生成が入力として受け取るものは、これまでどおりエントリだけでなければならない（MUST）。**

混入しないことはストア側で保証されなければならない（MUST）。取り出したあとに呼び出し側が種類で振り分けることを必要としてはならない（MUST NOT）。振り分けを呼び出し側に置くと、振り分けの漏れがそのまま公開サイトの生成物に現れる。下書きの除外を取得側のフィルタに戻さないのと同じ判断による。

同じストアに別の種類のものを置くのは、日記と写真が同じ日付を軸に並ぶためであって、両者を混ぜるためではない。

#### Scenario: 写真がある日のエントリの取得

- **WHEN** 写真が投入されている日付のエントリを取得する
- **THEN** 返るのはその日のエントリだけで、写真は含まれない

#### Scenario: 公開サイトの生成の入力

- **WHEN** 写真が多数投入されている状態で公開エントリの全件取得を行う
- **THEN** 返るのは公開状態のエントリだけである

#### Scenario: 下書きを含む全件の取得

- **WHEN** 写真が投入されている状態で、下書きを含む全エントリを取得する
- **THEN** 返るのはエントリだけで、写真は含まれない

#### Scenario: 呼び出し側での振り分け

- **WHEN** エントリを読み取る側の実装を確認する
- **THEN** 返ってきたものから種類で絞り込む処理は存在しない

### Requirement: 索引を用いるエントリの取得は他の種類のものに影響されない

日を指定した取得・年別の取得・月別の取得・最新の取得・公開エントリの全件取得は、エントリ以外のものが何件保持されていても、同じだけの読み取りで満たされなければならない（MUST）。

これらは公開サイトの生成が繰り返し行う読み取りである。**写真が増えるほどサイトの生成が重くなる、という形の結び付きを作らない。**

下書きを含む全件の取得はこの要件の対象外とする。この取得は編集アプリケーションの一覧と書き出しにのみ用いられ、公開サイトの生成の経路には現れない。

#### Scenario: 写真の増加とサイト生成

- **WHEN** 写真の枚数が10倍になった状態で公開エントリの全件取得を行う
- **THEN** 読み取られる量はエントリの件数だけで決まり、写真の枚数によって増えない

#### Scenario: 日を指定した取得

- **WHEN** 同じ日に写真が何枚投入されていても、その日のエントリを取得する
- **THEN** 読み取られるのはそのエントリ1件だけである

### Requirement: 誤操作からの復旧手段を備える

日記データは再取得が不可能であるため、ストアは過去の任意の時点への復旧手段を備えなければならない（MUST）。

#### Scenario: 誤って削除・上書きしたエントリの復旧

- **WHEN** エントリを誤って削除または上書きしたことに後から気づく
- **THEN** 障害発生前の時点のデータを復元できる

### Requirement: エントリの本文は Markdown として保持する

エントリの本文は、表示側の実装に依存しない Markdown テキストとして保持しなければならない（MUST）。整形済みの HTML を保持してはならない（MUST NOT）。

#### Scenario: 本文の保持形式

- **WHEN** エントリの本文を保存する
- **THEN** 入力された Markdown がそのまま保持され、HTML への変換は行われない
