# editor-hosting Specification

## Purpose
編集アプリケーションを独自ドメインで届け、使っていない時間に費用を発生させないための配信と実行の基盤。日記を書く時間は1日のうち数分であり、その数分のために計算資源を常時抱えないことを構造として担保する。
## Requirements
### Requirement: 編集アプリケーションは環境ごとに定められた独自ドメインで配信される

編集アプリケーションは、実行基盤が自動で払い出す名前ではなく、環境ごとに定められた独自ドメインで到達できなければならない（MUST）。環境が異なればドメインも異なっていなければならない（MUST）。そのドメインは公開サイトおよび写真の配信に用いるドメインと異なっていなければならない（MUST）。

独自ドメインでの通信には、そのドメインに対して有効な証明書が提示されなければならない（MUST）。

#### Scenario: 独自ドメインでのアクセス

- **WHEN** 利用者が環境の独自ドメインで編集アプリケーションにアクセスする
- **THEN** その環境の編集アプリケーションに到達する

#### Scenario: 証明書の検証

- **WHEN** 利用者が独自ドメインに HTTPS で接続する
- **THEN** そのドメインに一致する有効な証明書が提示され、警告なく接続が確立する

#### Scenario: 環境ごとのドメイン

- **WHEN** staging と production の編集アプリケーションのドメインを確認する
- **THEN** 互いに異なるドメインである

#### Scenario: 実行基盤の作り直し

- **WHEN** 実行基盤を作り直し、自動で払い出される名前が変わる
- **THEN** 利用者が使うドメインは変わらない

### Requirement: 通信は HTTPS に限定する

編集アプリケーションへの通信は暗号化されなければならない（MUST）。暗号化されていない経路で要求を受け付けてはならない（MUST NOT）。

平文の要求を受け取ってから HTTPS へ導く形は採らない。導く時点で、その要求の宛先と Cookie は既に平文で流れている。

#### Scenario: HTTP でのアクセス

- **WHEN** 利用者が HTTP で編集アプリケーションにアクセスする
- **THEN** 接続が確立せず、要求の中身が平文で送られることがない

#### Scenario: 以後の接続の保護

- **WHEN** 利用者が一度 HTTPS で接続する
- **THEN** 以後そのブラウザは、同じドメインに対して HTTP での接続を試みない

### Requirement: 使われていない間は費用が発生しない

編集アプリケーションは、要求を処理していない間、計算資源に対する費用を発生させてはならない（MUST NOT）。常時稼働する計算資源、および稼働の有無によらず時間あたりで課金される構成要素を、この基盤のために新たに設けてはならない（MUST NOT）。

#### Scenario: 使わなかった月

- **WHEN** ひと月のあいだ編集アプリケーションに1度もアクセスしない
- **THEN** 編集アプリケーションのために新たに発生した計算・配信の費用は生じない

#### Scenario: 待機している計算資源の不在

- **WHEN** 要求を処理していない時点で、この基盤が保持している計算資源を確認する
- **THEN** 要求を待つために起動されたままの計算資源は存在しない

### Requirement: 利用の開始に人手の操作を必要としない

編集アプリケーションを使い始めるにあたり、起動・停止の操作を人が行うことを要求してはならない（MUST NOT）。ドメインにアクセスするだけで利用できる状態にならなければならない（MUST）。

#### Scenario: しばらく使っていない状態からのアクセス

- **WHEN** 長期間アクセスしていない状態でドメインにアクセスする
- **THEN** 事前の起動操作なしに、そのまま利用できる状態になる

#### Scenario: 使い終わったあと

- **WHEN** 利用者が編集を終えてブラウザを閉じる
- **THEN** 停止の操作を行わなくても、費用の発生しない状態に戻る

### Requirement: 起動にともなう遅延には上限がある

要求を処理する準備ができていない状態からの最初の応答であっても、応答は所定の時間内に返らなければならない（MUST）。ここでは 30 秒を上限とする。時間内に準備が整わない場合、無応答のまま放置するのではなく、失敗として利用者に伝えなければならない（MUST）。

#### Scenario: 準備が整っていない状態での最初の要求

- **WHEN** 長期間アクセスしていない状態で最初の要求を送る
- **THEN** 30 秒以内に応答が返る

#### Scenario: 2回目以降の要求

- **WHEN** 最初の要求に続けて操作を行う
- **THEN** 起動にともなう待ちは生じない

#### Scenario: 応答が得られない場合

- **WHEN** 上限の時間内に応答を生成できない
- **THEN** 失敗した旨が利用者に返り、要求が無応答のまま残らない

### Requirement: 実行基盤には配信経路を経由してのみ到達できる

編集アプリケーションを実行する基盤には、定められた配信経路を経由せずに到達できてはならない（MUST NOT）。実行基盤が固有に持つ到達点を、そのまま外部に露出してはならない（MUST NOT）。

#### Scenario: 実行基盤への直接アクセス

- **WHEN** 実行基盤が固有に持つ到達点へ直接アクセスする
- **THEN** アクセスが拒否される

#### Scenario: 配信経路を経由したアクセス

- **WHEN** 独自ドメインを通じて同じ内容にアクセスする
- **THEN** 正常に応答が返る

### Requirement: 実行基盤の権限は自環境の日記データに限られる

編集アプリケーションの実行に与える権限は、自環境の日記データストアへの読み書きと、自らの動作に必要な設定値の読み取りに限らなければならない（MUST）。他方の環境のリソース、および写真や公開サイトの配信にかかわるリソースへの権限を与えてはならない（MUST NOT）。

#### Scenario: 他環境への到達

- **WHEN** ある環境の編集アプリケーションが他方の環境のデータストアへアクセスを試みる
- **THEN** 権限がなく拒否される

#### Scenario: 配信物への到達

- **WHEN** 編集アプリケーションが公開サイトまたは写真の配信元へ書き込みを試みる
- **THEN** 権限がなく拒否される

### Requirement: 編集アプリケーションの障害は公開サイトに波及しない

編集アプリケーションが停止・失敗しても、公開サイトおよび写真の配信は影響を受けてはならない（MUST NOT）。

#### Scenario: 編集アプリケーションの停止

- **WHEN** 編集アプリケーションが応答しない状態になる
- **THEN** 公開サイトと写真は従来どおり配信され続ける

#### Scenario: 編集手段を失っているあいだの登録

- **WHEN** 編集アプリケーションが利用できない
- **THEN** 従来の手元からの登録手段によってエントリの追加と公開は行える

### Requirement: 実行の記録が残る

編集アプリケーションの実行中に生じた失敗の原因を、後から追える記録が残らなければならない（MUST）。記録は環境ごとに分離されていなければならない（MUST）。記録は無期限に蓄積してはならず、保持期間を定めなければならない（MUST）。

#### Scenario: 失敗の追跡

- **WHEN** 編集アプリケーションが要求の処理に失敗する
- **THEN** その原因を特定できる記録が残っている

#### Scenario: 環境ごとの分離

- **WHEN** ある環境の記録を確認する
- **THEN** 他方の環境の実行に由来する記録は混ざっていない
